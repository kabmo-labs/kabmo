# AGENTS.md — OMPChamber AI System Instructions & Protocols

## Overview
**OMPChamber** serves as the developer web view console and diagnostic chamber for **AI Oh-My-Pi** (`oh-my-pi`), integrated with **remisJS** and **bun** runtime environments.

---

## Runtime: Bun Only

**This application runs exclusively on Bun. Do not introduce Node-only APIs, and do not assume `node <entry>` works.**

- **Server** (`src/server/**`) imports `bun:sqlite` and resolves the `@/` path alias — Node fails on both with `ERR_MODULE_NOT_FOUND`. Run it with `bun run src/server/index.ts` (dev, watched) or `NODE_ENV=production bun run src/server/index.ts` (prod). `bun run start` does the latter, and `ompchamber serve` is production by default (`--dev` selects the source entry).
- **Tests** run under `bun test`; do not add a Node test runner.
- **A suite that touches the database must isolate it (`isolateDb`/`releaseDb`, `src/test-support/isolated-db.ts`).** The handle is a PROCESS-wide singleton (`globalThis.__ompChamberDb`) and `OMPCHAMBER_DB_PATH` is read only while that handle is being opened, so setting the path inside a test — after another file already opened the handle — reads the developer's real `~/.ompchamber/db.sqlite` and WRITES to it. Verified: `bun test src/server/lib/panels/registry.server.test.ts` bumped the real database's mtime and left a test plugin id in its `omp_panel_plugins` row, and the panel scan is what reaches `getDb()` (it reads the disabled set), so a scan-only suite is not exempt. `isolateDb()` closes and clears the cached handle BEFORE pointing the path at a temp file, because the order is the whole point; `releaseDb()` closes it again and drops the directory.
- **CLI** (`src/cli/**`) is Bun too: `#!/usr/bin/env bun` shebang and `@/cli/...` imports, so it needs Bun on `PATH`. It resolves the Bun binary via `resolveBunBin()` and spawns the server with it. **Nothing in the toolchain runs under Node any more** — the client build is `Bun.build` (see Build & Dev Loop).
- **Practical rules:** never swap `bun:sqlite` for a Node driver; never add a `node:` import to `src/client/**` or `src/shared/lib/**`; keep `.ts`/`.tsx` execution in Bun's hands (no `tsx`/`ts-node`).

### Bun-Native APIs vs `node:*` Imports

Bun implements `node:*` builtins natively — they do **not** shell out to a Node binary. Verified: `node:child_process` runs with `node` off `PATH` and `process.execPath` stays `bun`. So a `node:` import is not a correctness bug; it is only a preference when Bun ships a first-class equivalent. **Do not "convert" a `node:` import to a `Bun.*` call when no equivalent exists** — the conversion is either impossible or silently changes behavior.

| Prefer | Instead of | Why |
|---|---|---|
| `Bun.env.X` | `process.env.X` | Same object in Bun (`Bun.env === process.env`), but the Bun name states the runtime. **Server/CLI only** — `Bun.env` does not exist in the browser, so `src/client/**` and `src/shared/**` must never use it. |
| `crypto.randomUUID()` (global) | `import { randomUUID } from 'crypto'` | Global is available; no import needed. |
| `Bun.gzipSync` / `Bun.gunzipSync` | `zlib.gzipSync` / `gunzipSync` | Byte-identical output, verified. |
| `Bun.YAML.parse` / `Bun.YAML.stringify(obj, null, 2)` | `yaml` package | Rust parser, zero-dependency. The third `stringify` argument (space) produces block-style multi-line YAML; without it output is flow-style single-line. **Caveat**: round-trip drops comments — files that must preserve user comments still need a document-model parser (the `yaml` package was removed because no remaining call site needs comment preservation). |
| `Bun.which('bin')` | `which` via `spawnSync` | Direct PATH lookup. |
| `Bun.spawnSync` / `Bun.spawn` | `child_process.exec`/`execFile`/`spawn` | Native `timeout`, `maxBuffer`, `windowsHide`, `detached` (process group), and `signal: AbortSignal` options. Unlike promisified exec, non-zero exits do **not** throw — check `exitCode`; timeout/kill detection uses `signalCode` (Bun sets `killed: true` even for normal non-zero exits). Server-wide: `lib/fs/shell.ts` wraps `sh -c` for shell strings; `lib/omp/rpc/lines.ts` reads NDJSON from Bun `ReadableStream` stdout (replaces `readline`). |
| `Bun.file(p).stream()` | `fs.createReadStream` | Returns a real Web `ReadableStream` for `new Response(...)` — no node-stream adapter or type cast. |
| `Bun.Glob.scanSync({ cwd, onlyFiles: true })` | `readdirSync` + regex filter loops | Rust-native globbing; supports `*.{a,b,c}` alternation. Returns relative paths; size guards still need `statSync`. |
| `await Bun.file(p).text()` / `.json()` | `fs.readFileSync(p, 'utf8')` / `fs.promises.readFile` | Only where the call site is already `async`. `Bun.file()` is async; do not force a sync caller to become async just to use it. Also: `.slice(a, b).text()` for partial reads (log follow), `.stat()`, `.exists()`. |
| `await Bun.write(p, data)` | `fs.writeFileSync` / `fs.promises.writeFile` | **`Bun.write` ignores `mode` when *creating* a new file (verified on Bun 1.4.0 and 1.4.2 despite the docs signature)** — it cannot create a `0o600` file; it is honored when overwriting an existing file. Keep `fs.writeFileSync(..., { mode: 0o600 })` for the CLI registry (`src/cli/lib/runtime.js`). |

**These stay `node:*` — Bun has no equivalent, so do not attempt a conversion:**

- **`node:path`** — `Bun.path` is `undefined`. No replacement exists. (The CLI uses its own minimal `src/cli/lib/path-utils.js` for join/resolve/dirname/home instead of importing `node:path`.)
- **`node:fs` directory + metadata ops** — `mkdir`/`readdir`/`stat`/`exists`/`rm`/`rename`/`Dirent`. Bun's own docs point at `node:fs` for directories; `Bun.file()` is for file contents (`stat()`/`exists()` are async BunFile methods where the chain is already async). `Bun.Glob.scanSync` covers readdir+filter scans.
- **`node:fs` sync reads in sync functions** — `Bun.file()` is async; the omp session/config layers are now fully async (2026-09), so sync reads survive only in genuinely sync contexts (module-level path setup, lockfile exclusive-create in `config/mcp.ts`, and the title-slot in-place 256-byte `r+` write where an offset write is required — Bun's FileSink cannot seek). Convert a read only when the enclosing call chain is already async; CLI bootstrap stays sync deliberately: sequential dependencies (mkdir → open fd → spawn → write registry), no concurrency to exploit, and signal-handler paths must not depend on pending promises.
- **`node:os`** — `Bun.os` is `undefined`. **Never replace `os.homedir()`/`os.tmpdir()` with `Bun.env.HOME`/`TMPDIR`/`TEMP` anywhere** — the env vars are absent when a process runs without a shell (cron, launchd, systemd, GUI launcher), and they yield `undefined`, not a fallback: `path.join(undefined, x)` throws, and in the CLI it produced `''` so `~/.ompchamber` silently became the cwd-relative `.ompchamber` (split-brain: `ompchamber stop`/`status` looked in the wrong directory and could not find a live server). `os.homedir()` falls back to `getpwuid()` on POSIX and `USERPROFILE` on Windows; `os.tmpdir()` walks `TMPDIR` → `TMP` → `TEMP` then `/tmp` (and strips macOS's trailing slash). This applies to `src/cli/**` too — `src/cli/lib/path-utils.js` uses `os.homedir()` for exactly this reason. Signal numbers use the local table in `src/cli/lib/process-lifecycle.js` instead of `os.constants.signals`.
- **`node:readline`** — no Bun equivalent for generic streams; `src/server/lib/omp/rpc/lines.ts` is the in-repo NDJSON reader for Bun spawn stdout.
- **`node:zlib` brotli** — `Bun.brotliCompressSync` is `undefined`; Bun ships gzip only (`src/server/plugins/compress.ts` keeps brotli here).
- **`node:child_process`** — fully migrated (2026-09): every `exec`/`execFile`/`spawn` call site now uses `Bun.spawn`/`Bun.spawnSync`, and `readline` usage is gone. Do not reintroduce `child_process`; new code goes through `Bun.spawn` (or `lib/fs/shell.ts` for shell strings).

### Toolchain Commands: Bun Only (no npm, npx, yarn, pnpm)

**`bun.lock` is the only lockfile.** `npm`, `npx`, `yarn`, and `pnpm` are never used in this repo — not to install, not to run scripts, not to execute a binary. Every tool that would otherwise be reached through `npx` is reached through **`bunx`**, which resolves the same local `node_modules/.bin` binary.

| Never | Always |
|---|---|
| `npm install` / `npm i <pkg>` / `npm uninstall <pkg>` | `bun install` / `bun add <pkg>` / `bun remove <pkg>` (add `-d` for dev deps) |
| `npm run <script>` | `bun run <script>` (or bare `bun <script>` when it is unambiguous) |
| `npx <bin>` / `npx -y <pkg>` | `bunx <bin>` — e.g. `bunx tsc --noEmit` |
| `node <entry>` / `tsx` / `ts-node` | `bun run <entry.ts>` — Bun executes TypeScript directly |
| `npx jest` / `npx vitest` / `npx mocha` | `bun test` |

- **Never commit** `package-lock.json`, `yarn.lock`, or `pnpm-lock.yaml`; if one appears, delete it and re-run `bun install`.
- `bunx` is preferred over `./node_modules/.bin/...` for readability; both hit the identical local binary.

## Architecture & Agent Roles

### The Oh-My-Pi Autonomous Agent (`oh-my-pi`)
- **Primary Function**: Autonomous CI/CD pipeline monitoring, build log analysis, dependency resolution, and edge deployment verification.
- **Runtime Target**: Bun 1.4.x with native ESM and TypeScript striping.
- **Framework Integration**: Elysia edge routes & Rsbuild plugins.

### OMPChamber Web View Interface
- **Session Sidebar** (left, default 268px): workspace folders bound to oh-my-pi projects, each listing its sessions, plus search/sort/archive toolbar and the settings/about/new-workspace/scheduler modals (`src/client/components/layout/session-sidebar/`).
- **The workspace list is the user's, and the omp-project sync only SEEDS it — once per database, and only while it is still empty** (`syncWorkspaceFoldersFromDiscovery`, `src/server/lib/db/workspace-sync.ts`, called once from `getDb()`). It is a bootstrap, not a background indexer: with any row present — bound or unbound, a hand-made grouping counts — it returns without touching the table, and `SYNC_WORKSPACE=false` skips it outright. Two conditions because "empty" has two meanings a row count cannot separate: a database that has never been seeded, and one whose owner deleted every folder on purpose. The `workspace_sync_ran` marker in `app_settings` covers the second, and it is written on EVERY path that decides — including the "list is non-empty, step aside" one, which is the upgrade path: an install that predates the marker arrives with folders and no marker, so skipping without recording would leave the hole open for exactly the installs that have been running longest. It is written BEFORE the insert loop — a pass that found no project still counts as run, or the first session written afterwards would seed the list. The sync's input is every session file under `~/.omp/agent/sessions`, and a session's cwd is whatever directory omp was spawned in, so without the gate each scratch directory that appeared after the user had curated their sidebar became a new folder on the next boot. Measured on the author's install: 556 session files carrying 43 distinct cwds, 33 of them scratch (`/tmp/omp-*`, `/var/folders/.../T/opencode/*`, `$HOME` itself), against a sidebar of 3 — and 88 folders already deleted, 13 of them in a single minute. The delete path is why it could not self-correct: it only tombstones the paths it saw (`deleted_workspaces`), so the next scratch cwd is a fresh insert, not a resurrection. Verified end to end on real boots against database copies: a curated 3-folder one stayed at 3 with no banner line, an emptied one seeded from discovery, one already carrying the marker stayed at 0 with the list empty, and a pre-marker 3-folder database recorded the marker on its first boot and then stayed at 0 after its folders were deleted. `workspace-sync.test.ts` pins both gates and both directions — a non-empty list is never appended to, an empty one is seeded, an emptied one is not refilled, a no-project pass still spends the one run, and a pre-marker database records it.
- **The New Workspace dialog is two tabs, and both of them write a row into that list** (`src/client/components/layout/session-sidebar/new-workspace-modal/`, reached from the toolbar's `FolderPlus` on both layouts). **Create** registers a directory that already exists; **Clone** fetches a repository and registers it in one step. Two tabs rather than one column of controls because the two flows ask for different things and neither is a variation of the other: Create needs a name and a listing to pick from, Clone needs a URL and a parent and produces its own name. The modal owns the ONE value both tabs share — the directory being browsed — so a folder entered in Create is the parent Clone shows; a second path state per tab is two fields that can disagree about where the user is.
- **The listing is read from `/api/fs/browse`, through one shared module** (`src/shared/lib/fs/browse.ts`, also used by `FolderPicker`, which `Browse…` still opens for deep navigation). Clicking a row ENTERS that folder and moves the path field with it: the dialog has no second destination, so a row can only mean "go there" and the path it sets is what a submit reads. **⟳ Refresh** re-reads the current directory; **📁+ New folder** opens an inline name field. The new folder is created, NOT selected — the listing is refreshed and the user picks it — because "make a folder" and "use this folder" are two decisions. A refusal (name taken, slashes in the name, missing parent) is reported inline and leaves the field open, since a refusal that closed it would read as success.
- **`mkdir` and `clone` are their own routes, NOT `/api/fs/action`'s `create`** (`src/server/routes/folders/{mkdir,clone}.ts`). That route scopes through `resolveRoot`, which only accepts the app root, a path beneath it, or a registered `project_path` — and the whole point of this dialog is to name a directory that is NOT registered yet (`~/projects`). A request for one would fall back to the app root and create the folder in the wrong place. So both routes validate an absolute existing parent themselves, and the folder name must be one path segment (`isSinglePathSegment`), which is what proves `join(parent, name)` cannot resolve outside the parent.
- **Clone checks the name collision BEFORE it clones, and removes the partial tree on failure.** A rejected workspace that already cost a full download is a failure the user can only undo by hand; and `git clone` creates the destination before it knows the fetch will work, so a failure leaves a partial directory in the user's projects. The workspace row is written from the RESOLVED destination — a name derived from the URL after the clone picked its own path is exactly how the row and the directory drift. `git` runs as argv with `GIT_TERMINAL_PROMPT=0` (`runGit`, `lib/fs/git-run.ts`), because a private repository would otherwise block on a credential prompt with no terminal to answer it and the URL is user input.
- **Both creation paths share one insert** (`registerWorkspaceFolder`, `src/server/lib/workspace/register-folder.server.ts`, used by `folders/create.ts` and `folders/clone.ts`): case-insensitive name guard, tombstone clear by CANONICAL key (a `deleted_workspaces` row for the same directory would otherwise make the new folder vanish on the next boot), the skill-discovery watcher sync, and the `sidebar-structure` signal. `isGitUrl`/`repoSlug` live in `@/shared/lib/git/url` so the Clone button's enabled state and the route's refusal read the same predicate — a per-caller copy is what lets the button enable on a string the server then rejects. Both routes refuse under `MOCK=true`.
- **Top Navbar**: active session title plus view controls — switch to mobile view, toggle the editor panel, and toggle the right panel (`src/client/components/layout/desktop-layout/TopNavbar.tsx`).
- **Chat Timeline** (center): the streaming agent conversation — thinking accordions, tool-call cards, rendered mermaid diagrams (click one to open the zoom/pan viewer in `src/client/components/common/diagram-viewer/`), queue panel, and the composer (`src/client/components/workspace/chat-timeline/`).
- **A running subagent is steerable and stoppable, from the roster and from its transcript.** `cancel_subagent` / `steer_subagent` are omp RPC verbs that act on ONE subagent without touching the parent turn, wired through `sessions/subagent-control.ts` (POST-only, id validated against the same grammar the transcript path derivation uses) and the `PASSTHROUGH_COMMANDS` set. The id is the ROSTER id the session file and `get_subagents` both report — measured on 18.8.3 it is a slug (`Sleeper`, `ListOmpws`), NOT a uuid, and the `subagent_progress` frame carries no `id` at all, so the roster is the only source. Both routes answer `409 session_not_running` for a session this process does not manage, because a subagent is by definition something the session's own child runs — the spawn path must never boot a child to answer "stop that". The UI is `SubagentControls` (a steer box plus a stop button, rendered in place of the transcript's composer ONLY while the subagent runs) and a stop button on each roster row, which is a SIBLING of the row's own button rather than nested inside it (a button in a button is invalid and swallows the inner click).
- **The subagent transcript renders the chat's own footer, in whichever variant the chat is in.** `SubagentView` passes `isMobile` down to `RunFooter`, so a phone gets the same compact row the main agent gets — provider • model • thinking inline, everything else (date, duration, tokens) behind the three-dot sheet — instead of the desktop row it used to draw. `showActions={false}` (and `userActions={false}` on its message rows) is the same rule the BTW panel follows: Retry / New-chat / Undo act on the CHAT, and this view owns no chat turn, so they would be dead buttons. **The thinking level must come from the CHILD, never the parent session** — a subagent routinely runs at a different level than the chat that spawned it. Two sources, because the two paths carry different data: a live child reports `progress.resolvedThinkingLevel` (omp's `AgentProgress`; `parseSubagentProgress` reads it), while an on-disk transcript records it as a `thinking_level_change` entry that `convertMessages` walks and stamps onto each non-user row (mirrors the server's `loadSessionMessages`). Note the frame shape: `subagent_progress` nests the `AgentProgress` under `payload.progress` and puts no `id` on the wrapper, so `readSubagentProgressFrame` unwraps it — reading the wrapper alone silently dropped every field the frame reports, including the resolved model. That reader is shared by the roster, the transcript hook and the server's liveness fold.
- **Editor Panel**: opened-file tabs and code editing (`src/client/components/workspace/editor/`).
- **Both editors draw the same type, from one module** (`src/shared/lib/code/editor/typography.ts`). The desktop editor and the phone's full-screen editor are the same surface on two layouts, so face and line box are shared while padding and gutter width stay per-layout. They were not: the stack was written out as a literal twice in the desktop editor and replaced by a bare `monospace` on the phone, which dropped Fira Code and put the phone's line numbers in a different face from the code beside them — the gutter was already `font-mono`. Two further drifts went with it: the phone used a px `line-height` (`20px`) that does not scale with the zoom control, so at 18px the rows were cramped and at 10px loose, and it pinned the gutter to `text-[10px]` and a fixed `w-10` while the code scaled, clipping a 3-digit line number at the top of the range. The line box is a ratio (`EDITOR_LINE_HEIGHT`) applied to the editor **and** its gutter — with word wrap off the gutter rows carry no explicit height and take their spacing from their own line-height, so a gutter pinned to a different value drifts out of register with the lines it counts. The zoom bounds are shared too (8–24px), because a phone clamped to a narrower range is a different editor, not a smaller one. Verified in the browser: at 12px both layouts measure `Fira Code / 12px / 18px` on the textarea, the `<pre>`, the gutter and the gutter line, and zooming to 18px moves all four to `18px / 27px`; the clamp stops at 8 and 24 on both.
- **The face itself is a setting, and only one of the offered faces is bundled** (`EditorFontSection`, `EDITOR_FONT_CHOICES`). `editorFontStack` puts the chosen family FIRST in the shared stack, so a face the device does not have falls through to the bundled Fira Code rather than replacing it — verified: an uninstalled family measures identically to Fira Code, not to a system serif. That property is why the picker can offer JetBrains Mono / SF Mono / Menlo / Consolas / Monaco / Courier New, none of which the app ships, and why the section marks Fira Code `Bundled` and previews each row in the face it names (an absent choice shows its own fallback before the user commits to it). A change has to reach an editor that is **already open**, which rules out reading `appSettings` — a boot-time prop, the way `keybindingSend` is read — so the picker broadcasts `omp:editor-font-changed` and `useEditorFontStack` subscribes, the same shape the theme uses; the event fires only when the value actually moved, or every unrelated settings toggle would churn every editor's stack. Verified live in the browser with no reload: the open editor's textarea, `<pre>` and gutter all moved from `Menlo` to `Courier New` in one step and stayed aligned, and the choice survived a full reload.
- **`SettingsState` holds only settings that do something.** 16 of its 26 fields were dead — declared and defaulted in the modal, never rendered, never read (`editorFont` among them, along with `tunnelEnabled`, `activeProvider`, `binaryPath`, …). They arrived in the Remix migration and were never implemented, and because `DEFAULT_SETTINGS` is only merged for display — `diffSettings` persists just the keys an edit moved — their fake defaults never reached SQLite either, so nothing downstream could have depended on them. `editorFont` was wired to the picker above rather than deleted; the other 15 were removed, and a field that only ever appears in `types/settings/state.ts` and `DEFAULT_SETTINGS` is now the signal that it was never wired.
- **Editor & Diff toolbars**: every action is an icon-only `<button>` carrying both a `title` and an `aria-label` (a bare `<svg onClick>` is unreachable by keyboard), and each reflects its own state — word wrap / preview / full screen are `aria-pressed`, Save shows `saving` → `saved` → `error`, and Copy flashes a check for 1.5s. Two rules the toolbars exist to enforce: **a failed read is reported, never substituted** (`useFileEditor` has no `fallback`; the mock sample it used to drop in was written straight over the real file by the next save), and **a failed save says so** (`reportSaveError`, since a silent failure left the user believing the file was written). A file whose read failed also has Save disabled — its buffer is empty, so writing it would blank the file on disk. The save status is reset when the active tab changes, because it describes the file that was written. Both toolbars are `@container`s, because the panel — not the viewport — is what runs out of room: the editor panel is 320px wide on a 1440px screen. The diff toolbar's action strip therefore **wraps** instead of scrolling: `overflow-x-auto no-scrollbar` clipped it invisibly (measured 361px of content in a 296px box, with `Stage` entirely outside it and no scrollbar to say so), and it now costs one extra row on a narrow panel and nothing on a wide one. The editor toolbar's path block is hidden below `@[420px]` for the same reason — the action strip is 273px of `flex-shrink-0`, which left the path a measured 23px of truncated fragment (the tab above already carries the name) — and its action strip carries `ml-auto` so it stays right-aligned once that block is gone.
- **Diff Panel toolbar**: `Discard` posts `actionType: 'revert'` — the server's own name for "restore this file from the index", and the one that handles the untracked case (removes the file). Sending `discard`, which no handler matched, returned `{success: true}` for doing nothing. Stage/unstage/discard await the response and surface a rejection in an inline error strip; the previous fire-and-forget submit flipped the badge optimistically and let a rejected action look successful. The Split/Unified segments each **set** their mode (toggling meant clicking the already-active segment flipped the view). The toolbar is an `@container`, so its labels collapse on a **narrow panel** rather than a narrow viewport — the editor panel is 320px wide on a 1440px screen, and `sm:` kept every label on, overflowing it. The `+n/-n` counts sit in the action strip rather than the identity block: the editor tab carries the file name but never the counts. A second segment pair beside Split/Unified chooses **how much of the file** is shown — `Diff Only` (default) or `Full Code`. It is a separate group because the two axes are orthogonal (Unified/Split is the shape of the rows, Full/Diff is how many there are), and each segment sets its own mode for the same reason the view pair does. The mode is not a client-side filter: it is sent as `fullContext=1` and `fetchWorkingFileDiff` adds `-U<large>` to every probe, so git itself emits the whole file in the same unified format — one parser and one renderer serve both modes, and the counts stay git's. `diff.contentMode` persists per session beside `diff.viewMode`. The probe's `maxBuffer` is sized off the content already read in full mode, because a killed process is not a success: `gitOut` would report the truncation as "no diff" and the synthesized whole-file fallback below would silently take over. **Word wrap is a third toolbar toggle, on by default** (`diff.wordWrap`) — a long line that runs off a 320px panel hides the very change the diff was opened for. It is not a CSS class swap on the scroller: both views are `<table>`s, and auto layout sizes a column by its widest cell's *unambiguous* minimum, which `overflow-wrap: break-word` does not lower — so the table kept widening and scrolling. Wrap therefore switches the table to `table-fixed` and drops the columns' `min-w-[320px]` (measured: unified `scrollWidth` 3875 → 396 with no horizontal scroll, one long cell 1890px → 99px). Split view additionally needs an explicit `<colgroup>`: fixed layout reads its widths from the FIRST row, and SplitView's first row is the `colSpan={4}` meta row, so every column came out equal (99px) and the line-number gutters grew to a code column's width — the colgroup pins them at 48px. One line = one row when wrap is off, which is what a column-aligned comparison needs.
- **Diff→editor conversion** goes through `useFileTabs().convertDiffToEditor`, which replaces the tab immutably and reuses `fileTabId` (`src/shared/lib/workspace/file-tab-id.ts`). The panel used to assign `activeFile.isDiff = false` on the object inside `layout.openedFiles`: React saw no change (identical array identity), and because that array is what gets persisted the mutation reached the database — the "diff" tab came back as a file tab after a reload and its diff never returned. If the target file already has a tab the diff entry is dropped instead, or the two would share an id.
- **Right Panel + Activity Bar**: switchable developer panels — `context` (Context & Telemetry), `files`, `search`, `git` (Source Control), `wiki`, `terminal` (Bun), `user-browser`, `browser`, `usage`, `todo` and `plan` (`src/client/components/workspace/`, `src/client/components/layout/RightActivityBar.tsx`).
- **Every right-panel view is a PLUGIN, including the eleven the chamber ships.** One catalog (`usePanelCatalog`, `src/client/components/workspace/plugin-panel/resolve.tsx`) merges the built-in views and the installed plugins, and the activity bar, the desktop panel stack and the phone's tab strip all render from it — so a view cannot be a table in one layout and a fetch in the other. `RIGHT_PANEL_TYPES` (`src/shared/lib/workspace/right-panels.ts`) stays the single source of the ORDER (it is shared, with no client import, because the width map and the persisted-id guard read it too), and `builtin.tsx` (`src/client/components/workspace/panels/`) is the built-in half: id, title, label, icon, a `lazy()` component, sizing and `requiresWorkspace`. **The `lazy()` wrapper is created at MODULE scope**, which is what `lazy-panels.tsx` used to arrange: a view's code stays in its own chunk, and because the wrapper's identity is stable across renders a view stays MOUNTED (its tree expansion, search results and terminal buffer alive) while the layout hides it with CSS. `requiresWorkspace` and `liveWhileHidden` are DATA rather than conditions at a call site: a view that reads the working tree is inert without a folder while one that reads the SESSION (`todo`, `plan`, `usage`, both browsers) is not — gating those showed "No session selected" over a list that was right there — and only the terminal stays live while another view is on screen, because it owns a live PTY. `panel-meta.tsx` and `lazy-panels.tsx` are gone with it; there is no per-view branch left in any layout.
- **Enablement is ONE axis and one store, and the ID PREFIX is what keeps the two kinds apart.** A built-in view is switched off by its BARE id (`git`, `files`, `terminal`) and a plugin by `plugin:<pluginId>` — the same key the client filters its catalog by and the same key the server tests before publishing a bundle. That prefix is load-bearing on the server too: `registry.server.ts` gates a plugin's bundle on `pluginPanelKey(manifest.id)`, and testing the bare manifest id there made a disabled plugin still report `enabled: true` while its panel stayed hidden — two answers for one question. The server stores whatever ids it is given and never learns which are built-in; `disabledPanels` travels on `GET /api/panels` and the client resolves its own views against it. **Absent means enabled**, which is what makes a freshly installed plugin live immediately, what shows every built-in view on a fresh install, and what keeps a database written before this feature from switching everything off. Two surfaces write the same set through the same `setEnabled(id, enabled)`: the activity bar's right-click menu (every panel, on or off, with its row kept while off — the only place it can be switched back on; nothing is pinned any more) and Settings → Panel Plugins' `BuiltinList` (all eleven with the switch a plugin card gets, and no Remove, because the code is in the bundle). The retired `hiddenRightPanels` list is folded into the disabled set ONCE, guarded by the old key's PRESENCE and deleting it as it goes, so the pass is idempotent and a view switched back on afterwards cannot be re-adopted (`migrateHiddenPanels`).
- **Two browser panels, one toolbar, and only one of them may offer device presets.** `browser-panel/` mirrors the tab this session's omp agent drives in the project-shared Chromium (a read-only screencast: status, URL, zoom, include-in-chat, copy, reconnect); `user-browser-panel/` is the user's own private iframe with real history and navigation. Both render `browser-toolbar/`, whose device cluster (`BrowserViewportSelector` + `ViewportMode`) is **optional** — the user panel passes it, the agent panel deliberately does not. A preset is genuine emulation only where the CSS box *is* the layout viewport (an iframe); on the agent panel it could just letterbox a fixed-resolution JPEG while claiming to emulate a device, and the cluster's 401px pushed the bar to `scrollWidth 482 > clientWidth 373` on a 373px panel, crushing the read-only URL to 18px. Agent-side emulation belongs to the agent itself (`tab.emulate()` / `browser.open({ viewport })`). `VIEWPORT_CLASSES` (`common/viewport.ts`) is therefore user-panel-only.

### Message-Footer Actions (Retry / Copy / Undo / New-chat)
- **A run footer describes the run, but its actions act on the TURN.** `RunFooter` gets the run's owner row (its last real AI message) for model/usage/duration, and `resolveRunFooters` now also carries the run's own boundary: `runStartIndex` / `runUserId` (the user row that opened it, `-1`/`''` for a transcript that starts mid-run) and `answerText` (every non-notice row between them, joined). An omp run spans thinking → tool calls → answer, so the owner row is almost never the row a user turn sits in front of. Measured on 498 real sessions (1453 footers): **Retry fired on 19.7% of footers before and 99.2% after**, and the copy payload differs from the owner row's own text on **48.4%** of runs (127 runs where the old copy produced nothing at all).
- **Retry re-runs the run's opening user row, and rewinds the JSONL first.** The old lookup required the owner's immediate predecessor to be a user turn and returned the list unchanged otherwise — a silent no-op that still aborted the live run, so clicking mid-stream stopped the answer and did nothing else. A real omp session now posts `POST /api/chat/:id/rewind` for that user row before re-sending: dropping only the client's rows left the abandoned turn on disk, and the next reload brought the "retried" answer back beside its replacement. The row-before-the-owner fallback survives for a caller that still hands over an AI row id.
- **Undo and Retry live together in `src/client/hooks/chat/timeline/rewind-actions.ts`** because they share those rules plus one more: **a refusal is reported**. `requestRewind` (`client/hooks/chat/timeline/rewind.ts`) returns the server's own reason, `reportActionError` (wired to the chat's toast stack from `ChatTimeline`) surfaces it, and the Undo dialog keeps itself open with an inline line as well. Previously a 400 was a bare `false` that only stopped the modal from closing — indistinguishable from a slow request.
- **A rewind cut point is a turn, not just a user message — and not always a record IN the file.** `isRewindCutPoint` (`server/lib/omp/session/rewind-file.ts`) accepts `type:"message"` with `message.role:"user"` **and** `type:"custom_message"` with `customType:"skill-prompt"` — omp expands `/skill:<name>` into a custom record and writes no user message for it, so the route's original role test refused every skill turn with `entry_not_found`. A builtin command (`/usage`, `/compact`, `/context`) goes further: it writes **no entry at all**, so its timeline row lives only in the chamber overlay under a client-side id (`msg-…-user`). The client therefore sends that row's own `startedAt`, and `truncateSessionBody` places a cut the file cannot name at the first file turn at or after that clock (a clock past every turn cuts at the end). `overlayCutClock` is the **requested row's** clock in that case, not the file turn's, so undoing one `/usage` also removes the next one; the overlay prune (`pruneStoredAfterCut`) drops rows at or after it, plus the file turns the cut removed. Verified over every user row of all 498 sessions: 1452 cuts, **0 refusals, 0 resurrections on reload, 0 earlier rows lost**.
- **A failed Undo leaves the draft alone.** The composer text is restored only AFTER the rewind succeeds: restoring it first read as "undo worked" while the turn was still on screen, and had to be cleared by hand.
- **A failed Copy says so instead of doing nothing.** `CopyButton` disables itself on an empty payload with a reason in its title/aria-label, because 8.1% of runs genuinely have no text anywhere (tool-only or aborted turns) and the old `if (!text) return` swallowed the click. The run footer passes its own "Nothing to copy — this run produced no text" wording.
- **New-chat from a row carries the row's attachments, and seeds the draft as a QUOTATION.** `onNewChat(content, attachments)` seeds `NewChatModal`, so an image or inlined text file is not dropped from the branched chat. The draft itself goes through `seedNewChatDraft` (`shared/lib/chat/new-chat-seed.ts`): the row's text, a blank line, then `---`, so the user types their instruction UNDER the quoted message instead of into the same paragraph. Two properties of that placement are load-bearing. The blank line before `---` is what keeps it a thematic break — a `---` directly under a line of text is a setext H2 underline, and the timeline renders every user turn as markdown, so the seeded message would come back as a heading. And the divider sits AFTER the seed, never before: omp parses a command token at the START of the prompt, so prefixing would turn a leading `/usage` into prose and stop it running. **Do not "harden" this by fencing the seed** — a fence changes exactly one thing (a command stops being a command), while protecting nothing: nothing on the chamber's side executes that text, and a `@agent` mention is rewritten by `translateAgentMentions` whether or not it sits in a fence (measured: raw, fenced and `---`-prefixed seeds all rewrite the mention). It would also turn the TUI-only names (`/plan`, `/clear`, `/hotkeys`) from a refused-and-reported turn into literal text the model improvises around, which is the failure `composer/tui-only.ts` exists to prevent.
- **The New Chat modal maximizes, and its composer grows with a ceiling.** A header button toggles the card between its default `42rem / 90vh` and an expanded `min(96vw, 1600px) / 92vh`, and the composer's textarea sizes itself to its content — `useAutoGrow` (`hooks/chat/composer/auto-grow.ts`) measures `scrollHeight` and clamps it between 80px and a ceiling (320px, 480px expanded), scrolling past it. The chat composer deliberately does NOT grow: its textarea is a fixed box, because the timeline owns that space and a composer growing on every paste would move the conversation under the reader. Two failure modes are pinned here. The card's size is applied as an **inline style, not `h-[92vh]`/`max-w-[min(96vw,1600px)]`** — an arbitrary-value class only exists if the CSS generator emitted a rule for that exact string, and a missing rule fails silently (the toggle reported `aria-pressed="true"` while the card kept its content height; measured in the browser, and the dev CSS bundle does not always regenerate). And the measurement resets `height` to `auto` first, because `scrollHeight` reports the height the box would need AT its current size — without the reset the box never shrinks back after a deletion.
- **The seeded bytes travel through `attachmentImage`, which also reads a `data:…;base64,` preview** — the load path never sets `dataBase64`, so a replayed image had no payload and was silently omitted from a retry or a seeded chat. `attachmentHasPayload` is the one predicate the composer's send guard uses, so a replayed image is not mistaken for an unreadable one.
- **Side effects that must happen EXACTLY once never sit inside a `setLocalMessages` updater.** Undo/Retry compute the truncated list from `localMessagesRef` and persist outside it; the updaters that still call `persistMessages` are full-array overwrites of the same row, which re-applying cannot double (noted at each site). `submitNewChat`'s `any[]` became `Attachment[]`, and committed rows are normalized through `toAttachmentList` rather than cast.
- **The pending "new-…" view offers the same actions as the real timeline.** `EmptyWorkspacePrompt` renders the same rows, so `ChatTimeline` passes `onUndo` / `onRetry` / `onNewChat` into it; without them the optimistic turn's footer and its user bubble drew buttons that did nothing until the omp session was adopted.

- **The New Chat dialog's first send is PARKED and fired by the render that carries its pending id — never dispatched from the handler that opened the dialog.** `useNewChatSubmit` (`hooks/chat/timeline/new-chat.ts`) writes `new-…` into the URL, parks `{ pendingId, text, attachments }` and lets an effect call the send path once `sessionId === pendingId`. The previous shape (`setTimeout(() => executeSend(...), 0)` inside `submitNewChat`) captured the render the dialog was opened in, so the FIRST prompt left against the session the dialog was opened FROM — for an omp session it landed in the previous chat, no spawn ever happened, no sidebar spinner was armed (the run had no server row at all), and the new chat showed an optimistic bubble with no stream until the operator typed a second prompt, which worked because the composer's own handler reads the pending scope. The same call carries the workspace: the pending session gets a `folderId` (the current session's owning folder, else the composer's pick, never overwriting one already in the URL), because the first send SPAWNS in that folder's cwd and a dialog opened from a session picked in the sidebar had no `folderId` at all — the send would have fallen back to the simulated stream. Verified in the browser against an isolated MOCK instance: the send navigated to `?sessionId=new-…&folderId=3`, issued no POST to the session the dialog was opened from, and rendered exactly one user bubble; `new-chat.test.ts` fails with the old dispatch restored.

### Generating State (timeline & composer dock)
- **One "a run is in flight" state serves the whole timeline: `timelineRunning = isGenerating || isSessionStreaming(streamStatusMap, sessionId)`** (`ChatTimeline`, `hooks/chat/timeline/index.ts`). `streamStatusMap` is the provider's `sessionId → streamStatus` map built from the `sidebar:status` topic (`hooks/chat/omp/session-list.tsx`), and `isSessionStreaming` (`hooks/chat/omp/session-statuses.ts`) is the exact `streamStatus === 'stream'` test the session item's `Loader2` spinner is drawn from. The docked indicator, the streaming row's marker and the withheld run footer all read `timelineRunning`, so they cannot disagree with the sidebar, and a run this page did not start — a second tab, a second chamber instance (the status row lives in the shared database and the child belongs to whichever process owns it), a scheduled task, a page that never attached to the stream because `GET /api/agent/:id` answers `running: false` for a wrapper this process does not hold — is still reported. **A THIRD source must not exist, and it is what this used to have.** `stream-pending` was a client-side mark armed by the send path and released by `onAgentEnd`/`onPromptSettled`, and its release depended on the client naming the session id it had armed: a mark armed for a pending `new-…` id and released under the adopted omp uuid was never released at all, and a mark re-armed by `onResumeStream` outlived the run it described. It forced `stream` into the sidebar's `folders`, so `isSessionStreaming` read it too and BOTH surfaces kept spinning over a finished turn — the reported "spinner and generating indicator run again after the stream has finished". The whole mechanism is gone (`stream-overlay.ts` → `sidebar-overlay.ts`, which now holds only the seen-strip and the title hint). The composer's own `isGenerating` prop stays the flag for Send-vs-queue and the model/thinking picks deferred to the next prompt — those belong to the run this client is driving — but **Stop follows `timelineRunning`**, because a run this page did not start (a second tab on the same session, a scheduled task, the goal driver's continuation, a reload that never re-attached) is still a run, the sidebar's spinner says so, and hiding Stop for it left the only control that ends a turn unavailable with nothing on screen to explain why. The press stays honest about ownership: `POST /api/agent/:id` answers a stop for a session this process does not hold with `session_not_running` (409) instead of falling through to the spawn path (`LIVE_RUN_COMMANDS`, `rpc/constants.ts`), which would resume the session FILE — a second writer on a file the owning instance is streaming — answer `abort` against the child it had just created, and then, on the `force_reset` escalation, destroy that same child. A run streaming on another instance therefore shows the rotating `COOL_VERBS` fallback: no frame ever named its activity here.
- **A run omp no longer owns is settled by the CHAMBER, on omp's own quiescence verdict** (`src/server/lib/omp/rpc/run-settle.server.ts`). A `stream` row is released by a terminal `agent_end`, and two shapes never send one: omp ends the turn with `agent_end {isTerminal:false}` (a detached subagent, a background job, a queued continuation) and the continuation never arrives, or the frame stream stops for any other reason. `streaming` then stays true for the life of the process, and nothing reaches the row: its owner is THIS process and it is alive, so the sidebar heal's staleness half sees a live pid and its orphan half only releases rows whose run this process does NOT hold; and `GET /api/agent/:id` answers a busy session from local flags precisely so a `get_state` cannot queue behind the running turn, so the one reconciler is never called. Measured on a real stranded child: the row survived 90s of sidebar loads and the attach probe answered `busy:true` throughout, while the transcript was complete — the reported "finished session spins forever". The repair is a probe of `get_state.isSettled` (omp's own "nothing live, admitted, scheduled, queued or awaiting background work"), and it is the ONLY thing allowed to settle: anything short of `true` touches no flag, so a mid-run probe can never blank a live run. The clock (`RunSettle`) is fed by every frame, fires after `RUN_SILENCE_MS` (30s) of quiet, and an announced retry wait (`auto_retry_start`'s `delayMs`) pushes the deadline out by the wait omp promised. On a settle it reconciles the flags through `buildWebState`, writes `finish` and emits the terminal `agent_end` — without that frame the clients keep `isGenerating` and the withheld run footer armed (verified end to end: row `stream`→`finish` at t+32s with no restart, and in the browser the indicator was replaced by the settled run footer). It is armed from the module (`loadSidebarData` asks each live wrapper, fire-and-forget, so the list never waits on a probe) and awaited from the attach probe, which is where the user's own click lands.
- **A provider retry is NAMED, because the run legitimately stays open across it.** omp replays transient provider errors by itself (`retry.enabled`, `retry.maxRetries`, honoring the provider's `retry-after`) and each retry announces itself with `auto_retry_start` and opens a fresh `agent_start` — no `agent_end` in between, so the sidebar spinner and the indicator were correct while the timeline said nothing about why nothing moved (measured: 2m43s on a real quota wall, last visible row an error). `shared/lib/chat/timeline/provider-retry.ts` folds those frames: the indicator reads `Retrying after a provider error 2/3 · next in 7s`, and the FIRST attempt of a saga (`attempt === 1`) leaves one persisted notice row so a reloaded chat still records it. **The phrase is sticky for the saga's duration** (`providerRetryVerbRef`, consulted by `setActivity`) because otherwise the attempt's own frames name a phase — `turn_start`/`agent_start` say "Thinking…" over a request that is about to fail, which is the uninformative spinner this replaced. Two traps are pinned by tests: the saga's own `agent_start` re-enters the loop and `onAgentStart` writes the indicator directly (bypassing the mirror), so the override must publish even when the mirror already holds the phrase; and a terminal `agent_end` closes the saga, since it can arrive with no `auto_retry_end` in front of it. Never settle a retrying run: `get_state.isSettled` is `false` throughout one (verified against real omp), which is what lets the two mechanisms share one predicate.
- **A committed history fetch never lands while a run THIS page started is live; the guard is keyed on `ownRunRef`, never on `isGeneratingRef` and never on the AI placeholder.** `useSessionLoad` (`hooks/chat/timeline/session-load.ts`) skips the `/api/chat/:id` payload entirely — no replace, no merge, no emptying — while a run THIS page dispatched is streaming, because that payload is a LAGGING snapshot: for a fresh spawn omp may not have written the session file at all (its writes are buffered until the first assistant message settles) and it never carries a segment still streaming. Keying the guard on the AI placeholder instead (`isGenerating && aiPlaceholderIdRef`) re-opened it mid-run, because the stream releases the placeholder at the first assistant `message_end` while the run continues — and both failure shapes were measured on real sessions: an empty payload emptied the list (the just-sent turn vanished), and a payload carrying the file's own copy of that turn was merged UNDER the live rows, whose ids differ (`msg-…-user` vs the echoed id), so the turn rendered twice. Keying it on `isGeneratingRef` alone was worse and is the bug this fixes: the mount probe that RESUMES a live run's generating UI (`useOmpAgent` → `onResumeStream`) sets that flag too, so merely OPENING (or reloading) a session another writer was streaming discarded its whole transcript — measured on a real 333-message run: 0 rows on screen with only a `Load earlier messages` button, whose click paged a window into an empty head and so appeared to do nothing. `ownRunRef` is claimed by the send path alone (`setGenerating(true, true)` in `hooks/chat/timeline/send.ts`) and released by `setGenerating(false)`, so a run merely ADOPTED still loads its history and an empty payload still clears a non-pending session. `session-load.test.ts` pins every direction (the own-run skip, the adopted-stream load, and the idle mount's load/clear).
- **The docked indicator names the WAIT when the run's identity is not known yet, instead of drawing an empty one.** A fresh spawn has no provider/model for its first seconds: a pending `new-…` session has no sidebar row yet, so `runModel` is null, and the resolved model only arrives with the spawn response (`seedSession`). `GeneratingIndicator` therefore renders `Loading…` when neither half resolves, rather than a bullet with nothing in front of it (`• Thinking…`, which is what the first prompt of a new session showed — measured in the browser: `Loading...` until the spawn answered, then `Kenari · Deepseek-V4-1-Flash · Thinking…`). One half is enough to name the run: a provider-only identity still says which account is answering. The rule lives in the SHARED component, so the chat dock, the empty-workspace view and the BTW panel cannot disagree about it.
- **The run footer is withheld from the streaming row by POSITION, never by its role spelling.** `resolveRunFooters` skips the footer while generating when `ownerIndex === streamingRowIndex(messages)`, and the guard must not also require the row's role to be `ai`: that is only the LIVE mapper's spelling, while `roleFor` (`shared/lib/omp/session/messages-map.ts` → `messages-parse.ts`) spells the rows a JSONL load produces for omp's `developer`, `custom` and `toolResult` entries `assistant` — and a run reopened mid-flight has exactly such a row at its tail, the last entry written before the streaming answer. Gating on `ai` settled the footer on the row the answer was still streaming into, which is what "the AI footer already rendered while the stream was running" was. `ownerIndex` only ever holds a non-user, non-notice row, so no role test is needed. Pinned by `run-footer.test.ts` and a rendered `MessageList.test.ts` mount (both fail with the role test restored), plus the `timelineRunning` gate above: a run this page did not start used to settle its footer too, for the same reason it hid the indicator.

### Agent Event Stream Transport
- The live omp agent bridge (`POST /api/agent/:sessionId` for commands) streams events over **WebSocket by default** — `GET /api/agent/:sessionId/ws` — with **SSE** (`/api/agent/:sessionId/events`) as the fallback, selected in **Settings → Chats → Streaming Transport** (`streamTransport` in `omp_chamber_settings`; default `websocket`).
- Server side is one Elysia app for dev and prod: `src/server/index.ts` owns the port and mounts `src/server/routes/`, so the agent WebSocket (`src/server/routes/agent/ws.ts`) is a first-class `.ws()` route on that same listener. Started by `bun run dev` (watched) and `bun run start` / `ompchamber serve` (production by default; `--dev` runs the source entry).
- Client side: `src/shared/lib/chat/omp/{transport,socket,sse}.ts` own the connections; both hand every frame to `src/shared/lib/chat/omp/agent-events.ts`, which folds it into chamber state. Keep frame handling in that folder — never fork behavior per transport. The two connectors are transport-generic (`connectSocket`/`connectEvents` take a URL); a session's BTW stream dials the same pair against `/api/btw/:sessionId/*` instead of adding a third flavour.
- **A spawned child streams `message_update` in FULL mode, because delta mode drops the tool call's identity.** `configureChild` (`src/server/lib/omp/rpc/child-config.ts`, called from `manager.ts` `initialize`) sends `set_event_filter {events:null, messageUpdates:"full"}`, so each frame carries the whole accumulated message and the client folds it as-is. `"delta"` was measured ~101× smaller on the wire (108 KB / 486 frames against 10.9 MB / 2217 on a 300-word prompt), but it drops the name and id a streaming tool call needs: `toolcall_delta` carries ONLY `{contentIndex, delta}` and `toolcall_start` carries no block at all, so both live solely on the `message_start` seed — which does NOT reliably contain the block. Measured on omp 18.10.3, the same model produced a seed of `[text, toolCall]` on one run and `[thinking]` on the next, so a card rendered a bare **Tool** for the whole argument stream and only snapped to `Write — <path>` at `toolcall_end`, which also swapped the card id (`tool-1` → `call_…`) and remounted it, dropping the reader's expand state. `full` makes the name and id readable from the first delta; the terminal frames (`message_start`, `message_end`, `turn_end`, `agent_end`) carry the full message either way. `delta-accumulator.ts` and `partial-json.ts` (the rebuild the delta projection required) are gone with it.
- **The frames that are NOT about the conversation live in `transport-frames.ts`.** `rpc_frame_error` (omp dropped a frame that exceeded the transport limit — names the type, so the notice says which step is missing), `extension_error` (an extension threw; omp keeps the session alive, so this is the only place it surfaces) and `session_settled` (the session went quiet — releases the optimistic generating state without waiting for the sidebar's next poll) are folded there, and so are the frames deliberately ignored (`cache_warming_*`, `retry_fallback_*`, `config_warnings_changed`, `ttsr_triggered`, `todo_reminder`, `todo_auto_clear`, `irc_message`) — listing them makes the omission a decision. `agent-events.ts` delegates to it from its `default:` branch.
- **A topic's `attach` is bound once per SUBSCRIPTION, so a replaced SOURCE needs an explicit `rebind`.** `hub.subscribe` runs the descriptor's `attach` when the first subscriber arrives and its cleanup when the last leaves — the topic is wired to whatever the source was at that moment. A session's omp child is routinely REPLACED while a tab stays subscribed: the idle reaper reclaims it after 10 quiet minutes (`IDLE_REAP_MS`), a composer access-mode change respawns it (`reconcileSpawnApprovalMode`), a crash destroys it, and `force_reset` (Stop's escalation) tears it down. Without a rebind the topic keeps pointing at the DEAD child's fanout: the subscriber holds its subscription and receives the fresh snapshot (so `onResumeStream` resumes the generating indicator) but **no frames ever arrive** — the answer looks like it never streamed until a reload re-subscribes and re-attaches. That is the reported "second prompt sometimes doesn't stream until I reload", and the spawn path is what fixes it: `startRpcSession`/`startNewRpcSession` raise the `session-attached` signal the moment the new child is reachable, and `publishSessionState` (`topics.server.ts`) now calls `getRealtimeHub().rebind(topic)` before its `republishSnapshot`. `rebind` drops the stale cleanup, re-runs `attach`, and is a no-op with no subscribers (a topic nobody watches must not hold a source open). Pinned by `hub.server.test.ts` (frames follow the replaced source; no subscribers → no attach) and `topics.server.test.ts` (a `session-attached` signal detaches once, re-attaches, and re-snapshots the subscriber).
- **Steering uses omp's `steer`, never `abort_and_prompt`.** "Send Now (Steering)" on a queued row used to post `abort_and_prompt`, which CANCELS the running turn and starts a new one — the answer the user was watching was thrown away. Measured on omp 18.8.3 with a counting turn: `steer` produced one `agent_start`/`agent_end` pair with the model answering inside the same run, `abort_and_prompt` produced two of each. `OmpAgentHandle.steerOmpRun` (`src/client/hooks/chat/omp/index.ts`) posts `steer`, and because a steer creates no run boundary the `interruptPendingRef` guard that existed to survive `abort_and_prompt`'s abort-then-restart is gone entirely.
- **Session auto-titling is ONE-SHOT per conversation, with one retry inside the first run** (`src/server/lib/omp/session/auto-title.server.ts`, fired from the `message_end` and `agent_end` branches of `src/server/lib/omp/rpc/frame-fold.ts`). omp force-sets `PI_NO_TITLE=1` under `--mode rpc-ui`, so the chamber asks for the title itself by sending `/rename` to the child. **The trigger is the first settled USER message, not `agent_start`** — omp pushes `agent_start` before the turn opens, so the transcript is still empty there and a `/rename` at that point reads `messageCount: 0` and is answered "Could not generate a session title" (measured on omp 18.3.0: the user message lands ~120ms after `agent_start`). `message_start` is equally too early — omp appends the message to the agent's state on `message_end`, so only that frame makes `get_state` report it. `agent_end` then retries ONCE as the fallback, for the early attempt that came back empty (provider error, timeout, child gone, or the tiny model declining); it stands down when the early generation is still in flight (`autoTitleWindowUntil` unexpired — re-asking would reserve a fresh title revision and cancel it) and is a no-op when the name already landed. Never fire it beyond that: omp derives the title from the NEWEST turns and `generateRenameTitle` reserves a fresh title revision (cancelling any generation still in flight), so an attempt after turn two names the session after whatever the conversation had become by then — the bug this gate exists to prevent. The eligibility latch is `AgentSessionWrapper.autoTitlePending`, seeded in `applyIdentity` from omp's own `messageCount` (a `--resume` child reports the messages it restored, so an existing session is ineligible from the start) and consumed by the settle attempt — the early attempt deliberately does NOT consume it, or a first-turn failure would leave the session unnamed for good. `autoTitleRequested` (reset at each `agent_start`) keeps a queued steer message from re-asking inside the same run. A first message omp's low-signal filter rejects ("hi") therefore leaves the session unnamed for good — the honest outcome, since the fallback does re-ask and omp declines a second time (the rejection is a property of the opening message, not of when it is asked). **omp 18.9.0 added title CARDS and the chamber carries them through rather than stripping them**: `title.icons` (default `nf+emoji`) heads a generated or renamed title with an icon and a short code — `formatCardTitle` emits `🧪 FLAKY: Fix flaky park tests` — and `sessionTitleFor` returns `session.name` verbatim, so the sidebar renders exactly what omp's own TUI renders. No card-aware branch is needed (the prefix is part of the name omp persisted), and a user who wants plain names sets `title.icons: boring`, a row the panel gained with the 18.9.2 schema. The card is also why `/rename` now takes longer: a title with no card triggers a SECOND title-model request for the card (`renameTitle` → `#cardIcons` → `generateTitle(named, cardPrompt)`), which the 60s `AUTO_TITLE_OUTPUT_WINDOW_MS` has room for.
- **A `prompt_result` that opened no turn is suppressed for as long as the operator's turn streams, and the RUN is the attribution — not the `/rename` request window.** `frame-fold.ts` forwards that frame only when the run is not streaming; the auto-title window (`titleClaimArmed`) was not enough on its own, because it is armed around the `/rename` and omp answers that command within the same tick (measured ~3 ms on omp 18.7.0), so an ack that won the race reached the client anyway. The client folds this frame as "the run settled" (`agent-events.ts` → `onPromptSettled`), which blanks the docked indicator and drops the optimistic user mark — so the turn's own echo was appended beside the bubble it stood for, and the chamber's copy of the conversation held `msg-…-user` and the echoed row side by side for one prompt (measured on real sessions; the indicator died ~450 ms into a 20 s run, and the turn rendered twice). The rule covers every auxiliary sender that answers on this frame — a Plan/Goal toggle, `/reload-plugins`, `rename-with-ai`, a peer instance's command — and the run's flags are left alone, exactly as the dispatcher leaves a non-owning command's (`rpc/session-commands.ts`). A builtin the operator typed while the agent is IDLE still passes through untouched: that is the case the frame exists for.

### Internal-URL Reads (`read xd://…`, `skill://`, `omp://`)

- **`read xd://<device>` is the device's DOCUMENTATION, not a call, and it is the READ panel.** omp's `XdProtocolHandler#usage` answers a read of `xd://` (the listing), `xd://<device>` and `xd://<device>/<topic>` with `xdevDocs` — the `# <name> — <title>` page — and its own reader has no `xd://` read card (unlike `proc://` and `cfg://`), so it draws an ordinary read. Dispatching by device instead sent the doc page to the device's panel: `read xd://lsp` drew the LSP diagnostics card, `read xd://mcp__codegraph_explore` the MCP argument/result card, and `read xd://eval/browser` (the `eval` device's `browser` topic) the eval card — three panels for one class of call. `isXdDocRead`/`xdDocPath` (`tool-renderers/registry.ts`) gate on the **READ transport plus an `xd://` path**, tested before `xdDevice`; the WRITE transport is untouched, because `write xd://lsp` genuinely IS a call. `xdDocPath` returns the FULL path — `xdDevice` reports `eval` for `xd://eval/browser` and the card named the wrong thing.
- **A doc read's URL is its identity, so the card shows it.** `toolCardSubtitle` hides a bare `xd://` URL because for a device CALL the URL is transport (the device names the action); for a doc READ the URL is what was read. The card was otherwise `Read Done` with `aria-label="Expand Read"` — nothing naming it. Verified in the browser: `Read · xd://eval/browser · 77 lines`.
- **A path with no language answers `text`, not `javascript`.** `getLanguageFromPath` defaulted to `javascript` for an extensionless file, an internal URL or a web URL, so a `read` of one was badged `JAVASCRIPT` and its prose was tokenized as code. omp's own `getLanguageFromPath` returns `undefined` for the same input, and `text` is a Shiki SPECIAL language — always loaded, no grammar fetched, emitted escaped and uncoloured — so the badge and the tokenizer both stop claiming a language the input does not have (verified: `src/x.ts` still reads `typescript`). A `read xd://<device>` reached this badge only until it was given its own markdown branch (below); it now reads `Markdown`.
- **The read SELECTOR comes off the path first, or the language is lost with it.** `read` may name its lines on the path itself — `src/App.tsx:23-300:raw` — and the extension was read off the raw string (`tsx:23-300:raw`, an unknown extension), so `getLanguageFromPath` answered `text` and the code surface rendered unhighlighted. Only a `:N-M` suffix was ever stripped; measured on a real session store, **9517 of 18128** read paths carry a selector and **1268 of those — every `:raw`, `:img` and comma list — were missed**. `stripReadSelector` (`shared/lib/fs/paths.ts`) peels omp's whole grammar (`:N`, `:N-M`, `:N-`, `:N+K`, `:-N`, a comma list, `:raw`/`:conflicts`/`:img`, and a compound `:1-50:raw` / `:raw:-60`), mirroring `splitPathAndSel` in `@oh-my-pi/pi-tui/tools/read.ts` — including its trailing rule (a chunk must END in a digit, `.` or `-`, which is what rejects the in-flight `:50+`) and its conservatism about a bare `a:1-50` filename. A URL is returned untouched: its colon can be a PORT (`http://host:8080/x` would otherwise lose `:8080` to the line-range rule) and no fs route ever receives one. It is used by the language detector, the Read panel's `/api/fs/read` + `/api/fs/raw` path (`x.png:raw` read as an unknown extension, so the image sniff said "not an image") and `getFileExtension`. Verified in the browser on the `:23-300:raw` sample: badge `tsx`, 41 Shiki spans coloured; the plain `app/types/chat.ts` read still reads `TYPESCRIPT` with 63 coloured spans.
- **A `text/markdown` read renders as prose.** omp draws it as the document it is (`details.contentType === 'text/markdown' ? md(text) : code`); the panel had no markdown branch, so `read skill://diagnose` rendered `# Diagnose ## Steps 1. Reproduce` as one code block — the file's headings, lists and links came out as literal syntax. 86 internal reads carry that content type (`skill://` 11, `omp://` 22+, `agent://`), and 38 real `.md` file reads do too. The source is omp's own `displayContent.text`, never `rawContent`: omp prefixes every row of the raw output with its file line number (`1|# Diagnose`) and a markdown parser reads that gutter as content, turning the heading into the paragraph `1|# Diagnose`. The gutter-stripping parser (`parsedCode.cleanCode`) is only the fallback, because it needs TWO numbered rows to recognise the format — a one-row document (`read xd://propose`, a real payload) kept its `1|` prefix through it and rendered as the paragraph `1|Write your plan's <slug> …`.
- **A `read xd://<device>` is markdown too, even though omp tags it `text/plain`.** The device documentation (`# <name> — <label>`, `## Schema`, a ```ts fence) is the same prose a `skill://`/`omp://` read carries; only `XdProtocolHandler`'s hardcoded `contentType: "text/plain"` distinguishes it, and the panel had no branch for it — measured over every `xd://` read of a real install (220 rows, 11 distinct documents): all of them rendered as one `<pre>` of literal syntax behind a `TEXT` badge, `# ast_edit — AST Edit` and `## Schema` included. `isXdDocRead` widens the markdown predicate, so the badge reads `Markdown` and the prose renders as prose (verified in the browser: badge `Markdown`, no `<pre>`, the card body is `.prose-content`). A FAILED doc read is excluded — `read xd://nope` answers "No such tool: …", a refusal rather than a document, and it keeps the code surface.
- **The demo dataset carries a doc read.** `virtual-devices-session` renders `read xd://eval/browser` with the measured `details` (`contentType: text/plain`, `totalLines`, `displayContent`), so the badge, the URL subtitle and the prose surface are all exercised under `MOCK=true`. `tools-session` likewise carries `call_01b_read_selector` — a read whose path is `src/App.tsx:23-300:raw` — so the selector strip is exercised in the demo, not only in a test.

### Image Reads (tool renderers)

- **A `read` of a picture answers with the picture, so the panel paints the RESULT's bytes — never a re-read of the path it names.** omp's toolResult carries `{type:'image', data, mimeType}` beside its text note, and externalizes anything large to the content-addressed blob store (`blob:sha256:<hash>`; measured on this install, 421 of 435 image blocks across the session files are refs). Both parse paths now carry it: `extractToolImages` (`src/shared/lib/omp/session/tool-images.ts`) is applied by the reload pass (`collectToolOutputs` + the inline `toolResult` blocks) and by the live fold (`recordToolResult`, `tool_execution_end`), landing on `ToolCallData.images`.
- **The old path-only reconstruction was broken for exactly the reads people screenshot.** The panel pointed `/api/fs/raw?path=<target>` at the tool call's path, but that route only serves paths inside the browse scope and `read` routinely names one outside it (`/tmp/shiki96.png`) — so the panel drew a broken image while the bytes sat in the transcript. `readFailed` (`status: 'error'` / `isError`) suppresses the fallback too: a failed read ("Path '/tmp/x.png' not found") names a picture that is not there, and pointing an `<img>` at it drew a broken thumbnail over an error message.
- **Blob bytes are served by `GET /api/omp/blob?hash=` (`src/server/routes/omp/blob.ts`).** `readBlobImage` resolves the content type from the BYTES first (`getImageMimeFromBytes`, magic-byte table in `file-kind.ts`) and from the sibling extension link second, because omp stores the blob under its content hash and the extension lives only on a hardlink beside it — and because the type is not cosmetic: a 96×96 PNG read came back as a JPEG blob, and `image/*` is what makes the browser paint instead of download. The hash feeds a `path.join` against the store, so `readBlob`'s canonical-digest guard is the security boundary (verified: `../../etc/passwd` and a truncated digest both 404 before touching the filesystem). An inline payload becomes a `data:` URL instead — re-encoding megabytes into every session load is what the store exists to avoid.

### Process Supervision (`proc://`, and the legacy `hub` tool)

- **`proc://` is omp's device for background jobs, project services and live agents, and it is reached through the `read`/`write` TRANSPORT — so the URL, never the tool name, decides the panel.** omp replaced the `hub` tool with it (`hub` last used 2026-09-24; `proc://` from that same day on; 298 `proc://` calls and 503 `hub` calls in the author's session store). The grammar is `internal-urls/proc-protocol.ts`: `proc://` lists, `proc://<id>` reads status/log, `write proc://<id>` sends stdin (empty = Enter), `write proc://<id>/kill` cancels a job or stops a service, `write proc://<id>/mode` sets `persist|session|detached`. `toolPanelKind` (`tool-renderers/registry.ts`) tests `procPathOf(tool)` FIRST — before the `xd://` device and before the tool's own name — and `resolveToolKey` returns `proc`, so `write proc://x/kill` is a Proc card and not the EDIT panel (which rendered the stdin payload as "Written File Preview") while `read proc://x` is not the READ panel (which rendered the service log as file contents under a `javascript` badge).
- **One reader for every result shape, in `src/shared/lib/omp/session/proc.ts`.** Measured shapes of `details.proc`: `{action,daemon}` (stop/stdin), `{action,daemon,input}` (stdin), `{action,daemon,mode}`, `{daemon,log,terminalRows}` (a service read), `{job,log}` (a job read), `{jobs,agents,daemons}` (the listing), `{op:'cancel',jobs,cancelled}` (a job kill). The legacy `hub` tool carried the same keys at the TOP level of `details` (`{op,daemon}`, `{jobs}`, `{daemons}`), so `procViewOf` prefers the nested bag and reads through to the top level — one `ProcView` for both, which is why `hub`'s `PANEL_KINDS` row is `'proc'` and not a second panel. `procOpLabel` maps omp's action to the word a reader sees (`stop|kill` → `stop`, `read|list` → `list`), and `procRequestOp(path, toolName)` resolves the one ambiguity the path alone cannot: a bare `proc://<id>` is `stdin` on the write transport and `read` on the read transport.
- **`panels/Proc.tsx` is the body** (it replaced `Hub.tsx`, which only ever read `details.jobs`/`details.items`). It draws the daemon fact strip (state with its own tone, pid, `up`/`ran` span, exit code, restarts, persist/detached), the stdin payload a write sent, a job row, the `cancelled` outcomes a kill returned, and the listing as three groups (Services / Jobs / Agents). Terminal rows are ANSI-stripped — omp hands the log back terminal-formatted (`\u001b[0m\u001b[2;38;5;11m$\u001b[0m …`), and the panel is not a terminal. A named process is deliberately NOT echoed as raw text under its own facts (`Started ompchamber: ready pid=43148 …` under `ready · pid 43148` is one sentence twice); a FAILED call still shows its reason.
- **The span a daemon reports is the span it RAN, not the time since it started.** `procUptime` ends at `exitedAt` when the daemon exited — a service that died an hour ago has not been up for an hour. Verified in the browser against a real transcript: the card read `exited · ran 16m 29s · exit 0`, and the header facts read `stop · exited · ran 16m 29s · exit 0`.
- **Facts and phrases ride the same reader.** `src/shared/lib/chat/tool/proc-facts.ts` (split out — `summary.ts` is at the size ceiling) produces the chips, and `toolSummary` guards its `read`/`write` branches with `isProc` so a `proc://` write can no longer report `1 lines` (the line count of its own stdin payload) or a `proc://` read a file size. A cancelled job is excluded from the process count — counting it said `1 process · 1 job cancelled` for a kill that found exactly one job. `describeToolActivity` returns `Stopping <id>` / `Sending input to <id>` / `Setting mode on <id>` / `Reading process <id>` / `Listing processes`, because `Reading proc://ompchamber-dev/kill` describes a service stop as a file read.
- **A `bash` that launches a named service answers with `details.service` — the same snapshot, read by the same code.** 442 real results carry it (`{name, state, ready, timedOut, pid}`). `Bash.tsx` renders it as a strip above the command (name, state, pid, span, exit code, and the `read proc://<name>` it can be inspected with) and `bashServiceFacts` gives the collapsed card its chips; without either, the only thing the card said about a live dev server was its exit code. Verified in the browser on a real session: `SERVICE · tls-fixed · ready · pid 81406 · read proc://tls-fixed`.
- **A virtual URL never reaches `/api/fs/read`.** The Read panel's lazy fallback points that route at whatever path a `read` named, and `proc://ompchamber-dev` is not a file: the route refused it and the panel printed `// Loaded file: proc://ompchamber-dev` as if that were its contents. `isVirtualPath` (`shared/lib/fs/paths.ts`) gates the fetch; a bare `C:\x` (one colon) stays a path. Verified in the browser: zero fetches for the virtual URL, and `src/x.ts` still lazy-loads.
- **The demo datasets carry the real shapes.** `tools-session`'s `hub` sample has its measured `details`, and `virtual-devices-session` renders a `proc://` read (a ready daemon with ANSI terminal rows) and a `/kill` (the same daemon exited) from `samples/virtual-devices-proc.ts` — split out because that session file is at the size ceiling. A sample without `details` renders as a fallback and hides every panel bug this section exists to prevent.

### Dictation (composer mic button)

- **The mic button runs omp's OWN speech-to-text, not a second implementation.** omp ships STT as a TUI feature — `stt.enabled`, `stt.modelName`, `stt.submitTrigger` under Interaction → Speech — with local on-device models and no API key. It is turned on by the `app.stt.toggle` keybinding and captures the microphone of the machine running the TUI through `@oh-my-pi/pi-natives`' `AudioCapture`.
- **None of that surface reaches a web client, which is why the chamber drives the WORKER instead.** Verified against omp 18.4.10: `stream_start` / `stream_audio` / `stream_stop` / `stream_cancel` / `transcribe` / `download` are all answered `Unknown command` over `--mode rpc` (the surface the chamber's agent bridge uses), and no STT entry exists in `get_available_commands` — it is neither a slash command nor a tool. What omp does expose is `omp __omp_worker_stt`, and its transport is **Bun IPC, not stdio**: the worker is spawned with `stdin`/`stdout` set to `ignore`, `serialization: "advanced"`, and frames arrive on the `ipc` channel. A stdio client sees a silent, unresponsive process. The chamber runs on Bun, so `omp-stt-worker.ts` spawns the same worker and speaks the same frames.
- **Frames** (request/response by `id`): → `{type:'ping', id}`, `{type:'transcribe', id, modelKey, audio, language}`; ← `{type:'pong', id}`, `{type:'progress', id, event}`, `{type:'transcription', id, text}`, `{type:'error', id, error}`. `audio` is a **`Float32Array` of normalized samples at 16 kHz**, sent as structured clone over the IPC channel — NOT base64 and not an encoded file (a base64 WAV string fails with "AudioContext is not available in your environment"; a `Uint8Array` fails with "expects input to be a Float32Array"). The browser side captures PCM16, and `src/server/routes/dictation/ws.ts` converts with `pcm16ToFloat32` before `transcribe` — so the PCM16 lives on the WIRE (browser → server), not in the worker frame. omp 18.8.x also exposes a STREAMING path (`stream_start`/`stream_audio`/`stream_stop`/`stream_cancel` with `partial`/`segment` events, segmented by the worker's endpointer) which the chamber does not use yet: it still sends one utterance per socket, which is what omp's own TUI does (its text appears on release, not per word).
- **Model keys are omp's, and the default is deliberately NOT omp's.** The four keys are `whisper-base`, `whisper-small`, `whisper-large-v3-turbo`, `parakeet-tdt-0.6b-v3`; anything else answers `Unknown stt model`. omp's own default is Parakeet v3, which covers **25 European languages only** — so the chamber defaults to `whisper-base`, the smallest MULTILINGUAL tier (~80 MB on first use). A first run that downloads 465 MB to transcribe a non-European language wrongly is the worst possible default.
- **One utterance per socket, and the audio travels in ONE frame.** Streaming chunks while the user speaks buys nothing: omp's STT is not incremental (its own TUI inserts text on release), so a chunked transport would only add reordering and reassembly for a result the final decode replaces. The socket exists for the other direction — the server pushes model download progress while a first-run decode waits on a fetch.
- **The two progress numbers under the same field are different quantities, and neither is dependable enough to trust blindly.** `progress_total` covers the whole download while `progress` covers a single file, so only the former may set the figure — the per-file value taken as the total jumps backwards at every file boundary. But on a real first-run fetch (omp 18.4.10, ~76 MB at ~68 KB/s) the total reached 100 within the first eight seconds and then climbed past it to 2654 while the files were still arriving, because `loaded` accumulates across retries while `total` stays fixed. `summarizeProgress` therefore reports a `progress_total` outside 0..100 as INDETERMINATE (percent `null`, status stays "downloading") instead of pinning a 100 that would sit on screen for the whole download and read as "finished but stuck". The route then drops frames that do not move the percent by a point or flip the phase — a single download emits hundreds of them.
- **Capture uses `AudioContext` + `ScriptProcessorNode`.** The node is deprecated in favour of `AudioWorklet`, but it is the only capture path every target browser ships (Safari included) without serving a separate worklet module. `MediaRecorder` is not an option: it emits Opus/WebM, which the worker cannot decode.
- **The worker handle is anchored on `globalThis`** for the same reason the database and terminal store are: `bun --hot` re-evaluates the module while the spawned worker (and the model it holds in memory) lives on, and a module-level binding would orphan the child with no handle left to kill it. It shuts down after 10 minutes idle, and `/reload-engine` recycles it alongside the other omp processes.
- **The WebSocket upgrade is origin-checked** with the same predicate the terminal uses (`server/lib/http/same-origin.ts`), because dictation triggers real work — a model download and a decode — and an upgrade carries no preflight to stop a cross-origin page from asking for it.

### Chat Transcript Store (`chat_sessions`)
- **The chamber's copy of a conversation is an OVERLAY, not a transcript.** For a session omp owns on disk the session JSONL is authoritative (`loadSessionMessages` → `mergeOmpAttachments`), and the DB row carries only what the JSONL cannot record: the **user turns** — the text as the user typed it, since omp delivers `@agent` as a task-tool delegation prompt and `/skill:a b` as `/skill:a`, plus the attachment metadata, since a text file is inlined into the prompt and its name/content/preview exist nowhere else — and the **notice rows** (a builtin command's output, for which omp writes no entry at all). Nothing else in the row is read: `merge-stored.ts` filters on `role === 'user'` and on a non-empty `notice`, and no code path reads an assistant row.
- **Only those rows are written.** `overlayRowsForOmpSession` (`src/server/lib/omp/session/merge-stored.ts`) narrows what the POST handler stores, gated in `src/server/routes/chat/session.ts` on `findSessionFileById` — **the session file's existence, never the id's shape**: a chamber-created `new-<ts>` session has no file, and there the DB is the only copy, so it stays whole, as does an omp uuid whose file is gone. Before this the client posted its entire rendered timeline on every `message_end` and the server stored it verbatim — measured on the author's install at **165.6 MB of 167.9 MB of mirrored assistant rows nothing consumes**, on top of re-writing a multi-megabyte array per stream segment with no body-size guard. Verified: narrowing changed the merged timeline of **0 of 260** stored sessions compared against their own files.
- **Nothing the narrowing drops is needed to place a row.** A stored raw turn that no JSONL user turn relates to — a `/usage` or `/compact` turn, for which omp writes no entry at all — is positioned by its own `startedAt` against the merged rows' clocks (`anchorIndexFor` in `merge-stored.ts`), never by scanning the stored array for a row the JSONL carries. That scan is what made the first version of this narrowing move those turns to the END of the timeline, after answers that came later: it resolved against the mirrored rows that are exactly what gets dropped. The scan survives only as the fallback for a legacy row with no clock to read. Verified on the author's install: of the sessions holding such turns, only the ones whose anchor the scan had been supplying changed order, and they changed to the time the turn was sent. Do not "fix" the missing assistant rows — their absence is the point.
- **`compactChatOverlayRows` applies the same rule to rows written before it existed**, called from the **server bootstrap right after the "listening" banner** (`src/server/index.ts`) and deliberately NOT from `getDb()`: the test suite and the CLI reach that in real mode, so a database handle must never be able to launch a rewrite of every mirrored conversation — **a `bun test` run did exactly that, compacting a live 172 MB database**. It has **no marker**, unlike `queue_fk_removed`: the guard is per-row ("does the filter actually shrink this row?"), so the pass is self-limiting — measured 762 ms for a 173 MB overlay on the first start, then one parse-and-skip of the remaining ~5 MB — whereas a marker would leave every row written by an older build uncompacted for good, and a live server keeps writing mirrors until it is restarted. Only a row whose session file exists is rewritten, so a chamber-created session stays whole. The rewrite makes the freed pages reusable; `VACUUM` on a stopped server is what returns them to the filesystem.
- **Two other writers sit deliberately outside the gate**: `src/shared/lib/chat/stream-service.ts` is the MOCK SSE path, where the DB genuinely is the transcript, and `src/server/routes/chat/root.ts`'s action is the pre-migration writer that no client calls (its loader's `?sessionId=` branch likewise has no caller).

### OMP Engine Settings Schema (generated)

- **`src/client/data/settings/omp-schema.json` is GENERATED, never hand-edited.** `bun run omp:schema` (`scripts/omp-schema.mjs`) imports `orderedSettings()` from the installed `@oh-my-pi/pi-coding-agent` and `SETTING_TABS`/`TAB_METADATA` from `pi-tui`, and writes the panel's tab/group/label/editor metadata from that. `bun run omp:schema:check` regenerates in memory and exits non-zero when the file is stale, so a stale schema is a CI failure rather than a shipped panel — that gate is the `schema` job in `.github/workflows/ci.yml`, deliberately separate from `gates` because the generator imports the INSTALLED package (this repo does not depend on `@oh-my-pi/pi-coding-agent`) and a cold Bun global install would otherwise sit in front of every other check. It was **documented here before it existed**: no workflow called the script until 2026-10-12, which is how the file drifted 9 rows behind omp 18.9.2 unnoticed (now 412 entries, `10 tabs / 550 settings`, 0 of the chamber's 435 merged keys rejected by `omp config list --json`). The JSON sat frozen from the Remix→Elysia migration (2026-09-18) until this existed: **157 live settings had no row at all** (every `title.*`, `tui.renderSvg`, `tui.autoGraph`, `task.completionProbe`, `skills.*`, `ida.*`, `searxng.*`, `gc.*`, `memories.*`, `compaction.v2RetainedMessageBudget`, `browser.tern`, `stream.serverUrl`, `telemetry.otlpExportEnabled`), and **12 rows the chamber still offered were rejected by `omp config get` with `Unknown setting:`** — `stt.modelName`, `providers.tts`, `tts.localModel`, `providers.webSearchOrder`, `irc.timeoutMs`, `providers.autoThinkingModel`, `providers.imageOrder`, `providers.memoryModel`, `providers.tinyModel`, `providers.unexpectedStopModel`, `providers.webSearchExclude`, `providers.webSearchGeminiModel` — an editor whose write was guaranteed to fail.
- **The generator reads omp's own source, not its bundle.** The published package ships `src/` beside `dist/`, and the definitions live in `src`; `dist/cli.js` is minified, so its `re({…})` calls only partially evaluate (the enum and `ui` shape survive, an expression-valued default does not). A setting with no `ui` block has no row in omp's own panel either, so it is deliberately not carried — and `schema-extras.ts` still supplies the chamber's documented extras, which never shadow an upstream entry (asserted by `schema.test.ts`).
- **`task.completionProbe` replaced `task.completionProbeMs`** in omp 18.5.0 (`0` → off, any period → on), so the old key is gone from the schema and offering it would write a key the binary rejects.

### Standby omp Processes (Reload OMP Engine, omp update)

- **A reload means DISPOSE, not re-read.** `recycleStandbyProcesses` (`src/server/lib/omp/session/standby.server.ts`) disposes the two pools that hold an omp process with **no session and no turn** — the shared utility children (`--no-session --no-lsp`, answering `get_available_models`, `get_login_providers`, `get_available_commands`) and the per-cwd prewarm entries (an idle session host waiting for the next send) — so the next command boots the binary currently installed. `/reload-plugins` is a different question and lives in `reload.server.ts`: it re-reads skill/plugin FILES inside a live process and would leave the OLD BINARY running, which is exactly the staleness this exists to fix.
- **Why it is needed at all: a running child is the build it was spawned from, for its whole life.** `omp update` replaces the launcher and the package on disk, but a utility child lives up to 5 minutes (`IDLE_KILL_MS`) and a prewarm waits for a send that may be an hour away — so the provider list, the model list and the composer's `/` popup keep answering from the previous version with nothing on screen to say so. Verified end to end against a real server: after a successful update the utility child's pid was gone and the next `/api/models` booted a new one, while an **already up-to-date** run left the same pid alive (`applyOmpUpdate` returns `updated: false` for the phrase `checkOmpUpdate` already matches — a success that must not bounce a warm pool).
- **Live sessions are deliberately untouched.** They may be mid-turn, and a `--resume` on their next command already boots the current binary. The button is therefore safe to press at any time, and the smoke run proves it: with a real session host and a utility child alive, `POST /api/omp/reload-engine` recycled the utility pool and left the session's pid running and its `get_state` answering.
- **The prewarm pool's recycle is claim-safe by construction.** An unclaimed entry owns no session and no turn, and `startNewRpcSession` claims an entry with a synchronous check-and-set — so an entry is either taken before the pass reads it or taken after the pass removed it, never both. `restartPrewarmedSessions` (`rpc/session-registry.ts`) marks each doomed entry claimed before deleting it, then awaits `destroyAndWait`; a wrapper still booting is torn down the same way the prewarm's own error path does.
- **A resumed session can come back under a DIFFERENT id, and the registry must answer for the one the CLIENT holds.** omp 18.10.0 forks a session marked moved away (`omp session moved`, or a `departed` `session-transfer` marker) instead of continuing it: the child answers a fresh `sessionId` and writes the fork to a fresh file under a fresh id — verified against a real child, which resumed a departed file into another directory. The registry is keyed by the id the caller holds (the URL's session id), so keying it on that alone MISSED on the very next message: the send re-resolved the ORIGINAL file and spawned again, and **two sends on one session file produced two children with two different ids**, each forking its own file — a chain of forks with a sidebar row each and nothing on screen to explain it (measured through both `startRpcSession` and the route-level lookup). `registerSpawnedSession` (`rpc/session-registration.ts`) therefore registers the wrapper under the reported id AND, when they differ, under the requested one, removing both on destroy so a dead child cannot answer for the requested id; the spawn path also emits `session-attached` for the requested id so a subscribed tab re-snapshots instead of holding the pre-spawn `running:false`. `realSessionId` reports the child's OWN id even on a registry hit (it reported the requested id, which is the alias, not the session). Pinned by `forked-resume.test.ts`, which drives the real spawn path against `test-support/fake-omp-fork.ts` — the only way the two ids can differ — and fails with 2 children if the alias is removed.
- **Caches built FROM a process or the binary are dropped in the same pass** (`invalidateModelsCaches`, `invalidateSkillCache`, `invalidateUsageCache`, `invalidateOmpCliCache`), because a recycled server behind a cached provider/model list makes the recycle look like it did nothing. The client half is `useReloadOmpEngine` (`src/client/hooks/settings/reload-engine.ts`), which also calls `invalidateComposerCache` + `notifyModelsUpdated` — the `/` popup holds its list for 5 minutes and would otherwise keep offering the old commands.
- **Two triggers, one pass.** `POST /api/omp/reload-engine` (route `src/server/routes/omp/reload-engine.ts`) is the settings sidebar's "Reload OMP Engine" button — previously a 1200 ms spinner with no request behind it — and `applyUpdate`'s omp branch fires the same recycle after a successful update, gated on `updated` so an already-current run does not bounce anything. Both coalesce onto one in-flight pass, and a failure in one pool never skips the other (each is caught and reported separately; `standby.server.test.ts` pins all four properties).
- **The toast carries a tone.** The settings modal's single toast slot now reports the reload's real outcome — `Reloaded omp engine — N utility, M prewarmed process(es) recycled.`, or the empty-pool wording when nothing was live (a normal state, not a failure: the next command spawns the current build either way) — and a failed request renders under an alert icon in `text-error` instead of a check mark. Verified in the browser on a live server: the click issued `POST /api/omp/reload-engine → 200`, the toast named `1 utility, 0 prewarmed`, and a forced 500 rendered `alert-circle text-error`.

### Updates from the Console (self-restart and the page reload)

- **An OMPChamber update from the console restarts the server that answered it, and the page then reloads ITSELF into the new build.** `POST /api/updates/apply` arms the detached restart and answers first (`RESTART_GRACE_MS`, 1.2 s — the margin that lets the `result` frame reach the browser), so the page is still served by the process whose files were just replaced. Reloading on the `result` frame would fetch the OLD bundle back; never reloading leaves the user on a stale page with a "restarting" toast and nothing else. `useUpdates` therefore reads `/api/health` BEFORE the run, waits for a process that answers with a different `pid`/`startedAt`, and only then reloads (`src/client/hooks/ui/updates/restart.ts`, `waitForServerRestart`).
- **Identity, never a timer, is what "the replacement is up" means.** A timer is wrong in both directions: too short reloads into the dying process, too long leaves the user on a stale page after the new one is already serving. `/api/health` reports the serving process's `pid` and `startedAt`, so a different pair IS the replacement. A failed probe is EXPECTED (the old server is exiting and the port is briefly unbound) and is never read as an answer; with no baseline — the pre-run health read failed — the fallback is a young `uptime` (`REPLACEMENT_MAX_UPTIME_S`), which the update's own multi-minute duration makes safe. The ceiling is 30 s (`RESTART_WAIT_TIMEOUT_MS`), and on a timeout the result comes back with `restarting: false` and a sentence telling the user to reload by hand rather than a promise the console cannot keep. Verified against a live server: the real `/api/health` payload carries both fields, a re-read of the same process is not a replacement, and a changed pid is.
- **`restarting` is a FIELD on the result, not something the client sniffs out of the message.** `UpdateApplyResult.restarting` is set from the plan `scheduleSelfRestart` returned, and the sentence is folded in by the same helper (`withRestartPlan`, `src/server/lib/lifecycle/restart.ts`) so the flag and the wording cannot drift apart. Absent on every other outcome — an "already up to date" success, a `manual` install, a failure — and `false` when a restart was refused (an instance the CLI does not own), where the appended sentence is the only place the user learns why.
- **The message was wrong, and this is the fix.** It read `… — the console reconnects on its own`, which described the realtime socket and not the page: the console stayed on the old bundle until the user reloaded by hand. It now says `Restarting on port <port> to apply it — this page reloads on its own.`, pinned by `selfRestartMessage`'s own test.
- **The dialog stays in its "working" state across the wait, and the install log is APPENDED to rather than replaced.** A run that flashed back to idle before the navigation would read as finished; `apply` therefore leaves `applying` set when it ends by navigating, and appends `Update installed — waiting for the server to restart on this port…` to the log it already has, because a failed restart has to be read against the output that ran. An abort (the panel going away with the run) still returns `null` — the same answer the other abort path gives — so no caller toasts into a torn-down view.
- **The omp target never enters this path.** `applyUpdate`'s omp branch recycles the standby pools and restarts nothing, so the client only reads the baseline and only waits for `target === 'ompchamber'`. `restarting` is never set for it.
- **What is not covered by a test:** the real self-restart followed by a browser reload. Exercising it means killing a live CLI-managed instance mid-session, so the wiring is pinned by the pieces (`withRestartPlan` sets the flag and the sentence together; the hook's mounts drive the wait, the reload and the timeout through an injected clock and a stubbed `window.location`; the health payload is smoke-tested against a live server) and the assembled path is not.

### Plugins (Settings → Plugins)

- **The panel is a view over omp's own plugin state, and every mutation is `omp plugin …`.** omp owns four files — `<dataRoot>/marketplaces.json`, `<scope>/plugins/installed_plugins.json`, `<scope>/plugins/omp-plugins.lock.json` and the shared `cache/{marketplaces,plugins}/` — and re-implementing a write whose format omp also reads at runtime would be a second source of truth for state omp reports. The chamber's own job is the two things the CLI cannot answer: WHICH features and settings a plugin declares (its manifest) and WHERE its runtime state lives (the lockfile of its scope). `src/server/lib/omp/config/{plugin-registry,plugins,plugin-cli,plugin-actions}.ts`, route `src/server/routes/settings/plugins.ts`, UI `src/client/components/settings/categories/plugin-settings/`.
- **A plugin id is not unique — the selection is `(id, scope)`.** The same `name@marketplace` installs into BOTH registries at once, and omp lists the user copy with `shadowedBy: "project"` while the project copy shadows it; the two differ in version, enablement, install path and shadowing. Selecting by id made them one row, so the pane could render the user copy and act on the project copy. `pluginSelectionKey` (`plugin-settings/selection.ts`) is the key the rows, the selection and every action name.
- **`cwd` is the scope selector, not a filter.** `omp plugin` reads the PROJECT registry of the directory it runs in, so a workspace scope lists that workspace's project installs beside the user ones and the user scope runs in `$HOME` — which omp's own anchor walk deliberately stops before, because `~/.omp` is the USER config dir. A project install issued from a user-scope cwd would land in the wrong registry. `getProjectPluginsDir` (`core/paths.ts`) is a faithful port of omp's `resolveOrDefaultProjectRegistryPath` (nearest `.omp/`, else nearest `.git`, else the cwd).
- **The user plugin root is the DATA root, not `~/.omp`.** `getPluginsDir`/`getMarketplacesRegistryPath` follow omp's `DirResolver` `data` category, so on an XDG install they are `$XDG_DATA_HOME/omp/…`. Reading `~/.omp/plugins` unconditionally reports an empty plugin list there — the same trap `agentDataSubdir` documents for sessions. The condition is omp's own: the XDG app root must already EXIST.
- **A marketplace entry carries no manifest, and its runtime state is keyed by the PACKAGE NAME.** `omp plugin list --json` reports `{ id, scope, entries }` for a marketplace install, with no features and no settings; both live in the cached install directory, and its lockfile state sits under `@local/manifest-plugin`, never `manifest-plugin@local-mkt`. Reading the id against the lockfile reports "no features" for every marketplace plugin (measured), which is why `readPluginPackageName` exists.
- **Features are saved as ONE selection through `--set`, not as `--enable`/`--disable`.** The add/remove pair cannot express "no optional features", so a plugin that started with features on could never be returned to omp's defaults. `selected === null` means omp is applying the features marked `default`, and that is what the draft starts from. **A project-scoped install's features are read-only**, because omp's `features` command resolves the plugin from its USER plugin root (`getPluginsNodeModules()`) and writes the USER lockfile: on a project-shadowed pair it reports success while the ACTIVE project selection is untouched (verified on 18.4.4 — `features --set alpha` wrote `~/.omp/plugins/omp-plugins.lock.json` and left the project lock's `enabledFeatures` null). `featuresEditable`/`featuresNote` carry that to the pane, which renders the ladder without its save controls, and the route refuses the same request so a stale client cannot silently write the shadowed copy.
- **A plugin's SETTINGS live in the user lockfile in both scopes.** `omp plugin config set/delete` go through `PluginManager`'s single runtime config (`getPluginsLockfile()`) and have no `--scope` at all — the runtime reads them back the same way (`getPluginSettings(name, cwd)` merges that global map with the project overrides file). Reading the scope's own lockfile reports "no settings" for every project-scoped install (verified: a `config set` issued from a workspace cwd wrote the user lock and left the project lock's `settings` empty), so `listPlugins` reads values from the user lock in both scopes while `enable`/`disable` state still comes from the scope's own lock.
- **Features and settings are addressed by PACKAGE NAME, not by plugin id.** omp's `features` and `config` commands resolve the plugin from its `node_modules` entry, so a marketplace plugin needs `@local/manifest-plugin` — a bare catalog name exits 1 with `Plugin "<name>" not found` (measured). `PluginItem.packageName` carries it; `name` stays the catalog name the user sees.
- **A secret setting's value never leaves the server.** `omp-plugins.lock.json` stores plugin settings in plaintext and the pane is a browser surface, so `pluginSettingState` reports a `secret: true` key as present (`secretSet`) and omits its value — the pane can replace or clear it, never show it, which is also omp's own answer (`config list` masks it). The input starts EMPTY rather than prefilled with a placeholder a careless Save would write back literally.
- **`--json` is not honoured by every `omp plugin` verb.** install, `marketplace add/remove/update` and upgrade ignore it and answer on stdout as text, reporting failure on stderr with exit code 1 — so `runPluginCli` returns both streams and `pluginCliError` prefers stderr. A caller reading stdout alone reports every failure as an empty success. omp's own sentence is surfaced verbatim ("Plugin \"nope\" not found in marketplace …", "is installed in both user and project scope"), because it names the missing marketplace or the ambiguous scope, neither of which the chamber could reconstruct.
- **Every mutation answers with the whole panel payload, and the server re-reads omp's registries.** Installing moves the catalog's `installed` flag and can add a lockfile entry; uninstalling can drop a cache directory another scope referenced; an upgrade changes the version a second scope sees. Adopting the response verbatim is what keeps one source of truth.
- **A scope flag rides along only when it can matter.** The uninstall/enable actions send `--scope` for a marketplace plugin (whose id can exist in both registries), and nothing for a `package` plugin (npm/git/link), which omp resolves by name against the active project root first and the user root second — the flag is only honoured on the marketplace path. Features and settings carry the panel's scope instead, because that is the cwd those two commands resolve in.
- **`reloadLiveSessions()` runs after every accepted mutation.** omp discovers plugin capabilities once per process, so a newly installed plugin's skills and commands are invisible to a running session until `/reload-plugins` — the same refresh the Skills panel performs after a SKILL.md write.
- **MOCK mode answers a deterministic four-plugin dataset** (`src/client/data/settings/plugin.ts`) covering every render shape: a marketplace plugin, a project install with an update available, a shadowed disabled user copy, and a plugin with no `omp` manifest at all (conventional `skills/` content only).

### Skills (Settings → Skills, composer `/` popup)

- **Skill discovery delegates to omp, it is not re-implemented here.** `discoverSkills` (`src/server/lib/omp/config/skills.ts`) runs `omp skill list <dir> --json` — omp's own resolver, so it reports exactly what a session in that directory would load. A hand-rolled scan of `~/.omp/agent/skills` + `<cwd>/.omp/skills` is what it replaced, and it silently disagreed with the agent in both directions: it listed 6 skills where omp loaded 9, and it could not see `~/.agents/skills` (where `bunx skills add --agent universal` installs), `.claude`, `.codex`, `.github`, `.opencode`, plugin packages or the skillshare store. It also re-derived frontmatter rules it could not keep in sync — a missing `description` makes omp skip a SKILL.md entirely, and `hide`/`disableModelInvocation` keeps a skill runnable but out of the model's `<skills>` listing. One CLI call (~0.4 s, no session, no model) answers all of it, cached 5 s per directory (`invalidateSkillCache` after every write).
- **A skill is only editable where the chamber is the owner.** `managedSkillRoots` is `~/.omp/agent/skills` plus `<workspace>/.omp/skills`, and `managed` is true only for an `native:*` skill sitting directly under one of them. Everything else — a registry package in `~/.agents/skills`, a Claude plugin — renders read-only and its `DELETE` is refused by name, because the chamber is not the tool that put it there. The detail pane shows the source path instead of an editor it must not save through.
- **Create/save/delete are real SKILL.md files** (`writeSkillFile` / `deleteSkillDir`), not rows in an `app_settings` list. The old "custom skill" wrote only to the chamber's own store and omp never read it: the panel offered a save that changed nothing, and deleting it removed a record while the skill (or nothing at all) stayed as it was. A rename or a scope move (`user` ⇄ `project`) removes the previous directory, which is why `writeSkillFile` takes `previousDir` rather than a name — resolving the old path from the new scope silently left the source copy behind (verified: a user→project move left both).
- **The catalog install is scoped to the row that was clicked.** `installCatalogSkill` passes `--skill <name>`; without it `bunx skills add <repo>` installs every skill in the repository (measured: 20 directories for one "Install"). Uninstall runs the CLI's `skills remove` counterpart, so it clears what the install created instead of only the chamber's record.
- **omp discovers skills once per process, so a write is followed by a reload — and the reload reaches EVERY live process, including a busy one.** A SKILL.md that lands while a session runs is invisible to that session until it restarts (measured: `get_available_commands` kept reporting 8 entries after a ninth was written). `reloadLiveSessions` (`src/server/lib/omp/session/reload.server.ts`) sends `/reload-plugins` — omp's only refresh, reachable as a prompt because the builtin has a text-mode `handle` — and it broadcasts to the per-session children AND the pooled utility processes (which answer the composer's `/` popup). **The `isBusy()` skip is gone, and its premise was wrong.** The old guard reasoned that a prompt dispatched into a running turn is a queue insert; measured on omp 18.4.3, it is not. A `/reload-plugins` sent mid-turn is answered from omp's command loop in 16-40 ms with the turn still streaming — and with a blocking approval dialog parked (`get_state`, `get_available_commands` and the reload all answered within 16 ms; the RPC loop is independent of the turn waiting on the dialog) — after which the turn completes normally and the new skill is listed immediately. A PLAIN mid-turn prompt is neither queued nor injected: it is dropped outright (one `agent_start` for two prompts). The guard was actively harmful, because the common case IS a busy session: `create-skill` writes its SKILL.md with a tool WHILE the invoking chat streams, so the write landed during a run and the refresh was skipped — leaving the new skill invisible until the user found the manual `⟳` button (verified against a live chamber: absent from `get_available_commands` after the turn ended, present the moment a session reloaded). Verified on 18.4.3 it answers `agentInvoked: false` (no model turn) and leaves the session file byte-identical, and a burst of triggers coalesces onto one in-flight pass. Verified end to end: creating a skill through the API took a live session 9 → 10 skill entries with no restart, deleting it took the session back to 9, and a hand-written skill mid-turn was listed while the turn still streamed.
- **A SKILL.md written by anything OTHER than the chamber is watched for, not polled.** The root set is ONE table, `src/server/lib/omp/config/discovery-roots.ts`, shared by `locateCommandFile` and the watcher — they were written separately and the watcher's copy was short by every root but the omp-native pair, so a skill added to `.claude/skills`, `.codex/skills`, `.opencode/skills`, `.agents/skills` or `.github/skills` in a live session was never noticed. The set is measured against omp 18.4.3, not assumed: the project roots are those six, the user roots are `~/.omp/agent/skills` and `~/.agents/skills`, and `~/.claude/skills`, `~/.codex/skills`, `~/.config/opencode/skills` and `~/.opencode/skills` were verified NOT read — do not add a root on the strength of its command counterpart (omp does read `~/.claude/commands` and friends). Skills and commands share the project roots; `.github` differs by layout (`.github/prompts/*.prompt.md` for commands) and `~/.agents/skills` is skills-only. `src/server/lib/omp/config/roots-watch.server.ts` watches those roots for the user scope, for each registered workspace, and for each LIVE session — a session can run outside every registered workspace (a folder opened straight from the sidebar, the app root) and omp still resolves project skills from that cwd (verified: without this, a SKILL.md written into such a session's own `.omp/skills` was never picked up). It refreshes every live child 250 ms after a change (one reload per burst). The alternative — re-running `omp skill list` on a timer per workspace — spawns a process per tick to answer a question that only changes when a file does. Three rules make it work. **A root that does not exist is never created** (the chamber must not write `.omp/skills` into a user's repository just to watch it): the nearest existing ancestor is watched instead, and the change that creates the real root triggers a re-sync, which re-attaches it RECURSIVELY. **omp also reads project skills from every ANCESTOR of the cwd, up to the enclosing git repository** — measured on 18.4.3: from `/tmp/walk/a/b/c` with no `.git` anywhere it reported the skills of all four levels, an empty `.git` at `a/b` cut it to that level and below, a `.git` FILE (worktree/submodule) stops it the same way, and `$HOME` is NOT a boundary (the walk crossed it, and `~/.omp/skills` was never read). `skillRoots()` therefore appends `<ancestor>/.omp/skills` for each level, `managed: false` so the chamber's write/delete paths stay scoped to the cwd's own root. Without this, a skill written into the ancestor a session actually resolves was invisible (verified: a session in `/tmp/anc/sub` saw `a-parent` from `/tmp/anc/.omp/skills` but never `a-late` added later). Only a genuine root is watched recursively, and a BRIDGE is watched not at all in the sense that matters: the nearest existing ancestor of a missing root can be `~/.omp/agent` or a whole workspace, so a bridge firing only re-syncs — it never reports a change itself. Reporting those as reloads produced 170 broadcasts in 20 s on an idle machine and, worse, MASKED the ancestor gap: the skill appeared to be picked up by the watcher when it was only being re-read by a broadcast an unrelated file had triggered. Two further rules close timing holes a filesystem watch cannot: a root attached for the first time owes one delayed pass (the OS registers a recursive watch ASYNCHRONOUSLY, so a file written in the instant after a session spawn raises no event — verified: the skill was missed, and picked up once the attach settled), and a pending reload is never downgraded by a bridge pass in the same debounce window (the reload a root attach scheduled was overwritten by an unrelated directory's traffic before it ran). And the reconcile is idempotent and serialized, because `bun --hot` re-runs the server entry: a duplicated watcher would double every broadcast. The watcher set itself is anchored on `globalThis` for the reason the database is — a `bun --hot` module re-evaluation would otherwise orphan the previous `fs.watch` handles with no way to close them (confirmed: with the binding anchored in the module, a hand write stopped reaching the session after a hot reload; anchored on `globalThis`, it survived). It is reconciled at boot and on every workspace create/delete (`POST /api/folders`, `.../delete`), so a workspace added mid-session is watched without a restart. `fs.watch({recursive:true})` costs no descriptors on Bun/macOS (measured with the repo's own `countOpenFileDescriptors`: zero delta for three recursive watchers over 42 entries).
- **Both panels and the composer are scoped to one omp scope at a time.** `resolveDiscoveryScope` (`src/server/lib/omp/config/scope.ts`) turns the request into a cwd: `?scope=user` asks the agent dir (`~/.omp/agent`), `?root=<workspace>` asks that workspace, and neither keeps the historical app-root meaning (the composer's fallback for a session with no workspace folder, where omp itself spawns in the server's cwd). `resolveRoot` still gates a client-supplied `?root=` (app root, a path under it, or an exact registered `project_path`), and an unresolvable root falls back to the USER scope rather than to a directory the caller never asked about. The cwd is the whole point: omp resolves project skills and commands from the process cwd — a child in `$HOME` reported 7 skill entries and one `file` command, the same child in this repo reported 9 and its own `.omp/commands` — which is also why the utility RPC is pooled **per cwd** (`runUtilityCommand(command, timeout, cwd)`), so a home-scoped pool entry serves the registry queries while a workspace read gets its own. The composer's cache is keyed `command::<root>` and `invalidateComposerCache` matches that prefix, so `available_commands_update` still clears every workspace's copy.
- **A write lands in the scope the panel is showing, and a new draft inherits it.** The save carries the scope (`scope`/`root` on the POST body) and the draft's own `location` picks the root, so a create made while a workspace is selected writes `<workspace>/.omp/skills`; the panel passes `defaultLocation` for that, because a new draft used to open as `user` and a project skill created from the workspace scope was written to `~/.omp/agent/skills` — it then vanished from the list being viewed. A project write with no workspace is refused server-side rather than landing somewhere the user did not pick, and only the omp-native roots are writable at all (`managedSkillRoots`, `locateCommandFile`'s `managed` flag): everything else renders read-only, keeps its Save hidden, and its `DELETE` is refused by name.
- **The commands panel reads omp's own list, and finds the file behind a name itself.** `get_available_commands` reports the name, description and hint but never a path, so `withCommandFile` → `locateCommandFile` looks the name up in every root omp reads (`.omp/commands`, `.claude`, `.codex`, `.agents`, `.opencode`, `.github/prompts` — the last with its `.prompt.md` suffix); a name with no file is a builtin, a `skill:<name>` entry or an extension command and is `isBuiltIn: true, managed: false`. Only `<workspace>/.omp/commands` and `~/.omp/agent/commands` are `managed`. A name present in both roots resolves to the PROJECT file, which is what omp runs (measured), so the lookup checks the workspace first and a delete can only reach the two managed roots.
- **The panels' project picker lists real workspace folders** (`useWorkspaceRoots` → `/api/settings/projects`), not the hardcoded `ompchamber`/`workspace-edge` placeholders it used to offer: those sent a root the server could not resolve, so choosing one changed nothing. Each option's value is the folder's `project_path`, which is what the API takes as `?root=`, and `rootFor` resolves an option by **id OR value** — the dropdown emits the value through `onChange`, so an id-only lookup silently answered the user scope for every workspace while the trigger still printed the folder's name. Both the Skills and the Commands panel share the hook, the trigger-label resolver and the scope query.

### Side Questions (BTW panel)
- `/btw [question]` typed in the main composer **replaces the composer with the side-question panel** (`src/client/components/workspace/btw-panel/`, swapped in by `ComposerDock`, opened by the `omp:btw` window event; the mode state machine is `src/client/hooks/chat/btw/mode.ts`); bare `/btw` opens it on the current history. **The open flag is deliberately NOT persisted** (`useState`, not `useSessionState`): a panel that reopened itself on load left the user with no chat composer and a field they never asked for, and a `/btw` typed into that field became a real question to the model. The panel is a mode the user enters, so every load starts in the chat — while the drafts and the selected topic do persist (`chat.btwAsk` / `chat.btwFollowUp` / `chat.btwTopicId`), so leaving and re-entering loses nothing. The panel is **two cards**: the panel card — the ask card as its **header** (the field that starts a new topic, plus `⟳` start over, `⌄` topic history, `⧉` promote into chat, `✕` leave), the running turn's `GeneratingIndicator`, and the topic's turns as its body — and the composer below it for follow-ups. The ask field must stay a header rather than a free-standing card above the composer: as its own card it read as a second composer and users typed follow-ups into it. The answer card is capped at `520px` (`ANSWERS_MAX_HEIGHT_PX`) with its own scrollbar, and the header stays visible while the body scrolls.
- **The panel renders the CHAT's timeline, not a btw-specific one.** A turn's `messages` are `ChatMessageData` — the same shape the chat timeline folds — so `BtwMessages` builds one row list (each question as a user row, then that turn's conversation) and hands it to the chat's own `MessageList`. A tool the side child runs therefore draws the same card it would in the chat, and thinking / usage / errors come along; the two renderers cannot drift. On the server the conversation is accumulated by `trackTurnMessage` (`src/server/lib/btw/lifecycle.server.ts`) through the shared `toChatMessage` mapper, with the SAME by-id upsert the chat stream's `onMessageUpdate` performs (omp emits one frame per segment carrying that segment's full accumulated content). `BtwTurn.answer` stays as the plain-text summary (history labels, promotion titles) and is the fallback for a turn stored before the conversation column existed.
- **The run footer's token counts come from `message_end`, not the streaming frames.** omp's `message_update` frames report `usage` zeros; only the completed message carries the real counts, so `handleFrame` upserts `message_end` too — as a COMPLETED row (`toChatMessage(record, false)`, the same flag the chat stream passes), because mapping it as streaming left `thinking.isGenerating` true on every stored turn: each reload reopened the accordion and pulsed it over a finished answer. Dropping that branch is silent: the footer renders without its `… tok` segment. The row's `thinkingLevel` comes from the chat's transcript (`loadSessionThinkingSelector`), not from `get_state` — that reports the level the child RESOLVED, and storing it would pin an `auto` chat to a concrete effort on every later spawn.
- **`BtwState.live` carries the running turn**, not just frames: a client attaching mid-turn (a reload, a second tab) would otherwise get a snapshot whose running turn has no persisted messages yet and would show an empty answer while the child streams on. The `btw_message` / `btw_activity` frames drive the live upsert; the state is the seed. The child echoes the `<btw>`-wrapped prompt it received, and the panel drops that user echo (it already renders the user's own question).
- **The indicator's verb is the side child's own.** `btw_activity` carries it, derived server-side from that child's frames (`describeAssistantPhase` / `describeToolActivity`) — the chat's verb describes a different process and must never be borrowed. `PHASE_VERBS.sideQuestion` ("Answering side question") is the honest fallback before the child reports anything, since the side stream cannot tell reasoning from prose.
- **The child ECHOES the prompt it received**, and that echo is the `<btw>` wrapper the panel itself built, so it is filtered out of the rendered rows — the panel draws the user's own question instead. A legacy turn's plain `answer` is rendered only when it has no stored conversation.
- **The panel has NO model / thinking / access pickers.** A side question runs on the CHAT's model and thinking selector, and every `ask` re-reads both from the parent transcript (`loadSessionModel` / `loadSessionThinkingSelector`) — a chat that switched model or level is mirrored by the next question, and a live child is re-targeted over RPC before the prompt (`BtwRuntime.retarget`). That is omp's own shape: its side turn reads `request.session.model` at run time, so the TUI panel has no pickers either, and the chamber's per-topic `set_model` / `set_thinking_level` / `set_access_mode` actions are gone. `showModel`/`showThinking`/`showAccess` on `ComposerToolbar` (all off for `BtwForm`) is what keeps the composer's own selectors out of the side-question card without forking `ChatInput`.
- **omp's `/btw` is TUI-only**, so the chamber implements it. Its registry entry in `omp 18.2.6` has `handleTui` and no text-mode `handle`, and RPC dispatch only runs entries with `handle` — sending `/btw …` as a prompt would reach the model as literal text. Client interception lives in `src/client/hooks/chat/timeline/actions.ts`; server behaviour in `src/server/lib/btw/`. Because `get_available_commands` cannot advertise it, the composer's `/` popup gets its entry from the chamber-owned pool in `src/shared/lib/chat/composer/client.ts` (`CHAMBER_COMMANDS`, byte-identical to omp's own description and `[question]` hint) — never from omp's list.
- **Context arrives by transcript reuse, never by re-prompting it as text.** A topic owns a private copy of the parent session file (`<db dir>/btw/<sessionId>/<topicId>/session.jsonl`) taken on its first question; the side child is spawned as `omp --mode rpc-ui --resume <that copy> --no-title --no-tools` (`src/server/lib/btw/child.server.ts` builds the argv). **This is the one parity gap that cannot be closed**: omp's side turn runs IN PROCESS over the live `this.messages` (including a message still streaming), while the chamber resumes a file snapshot — there is no RPC for an ephemeral turn, so a side question here sees the parent as of the snapshot plus its own turns, not the parent's in-flight work. The parent's prompt-cache prefix survives, the parent file is never written (verified: byte-identical after many questions), and a follow-up after the child was reclaimed resumes the copy and still sees every earlier turn.
- **The side child runs WITHOUT tools (`--no-tools`), which is what omp's `/btw` effectively is.** omp's TUI does not pass `--no-tools` (that is a CLI flag for a whole session) — it runs the side turn through `runEphemeralTurn`, which keeps the tool catalog attached only to hold the prompt cache warm, tells the model in a `<system-reminder>` that tools are NOT available, and DISCARDS any tool call the model emits anyway (`agent-session.ts` filters `toolCall` blocks out of the final message). `--no-tools` reaches the same end state from the CLI: no catalog, so nothing can execute. Verified against omp 18.3.2 on a resumed transcript that already carries 384 tool results: `toolNames` empty, zero tool calls emitted, zero executions, the turn completed normally. There is therefore no approval gate to park on and no dialog path: `PendingUiDialogs`, `BtwState.dialogs`, `ExtensionDialog` in the panel, and the `dialog_response` action are all gone. `withoutToolCalls` in `lifecycle.server.ts` drops a `toolCall` block that arrives anyway (a hallucinated call against the catalog omp would still attach), mirroring omp's own filter.
- **One side question in flight per session** — no implicit queue, no implicit cancel; a second question is refused (`btw_busy`, 409) exactly like the TUI. A new question is its own topic; only the panel's composer continues the active one.
- **State and streaming**: `btw_topics`/`btw_turns` in the chamber DB (schema in `src/server/lib/btw/schema.server.ts`; `thinking_level`/`approval_mode` are added by the additive column migration there, because `CREATE TABLE IF NOT EXISTS` leaves an existing table alone — `approval_mode` is retained for rows written while a side child ran with tools and nothing writes it now, and `thinking_level` holds the chat's SELECTOR, `auto` included). A turn's status vocabulary is omp's own (`running`/`complete`/`cancelled`/`error`/`interrupted`; a row written as `failed` is migrated by `ensureBtwSchema`), and the stored `answer` summary is bounded the way omp bounds its side replies (`src/server/lib/btw/reply.ts`). The server is the source of truth and every frame is a snapshot (`btw_state`, carrying the live turn) or a delta (`btw_message` / `btw_activity`). Commands: `POST /api/btw/:sessionId` (`ask`/`abort`/`promote`/`delete`), stream: `GET /api/btw/:sessionId/events` + WS `/:sessionId/ws`. Unlike the agent stream this one is NOT observer-only: history must be readable while no omp child is running, so reading the state also repairs `running` rows whose runtime is gone.
- **Promote** materializes the topic as a session of the chat's own: the copy is written beside the parent under a fresh id, carrying `parentSession` and a title slot padded to exactly the `SESSION_TITLE_SLOT_BYTES - 1` bytes omp rewrites in place, with the `<btw>` boilerplate unwrapped so the promoted chat shows the question the user actually asked. It is refused while a turn runs, while the CHAT is streaming, for a topic with follow-ups (`btw_multi_turn` — omp's branch carries one question/answer pair and refuses multi-turn history), and once the parent transcript has moved past the snapshot's leaf (omp's own `/btw` branch guard). **That leaf is written where the snapshot is taken** (`BtwRuntime.openWorkspace` → `setBtwTopicLeaf`); it had lost its writer in the tools change, so `readBtwTopicLeaf` always returned null and the guard could never fire — rows created before the fix keep a null leaf and are not guarded, since their snapshot entry cannot be reconstructed.

### Scheduled Tasks (sidebar Calendar button)

- **The chamber owns the clock, because omp has none.** `src/server/lib/schedule/runtime.server.ts` runs ONE process-wide `setInterval` (20 s, anchored on `globalThis` like the database handle and the terminal registry — a `bun --hot` reload must not leave a second interval running). Each tick claims every task due at `now` and dispatches it. The Calendar button in both sidebars used to open a mock dialog: a textarea with no state, a "Schedule Task" button that only closed the window, and decorative kind/interval controls.
- **A fire is a normal prompt through the normal spawn path.** `runScheduledTask` opens a child with `startNewRpcSession` (fresh conversation) or `startRpcSession` when the task names a `sessionId`, sends the task's model snapshot (`set_model` / `set_thinking_level`), then `prompt` — exactly what a queued follow-up delivery sends. Nothing bypasses the registry, so the approval mode, the idle reaper and the stream-status row all behave as they do for a user-initiated prompt. Verified end to end on a real server: a `once` task and an `every 1m` task each produced a real omp session whose transcript reads `user: <prompt>` / `ai: <answer>`.
- **A claim is a WRITE, and it advances the schedule in the same transaction** (`claimDueTasks`). That is what makes two ticks — or two chamber instances on the shared database — safe: the second sees the row already moved past its own `now` and takes nothing. A `once` task is disabled by its own claim (`next_run_at = NULL, enabled = 0`) rather than by the dispatcher, so a one-shot whose dispatch failed cannot resurrect on the next tick or on a restart.
- **`next_run_at` is stored, not derived.** A `once` task's fire time IS its spec, a paused task has none, and a spent one-shot is a third state — none of which a re-parse could distinguish. The task list renders them differently on purpose: `Paused` versus `Ran once — no next run` versus a real `Next <time>`.
- **Editing a schedule or resuming a task RECOMPUTES the clock from now** (`updateScheduledTask`). Keeping the pending value would fire once on the cadence the user just replaced (a `1h` → `1d` edit), and re-enabling a paused interval task would fire immediately for every interval it spent paused.
- **The run record is the only place a failure exists.** A task is claimed before it is dispatched, so a spawn that throws can never be retried by a later tick; `finishScheduledRun` writes `error` + the message and the modal renders it under the row. A manual "Run now" is recorded with `countRun: false`, so testing a task does not inflate its fire count, and it deliberately does NOT move `next_run_at` — the user is asking "does this work", not asking to skip the scheduled fire.
- **One grammar, shared by the form and the runtime** (`src/shared/lib/schedule/parse.ts`). `every` takes `30s`/`5m`/`1h30m`/`2 days`; `cron` takes 5 fields with `*`, `N`, `a-b`, `a,b,c`, star-slash-n and `a-b/n`. Two rules are load-bearing and unit-tested: **when BOTH day-of-month and day-of-week are restricted the day matches if EITHER does** (Vixie cron — `0 0 13 * 5` fires on the 13th AND every Friday, not only Friday the 13th), and `nextCronOccurrence` walks DAYS with whole-month skips (a `0 0 29 2 *` is 1461 day-steps away; a minute walk would be 2.1 M iterations and an impossible date such as `0 0 30 2 *` reports "never" rather than hanging). The next fire is strictly AFTER the cursor, so a task that fires at exactly its own `lastRunAt` advances instead of re-firing forever. The 1-minute floor is enforced because the tick is 20 s.
- **The modal validates with the same parser it previews with** (`TaskForm`), so the form cannot accept a spec the route would refuse — and the route validates again (`createScheduledTask`/`updateScheduledTask`), because a stale client is always possible. Verified in the browser: `30s` renders "The shortest interval is 1 minute.", a red border and a disabled submit; a valid `2h` renders "Next run in 2h · <local time>".
- **The model snapshot is resolved SERVER-side when the request carries none** (`resolveDefaultTaskModel`): the composer's persisted pick plus the persisted access mode, or `null` when nothing is stored (omp's own default then applies). A scheduled run happens with nobody watching, so the snapshot has to exist, and the value the user last chose in the composer is the only honest default. An edit never rewrites it.
- **The cwd is resolved at WRITE time and stored on the row** (`resolveTaskCwd` → `project_path` else the folder name). A folder deleted after the task was created must still let it fire in the directory it was created for; storing only the folder id would leave the runtime falling back to the server's own cwd, which is how a scheduled job silently runs in the wrong project. No folder chosen means the server's cwd, and the form says so ("Server default directory").
- **State lives in `scheduled_tasks` / `scheduled_task_runs`** (`src/server/lib/schedule/schema.server.ts`, called from `initSchema` beside the BTW tables). Runs are capped at `RUN_HISTORY_LIMIT` (50) per task, pruned after each close, or an interval task would grow the table without bound. API: `GET/POST/PATCH/DELETE /api/schedule` (`?id=` for the single-task verbs, `?id=…&run=now` to fire immediately) and `GET /api/schedule/:taskId/runs`.
- **The toolbar badge is a derived read, and it follows the write.** `useScheduledTaskCount` reads the schedule realtime topic — the same one the modal reads, so the badge cannot disagree with the list and a mutation reaches it with no event and no poll. Verified live in the browser with no reload: `4 armed` → pause a row → `3 armed`, and the count survived a full server restart (the row is the state).
- **The runtime's dependencies are INJECTED** (`ScheduleDeps`), never mocked through `mock.module` in tests. `mock.module` swaps a registry entry for the whole `bun test` run: mocking the RPC manager in `runtime.server.test.ts` broke six unrelated suites with "Export named … not found" (measured), which is why `runScheduledTask(task, { deps })` takes them and `runtime.server.test.ts` drives the real dispatch logic with a fake session handle.

### Terminal Panel (real PTY)
- The right-panel terminal is a **real shell on a pseudo-terminal**, not a command runner: `Bun.Terminal` + `Bun.spawn`, one shell per terminal id, N attached viewers. `src/server/lib/terminal/runtime.server.ts` owns the registry, `history.ts` the bounded scrollback, `shell.ts` the launch argv, and `src/server/routes/terminal/ws.ts` the socket. `GET /api/terminal/sessions` lists live shells; `GET /api/terminal/run` only supplies header context.
- **Transport is one WebSocket per terminal** (`/api/terminal/:terminalId/ws`): text frames are JSON control (`attach` / `resize` / `close`), binary frames are raw PTY bytes both ways. The frame contract lives in `src/shared/lib/workspace/terminal/protocol.ts` and is shared by both ends — change it there, never per side. Client pieces: `src/client/hooks/workspace/terminal/{index,socket}.ts` and `terminal-panel/RealtimeXtermView.tsx`.
- **Three invariants the runtime depends on** (each was verified against Bun 1.4.2 and each fails silently when broken): spawn with `detached: true` (otherwise the child sits in the server's process group — no job control, and a group signal would kill the chamber); launch POSIX shells through the `shellLaunch` shim that re-opens the PTY as the controlling terminal (`setsid` drops it, and a shell without one disables job control entirely); and send `SIGWINCH` after `term.resize()` (Bun updates the winsize but never signals the child, so a TUI would not repaint).
- **`SIGWINCH` must be debounced** (`resizeTerminalDebounced`). Every accepted grid change signals the shell, and a shell answers by redrawing its prompt — so a resize burst that reaches the PTY one-per-frame prints the prompt dozens of times (measured: 10 signals in one second for a single panel drag). A quiet period coalesces the burst to its trailing size. For the same reason the client suppresses `term.onResize` reports while it is laying out replayed scrollback: that transient grid is the recorded history's, not the panel's.
- Terminal ids are per chamber session (`terminal.id` in session UI state) so a page reload reattaches to the same shell and the server replays its scrollback. The replay is written at the size it was drawn for (`replayCols`/`replayRows`) and only then fitted — re-wrapping history at another width leaves fragments the shell's redraw never clears.
- A terminal has **one grid**, so with several viewers (two tabs, a phone and a desktop) the most recent `attach`/`resize` owns `cols`/`rows` and the others see output wrapped for it. That is inherent to sharing a PTY; there is no per-viewer size to fall back to.
- Do not reintroduce a per-command `sh -c` route or a client-side line editor: the shell owns line editing, history, completion and signals, and `xterm` must receive raw bytes (`onData` + `onBinary` out, `Uint8Array` in) so a character split across PTY reads stays intact.
- **A failed terminal spawn reports the descriptor table, not just the shim.** `createSession`'s error is `spawn: Failed to start <shell>: <bun message>`, and the message now goes through `describeSpawnFailure` (`lib/lifecycle/fd-pressure.ts`). Bun's own text for an exhausted table is `EBADF: bad file descriptor, posix_spawn '/bin/sh'` — naming the `shellLaunch` shim and never the cause — so the helper appends the real one (the server is out of descriptors, with the count and the fix) **only** when `fcntl(F_GETFD)` can see the pressure; a genuine bad-descriptor failure still reads as itself. The omp child's spawn (`omp/rpc/process.ts`) is wrapped the same way, because it fails for the same reason at the same moment.
- **One shell per terminal id, even when two attaches race.** Creation awaits (cwd resolution, the shell probe, the capacity `ps`), so two `attach` frames for the same new id both used to pass the `sessions.get` check and both spawned: the map kept whichever landed last, and the other PTY plus its detached shell had no record — the reaper could never see it and the cap never counted it (measured on the real runtime: two concurrent attaches left two shells for one record). `openTerminal` shares one in-flight promise per id instead, and that map lives in `store.ts` beside the records, because a reload that dropped it would reopen the same race.
- **A touch device gets a key bar, and its bytes come from xterm's own key table** (`terminal-panel/KeyBar.tsx` + `src/shared/lib/workspace/terminal/keys.ts`, shown when `useTouchDevice()` reports a soft keyboard — `(pointer: coarse)`, or touch points plus `(hover: none)`, subscribed rather than read once so docking a keyboard hides the bar). A phone's soft keyboard has no Ctrl, Alt, arrows, Esc or `|`, so those are buttons; every sequence is what `@xterm/xterm/src/common/input/Keyboard.ts` sends for the same physical key, because a bar key that invented its own encoding works in bash and breaks in vim. Three of its rules are load-bearing: a modifier is a CSI **parameter** (`ESC [ 1 ; 5 A`), never an ESC prefix; DECCKM (set by vim/less) swaps arrows and Home/End to the SS3 spelling and a modifier **beats** it — read at press time from `term.modes` through the view handle, since the encoding cannot be decided at mount; and Ctrl is a **latch**, not a fold on literal keys, so a tapped `|` stays a pipe while `^C` is its own button. **A fourth rule is that xterm's own default is not always what the shell binds: Home and End send the `terminfo` spelling, not xterm's CSI one.** The PTY child runs with `TERM=xterm-256color`, and `infocmp xterm-256color` declares `khome`/`kend` as SS3 (`\EOH`/`\EOF`) — while xterm.js emits `ESC[H`/`ESC[F` whenever DECCKM is off, which is exactly the state a shell prompt sits in. The mismatch is silent from this side and total on the other: zsh's ZLE rings the bell and leaves the cursor where it was. Verified A/B/A against the chamber's own zsh — `ESC[H` → bell, `ESC[OH` → accepted, `ESC[H` → bell again — and the fix is a `terminfo` field on the `CsiSpec` that takes precedence over the DECCKM/default branches (`keys.test.ts` pins it). The arrows need no such field: their CSI and SS3 forms are both accepted, so DECCKM stays their only variable. The latch also folds into the soft keyboard's own letters (`applyModifiers` in `handleInput`) — that is the only way a phone reaches Ctrl+R or Alt+B — and only a **single** typed character consumes it, or a paste would spend it silently. Verified end to end against a live PTY: `^C` took the server's `busy` from true to false mid-`sleep 30`, and `printf '\033[?1h'` switched a subsequent Up arrow from `ESC [ A` to `ESC O A`. The bar **wraps** instead of scrolling (`overflow-x-auto no-scrollbar` hides keys with nothing on screen to say so — the diff toolbar's lesson) and is its own `@container`, so a 320px desktop panel gets three rows of keys and a wide one gets one. The control row carries the three Ctrl keys a terminal actually needs without a physical keyboard — `^C` (interrupt), `^D` (end of input), `^L` (clear screen, which is also the only way to clear a scrollback too wide to scroll on a phone) — and Shift+Tab, which no soft keyboard can produce.
- **The bar has two layers, and Cmd is an ACTION rather than a key.** A layer key swaps the control/cursor row for the symbol row in place — `TERMINAL_SYMBOLS` carries the `$ * ? & < >` set plus `|`, `~`, backslash, backtick and the brackets/quotes, because reaching `$` on an iOS keyboard is a mode switch per character and `~`/`|`/backslash/backtick have no layer at all. **There is deliberately no Cmd button**: xterm discards `metaKey` outright (`if (ev.metaKey) break;` in its cursor-key branches), so a button for it would send nothing. In a terminal Cmd+C/Cmd+V mean copy and paste, and that is what the bar offers instead — `Copy selection` reports "Nothing selected" rather than flashing success over an untouched clipboard, and `Paste` goes through `term.paste()` so a bracketed-paste shell receives its `\x1b[200~…\x1b[201~` markers (verified: the bytes on the wire carry them) rather than a line-by-line write. A denied clipboard read is surfaced as "Clipboard unavailable" with the button in its error tone, and no bytes are sent. Both actions share the row with the latches, and both `disabled` with the shell.
- **The panel lifts by its OWN overlap with the keyboard, never by the keyboard's height** (`useKeyboardInset` → `paddingBottom` on the panel root). Neither mobile browser shrinks the layout viewport for the soft keyboard by default, so a bottom-anchored bar would sit behind the very keys the user is typing on. The lift is `panelBottom − (visualViewport.offsetTop + visualViewport.height)`, and **that form is the whole point**: `innerHeight − visualViewport.height` measures the keyboard and then applies it to a panel that may not reach the screen's bottom edge — a drawer with `env(safe-area-inset-bottom)` padding, a container a `dvh` wrapper already shrank for the keyboard — which lifts by the keyboard's height *plus* a gap the panel never had. That was the too-far margin. Deriving from the panel's own edge yields exactly zero in every one of those cases. Two guards keep it honest: `MIN_KEYBOARD_INSET_PX` (80) so a collapsing URL bar is not mistaken for a keyboard, and a `≤ 0` visible-bottom fail-safe to no-lift. The measurement is deferred one `requestAnimationFrame`, because `visualViewport.resize` fires BEFORE the container reflows — reading in the handler sees the old full height and doubles the lift — and a `ResizeObserver` on the panel's **border** box catches a container that shrinks with no viewport event at all, without a feedback loop (our own padding moves the content box only). Verified with a stubbed `visualViewport` on a 390×844 phone: keyboard over a full-height panel → bar 844 → 508px (exactly the keyboard's top edge) and grid refit (`resize 58x13`, back to `58x30`); a panel that already cleared the keyboard → 0 lift; a 40px overlap under the floor → ignored.
- **The terminal font stack must keep its glyph fallbacks** (`XTERM_GLYPH_FALLBACKS` in `src/client/data/theme/terminal.ts`). Shell prompts are drawn with private-use symbols — powerline separators, devicons, Material Design icons — that no coding webfont contains: `@fontsource/fira-code`'s latin subset maps 226 codepoints, none above U+FFFF. Without a Nerd Font face in the chain the browser paints a hollow tofu box for every prompt segment. Note the two ways a local face can be referenced, because only one is reliable in Chrome: a **family name in the font stack works**, while `@font-face { src: local("…") }` matches the *full* or *PostScript* name only — `local("FiraCode Nerd Font Mono")` fails where `local("FiraCode Nerd Font Mono Reg")` and `local("FiraCodeNFM-Reg")` succeed.
- **The chamber bundles the symbols face, and it is LAST in the stack** (`NERD_SYMBOLS_FAMILY`, `src/shared/lib/fonts/nerd-symbols.css`). Naming installed families is not enough: the glyphs appeared on the machine that had one and were tofu on every other device — a phone, a second laptop. The vendored subset of Nerd Fonts' `SymbolsNerdFontMono` (MIT, 1.1 MB, built by `scripts/nerd-symbols-font.mjs`) closes that gap without taking the choice away, because a face is only reached when no earlier family supplies the glyph. Two properties make that safe and both are asserted in `nerd-symbols.test.ts`: the face must stay LAST (moved ahead of the installed families it would win on every machine and make every desktop download 1.1 MB for nothing), and its `unicode-range` must cover only private-use — which is what makes the download conditional. Verified: with a local Nerd Font present, laying out a PUA glyph issued **zero** font requests and the face stayed `unloaded`; with no local family, the face is fetched and all 43 codepoints of the user's own starship prompt render.
- **xterm must be told to re-rasterize when that face lands late** (`refreshAtlasWhenNerdFaceLoads`, `terminal-panel/mount.ts`). xterm has no `document.fonts` listener: it rasterizes a glyph the first time it draws it and keeps the result in a texture atlas, so a PUA glyph written before the face arrived stays a tofu box for the life of the buffer. Measured: the glyph was rasterized exactly once, at 53 ms, while the face landed at 4.1 s — and never again. A `loadingdone` naming our family is the exact signal that this machine had no Nerd Font of its own (a device that has one never fetches the face), so the listener calls `clearTextureAtlas()`, which is documented to force a redraw of all glyphs. It is a no-op on a machine with an installed Nerd Font, which is why it went unnoticed.

### Tray Icon and Start at Login (`serve --tray` / `--startup`)

- **The tray is a CHILD OF THE SERVER, and the process tree is the whole registration.** `serve --tray` passes `--tray` into the server's argv (`lifecycle/argv-flags.ts`), and `src/server/lib/tray/runtime.server.ts` `ensureTray` spawns the platform host as a plain `Bun.spawn` child. There is no pid file, no `status`/`stop` for the icon and nothing to keep in sync: the host exits when the server exits, and the menu's Quit signals the server. This replaced a `ompchamber tray` command that spawned the host detached and had to record a pid, answer `tray status`/`tray stop` and keep a record consistent — all of which the process tree now does for free.
- **The host watches its own parent, because a server can die without saying goodbye.** `getppid` is polled on a timer (`watchParent:` in `host/darwin.js`, `process.ppid` in `host/linux.js`, the parent process in `host/win32.ps1`); when the server exits the host is reparented to launchd/init, the change is seen, and the icon goes away. Verified end to end: a fake server spawned the shipped host, exited, and the host terminated itself. That is what makes a SIGKILLed or crashed server leave no orphan icon.
- **Quit signals the SERVER, so the icon and the console end together.** `kill(getppid(), SIGTERM)` on macOS (via `ObjC.bindFunction`), `process.kill(process.ppid, 'SIGTERM')` on Linux, `taskkill /PID <parent> /T` on Windows. Verified against a fake server: the Quit row produced a SIGTERM at the parent. A tray that outlived its server would be an icon for a port nobody serves.
- **Every host is a dumb renderer, and the SERVER is the brain.** Each host draws its own menu (the rows are data: Open Console, Open Logs, Start/Disable Start at Login, Quit) and every path it needs comes from the config document the server wrote. Nothing in a host probes liveness or reads a record: there is no liveness question left to ask once the host IS the server's child.
- **The login entry runs `serve --foreground`, and that is the second load-bearing rule.** launchd reaps a job's whole process tree when the job's program exits, so an entry that ran a detached `serve` (which returns as soon as the health check passes) produced no server at all — verified: `launchctl print` showed `state = not running` while the log recorded a successful start. In the foreground the CLI is the long-lived job, the server is its child, and the tray is the server's child: one tree, nothing exiting early. `buildLoginEntryArgv` (`tray/entry.ts`) also pins `--prod` (a login entry has no shell to export `NODE_ENV`) and carries `--tray` only when the registering invocation asked for it, so `--startup` alone is a supported shape.
- **`--no-startup` is a REGISTRATION change and returns before the port guard.** Asking to stop starting at login must work whether or not something already serves the port. Measured with the handler below the guard: `serve --no-startup` on a busy port failed with "already served" and left the entry in place.
- **The host script is COPIED into the data directory before it runs** (`hosts.ts` `installHostScript` → `<data>/tray/host/`, refreshed on every start). A login entry outlives the install that wrote it — an `ompchamber update` replaces the package tree, a checkout moves — so the path baked into the plist, the `.desktop` file or the Run key has to be one only the data directory owns.
- **`packageDir()`, never `import.meta.dir`, resolves the shipped host.** The production bundle flattens every server module into `dist/client/index.js`, so `import.meta.dir` is `dist/client` and the host sources are not beside it. Measured: the bundled server logged `icon shown` and then `osascript: …/darwin.js: No such file or directory`. The same rule is why `entry.ts` canonicalizes the CLI path with `realpathSync` — the CLI resolves its own root as `<dir>/../..`, and its path helper does not collapse a `..`, so a generated plist carried `<pkg>/src/cli/../../src/cli/ompchamber.js`.
- **`--no-startup` lives in `NEGATED_LONG`, not `BOOLEAN_LONG`, and that is the whole reason it works.** `BOOLEAN_LONG` stores a flag under its own spelling (`options['no-startup']`), while the command reads `options.startup` — so the flag parsed and the command never saw it. `src/cli/lib/args.test.js` pins the mapping, so a new hyphenated flag has to choose a side. `startup` is tri-state (`null` unmentioned, `true` install, `false` remove), because "install" and "remove" must be told apart from "not mentioned".
- **Linux is the one platform that can lack a tray client, and the server says so and keeps serving.** `yad` and `zenity` are absent from a default install on many distributions, and no icon can be drawn without one — so `ensureTray` returns `{started:false, reason}` and the entry logs `tray: not shown — …` with the package to install. macOS and Windows always have a tray API. `ensureTray` never throws: a tray is a convenience over the console, never a prerequisite for it.
- **`ensureTray` is idempotent through a `globalThis` slot**, for the reason the database handle is anchored there: `bun --hot` re-runs the server entry, and without the slot the reload would spawn a second icon beside the one the first generation still holds.
- **`host/linux.js` runs `main()` only when it IS the program** (`Bun.argv[1]?.endsWith('linux.js')`). Without the guard, importing the module to assert its payload builders started a tray from the importing process's argv — which is exactly how the first test run failed.
- **`buildTrayConfig` resolves every path a host needs, per PORT** (`<data>/tray/<port>.config.json`, mode 0600, rewritten on each start): the bun binary, the CLI entry, the icon, the log file, the URL and its scheme, and whether a login entry exists (so the menu can label its row without a subprocess). The scheme comes from the listener rather than the flag alone — a `--tls` server answers nothing on HTTP, so a wrong scheme would make "Open Console" open a URL that cannot connect.
- State lives in `<data>/tray/`: `<port>.config.json` (what the host reads) and `host/` (the extracted scripts). `MOCK` is irrelevant here — a tray watches a server, not a dataset.

### Right-Panel Repo Scope (Files / Search / Git / Terminal / Wiki)
- The five right-panel views share one repo picker (`file-explorer/GitRepoDropdown.tsx` is presentational; the panel owns the data) and one scope hook, `src/client/hooks/workspace/repo-scope/`. A repo is a path **relative to the active workspace root** (`projects/jns6_5/token` only names a directory under `~/JatisMobile/Workspace`), so both the choice and the discovered list are meaningless without the root they belong to.
- **All five views share ONE selection slot, `workspace.activeRepo`** (`REPO_SCOPE_STATE_KEY`). They describe the same working tree, so a repo picked in the Files tree has to move the search scope, the Source Control view and a terminal's cwd with it — that is also what makes the drop-down feel like one setting rather than five. `useRepoScope(rootPath)` takes no key for this reason: a per-panel key is not an option the API offers, so the views cannot drift back into disagreeing about which repository is on screen. `useRepoList(rootPath, active)` stays as it was (one shared discovery store per root).
- **A session that picked before the views shared a slot keeps its repo.** The retired per-panel keys are adopted once, in the order `git.activeRepo` → `files.activeRepo` → `search.activeRepo` → `terminal.activeRepo` (git first: that pick is the one the root-level fallback and the Source Control indicator were built around), and only a value whose recorded root matches the current workspace is adopted — the shared slot is per session, so consuming it with a value for another workspace would burn the one chance to migrate and leave the panel on the root. All four keys are then cleared (`clearSessionKey`), so the store holds the selection in exactly one place.
- **Every repo value is stored with its root, never bare.** `useRepoScope` persists `{ root, repo }` per session and reports `'.'` when the pick is not for the current root; the discovery store (`repo-scope/store.ts`) keys its snapshot by root. Bare values are what leaked: a workspace switch left the picker listing the previous workspace's repos and showing one of them as the selection, while every request named a path that did not exist under the new root. Storing the pairing invalidates by construction, so no reset effect has to be ordered against the per-session state restore — and a session returned to inside the same workspace keeps its repo.
- **Repo discovery is one shared store, not a fetch per panel.** `repo-scope/store.ts` subscribes to the `repos:<root>` realtime topic (the server discovers nested repos in the background and republishes the topic the moment its walk finishes), so the five views share one subscription per root instead of five, and cannot disagree. It is injected with `fetch` (only a rescan goes over HTTP), and `store.test.ts` drives it through a real socket: a new root never reports the old root's list, one subscription serves every listener of the same root, a snapshot is adopted, a republish reaches the listener, and a rescan goes out over HTTP.
- **`GET /api/fs/git` does NOT echo the repo back.** `repos` / `reposPending` / `activeRepo` travel only on the `?reposOnly=1` branch, keyed to the root they were discovered for. The status response used to echo `activeRepo`, and the git panel wrote that echo into its stored pick — so a repo the user never chose was adopted under whichever workspace was active when the response arrived. Resolve the fallback (first discovered repo when the root is not itself a repo) client-side in `resolveRepoForPanel` instead. Only git resolves it; Files/Search/Terminal keep `'.'` as the root itself, because browsing a workspace that is a folder of nested repos is legitimate.
- **Everything read for a scope is tagged with it and dropped when the scope moves.** The file listing carries its `root\0repo` (`Listing.scope`) and renders empty until the new root's read lands — its children cache and expansion set are keyed by paths relative to the listed root, so `src/` in one workspace would otherwise rehydrate into `src/` in the next. Search results carry their scope through `useSearchStream`, and the git panel gates `fetcher.data` on the scope the payload was requested for, so a switch never shows the old branch, changes or branch list under the new header. `useGitStatus` applies the same rule inside the hook — its state is tagged with the tree it was read from and a superseded read is dropped, so the "uncommitted changes" dot cannot describe the repository the user just left, and the state is thrown away when the scope changes because **the same scope string can be a revisit** (root → repo → root), where the earlier visit's changes would otherwise reappear.
- **A surface that FOLLOWS a panel's pick reads it shared, not from its own copy.** The Source Control dot in the activity bar and the phone's tab bar are the same indicator on two layouts, and they describe the repo the git panel is on: `useResolvedRepo(rootPath, active)` — the shared pick, the same list, the same `resolveRepoForPanel` fallback — passed to `useGitStatus` instead of the previous hard-coded `'.'` (which reported the workspace root's changes, usually nothing, under a repo whose tree was dirty; measured: `projects/jns6_5/personalschedulertrigger` with 14 changes showed no dot while selected). `useSessionState` hands every caller a private copy, so the pick is read through `useSharedSessionState` (`src/client/hooks/workspace/session-state/index.ts`) instead: the store notifies per `(session, key)` on `setSessionKey`, on a blob arriving, on a migrate and on a delete (`subscribeSessionKey`, `src/shared/lib/workspace/session-state/store.ts`), and the follower re-reads — a private copy left it on the previous repo until something unrelated re-mounted it. Verified live in both layouts: picking a clean repo in the panel's picker turned the dot off (and the dot's own read switched to `repo=projects/jns6_6/…`) with no reload, and picking the 14-change repo turned it back on.
- **The panels refresh PER TOOL CALL, not only at the run boundary.** `tool_execution_end` (`frame-fold.ts`) now emits `workspace-dirty` and calls `publishSidebarStructure()`, and a terminal `agent_end` calls the latter too (the final answer appends after the last tool). The old turn-boundary-only shape left a long run's git/files panels AND the sidebar blind for minutes: the sidebar's `updated_at` — its `LATEST_SESSION` ordering and the row's time-ago label — is a transcript-scan product that only re-runs on `sidebar-structure`, and `sessions-watch` deliberately ignores transcript appends (`change`; only `rename` is structural). Cost is bounded by existing machinery, not new: `schedulePublish` coalesces 120 ms per topic and dedupes identical payloads (a 3-call burst → 1 delta; a publish whose resolve lands inside the 4 s `SIDEBAR_DATA_TTL_MS` with an unchanged scan publishes nothing), only SUBSCRIBED topics are resolved, and `invalidateOmpSidebarData`-then-rescan over a warm per-file mtime cache is ~9 ms against 1211 ms cold. The session-data topics (`todos`, `telemetry`, `queue`) stay turn-boundary-only on purpose — their resolvers parse the whole transcript. Verified server-level with a temp agent dir: append → `tool_execution_end` fold → delta; append → `agent_end` fold → second delta with the newer `updated_at`; identical scan → zero deltas.

### Source Control — merge, conflicts and branch management (the `git` view)

- **A conflicted file is a THIRD kind of change, and reading its porcelain pair like a clean one is the bug that shipped.** The two letters of `UU`/`AA`/`DD`/`AU`/`UA`/`DU`/`UD` are the two SIDES of a conflict, not an index/worktree pair. `parsePorcelainZ` derived `staged` from `status[0] !== ' '`, so every conflicted file was reported STAGED — and because `ChangesList` splits on the same columns, a `UU` path satisfied BOTH filters and rendered twice (under "Staged Changes" and under "Changes"), while `getGitStatusInfo` fell through to the untracked branch and labelled `UU`/`UA`/`UD` **"Untracked"**. `isUnmergedCode` (`src/shared/lib/fs/git-unmerged.ts`) is the one predicate every surface tests; the status list, the tree roll-up and the staged-count all exclude unmerged pairs, and the file gets its own **Conflicts** section with its own count. `git-status.test.ts` used to PIN the wrong labels ("unmerged porcelain pairs carry no dedicated branch") — that test was deleted, not re-pinned.
- **An operation in progress is a first-class READ (`readGitState`, `src/server/lib/fs/git-state.ts`), and its state lives in FILES in the git dir, not in an exit code.** One `git rev-parse --absolute-git-dir` (absolute, resolves from a subdirectory and for a linked worktree) plus a stat of `MERGE_HEAD`/`rebase-merge`/`rebase-apply`/`CHERRY_PICK_HEAD`/`REVERT_HEAD`. `git rev-parse --git-path <name>` is NOT usable: it takes a single name (five names give one path then `fatal: ambiguous argument 'rebase-merge'`) and returns a path relative to the cwd. **`fs.existsSync`, not `Bun.file().exists()`** — measured, `rebase-merge` is a DIRECTORY and `Bun.file(<dir>).exists()` answers false for it, which reported a rebase as the `stash-pop` fallthrough and offered `reset --merge HEAD` instead of `rebase --abort`. The state rides the existing `git:<root>\0<repo>` realtime topic (it is part of `readGitStatus`), so a merge started by a tool call reaches the panel with no second read path.
- **`stash-pop` is a distinct operation because a conflicting `git stash pop` leaves NO operation file.** Measured: `UU f` with no `MERGE_HEAD`/`rebase-merge`/`CHERRY_PICK_HEAD`, so every `--abort` verb exits 128 with its own fatal. Its abort is `git reset --merge HEAD` (verified: clears the conflict and KEEPS the stash entry, so the pop can be retried), and it has **no Continue** — resolving its files leaves the changes in the working tree with no sequencer to conclude, so the bar hides the button rather than offering one whose only outcome is a refusal (`continueArgsFor` returns `null` for it and the route says "Nothing to conclude").
- **Continue is PER OPERATION, and `git commit --no-edit` is only right for a merge.** Measured on a real rebase conflict: resolving the file and running `git commit --no-edit` makes the commit and leaves the rebase RUNNING (`rebase-merge` still present, `git status` reading "interactive rebase in progress"), so the operation bar would never clear. `continueArgsFor` maps merge → `commit --no-edit`, rebase/rebase-apply → `rebase --continue`, cherry-pick → `cherry-pick --continue`, revert → `revert --continue`. `runGit` sets `GIT_EDITOR=true` on every spawn for the same reason it sets `GIT_TERMINAL_PROMPT=0`: measured, `--continue` with no editor fails ("Terminal is dumb, but EDITOR unset") and with a real `GIT_EDITOR=vim` inherited it BLOCKS on vim until the timeout kills it.
- **`--ours`/`--theirs` are INVERTED during a rebase, so the resolve buttons are labelled from the file's own conflict markers.** Measured on the same two commits: a merge conflict's `--ours` yields the branch you are on while a rebase conflict's `--ours` yields the branch being rebased ONTO — a button that says "ours" and runs `--ours` silently takes the other side in half the conflict states. `parseConflictMarkers` reads the `<<<<<<<`/`>>>>>>>` labels off the working file (via `GET /api/fs/git?conflictMarkers=1&file=…`, one read when the row's menu opens — NOT part of the status payload, which republishes on every tool call), and the buttons read `take HEAD` / `take feature/payments`. A failed read falls back to the words `ours`/`theirs`; the actions still work.
- **`revertPath` REFUSES a conflicted path (`src/server/lib/fs/git-revert.ts`).** The three-step discard (`reset` → `checkout` → `clean`) succeeds on a `UU` path while doing something the user did not ask for: measured, it threw the conflicted content away, restored the pre-merge version, and LEFT `MERGE_HEAD` in place — `git status` afterwards read "All conflicts fixed but you are still merging". A trash icon that silently ends a conflict by picking one side, and leaves the operation open, is worse than no trash icon.
- **Merge is merged BY NAME, not by SHA.** `git merge <sha>` writes `Merge commit '<sha>'`; `git merge <branch>` writes `Merge branch '<name>'` (measured, both). The commit modal's `merge_commit` still takes a hash (a legitimate need) but gained a `--` separator and a hash-shape guard — measured, `git merge --abort` ran when the "hash" was `--abort`. Every hash operand is guarded (`hashFor`), every client path is `resolveRepoPath`-checked, and a branch name is validated with `git check-ref-format --branch`.
- **Branch rename: `git branch -m` does NOT move the upstream.** Measured: after renaming `feature` → `feat2` the config still reads `branch.feat2.merge = refs/heads/feature`, and a plain `git push` then REFUSES ("The upstream branch of your current branch does not match…"). The remote half is therefore `push -u <remote> <new>` (which re-points the upstream as it publishes — verified) + `push <remote> --delete <old>` + `fetch --prune` (without the prune the stale `origin/<old>` survives and the dropdown keeps offering it). It is a checkbox, OFF by default, and the dialog names the three commands. A collision is git's own refusal, including a case-only rename (`fatal: a branch named 'Main' already exists`) — and `-M` does NOT help that case either, so the dialog must not offer "force" as a way around it.
- **Branch delete is `-d` first, `-D` only on an explicit second step.** `git branch -d` refuses an unmerged branch (`error: the branch 'feat' is not fully merged` — verified) and that refusal IS the safety net. The flag travels as `force=1` and is read as exactly that: the confirm path once dropped it, so ticking the box deleted with `-d` anyway — a bug the e2e spec now pins.
- **The branch list is ONE `for-each-ref`, and its hardest case is the EMPTY track.** `%(upstream:track)` measured in every form: `[ahead 1]`, `[behind 3]`, `[ahead 1, behind 3]`, `[gone]`, and EMPTY for a branch with no upstream — including a branch several commits ahead of everything, so an empty track renders `unpublished` and never "in sync". `%(ahead-behind:HEAD)` is deliberately unused: it answers "ahead of the CURRENT branch", not "ahead of the upstream" (measured: a branch two commits ahead of `main` reads `[2 0]` while its track is empty). Cost on 501 branches: 0.01s → 0.03s. A detached HEAD is dropped from the branch list (it reported the literal string `HEAD` as a checkoutable branch) and the toolbar shows it as a sha.
- **The amend checkbox PRE-FILLS the draft with the message it is about to rewrite.** `git commit --amend` REPLACES the message, so an empty box asks the user to retype what is already in the repository — and the common amend is a tweak to the previous subject (a typo, a missing scope, a ticket id). Ticking Amend loads HEAD's message via `?headMessage=1` (`readHeadCommitMessage`, `lib/fs/git-log.ts` — `%B`, so a multi-line message and a merge commit's own message round-trip whole) and seeds the draft. The read is ON DEMAND, never part of the status payload: that read travels on the realtime `git:` topic and is republished on every tool call, so a payload carrying it would pay one `git log` per tool call for a checkbox nobody ticked. Three rules keep the seeding from becoming its own bug, and all three live in `useCommitBox` (`client/hooks/workspace/commit-box.ts`, unit-tested): a draft the user already typed is NEVER overwritten (the check runs against the LIVE draft when the answer lands, not the one seen when the box was ticked, so typing during the fetch wins); the read's answer is discarded if the box was un-ticked while it was in flight; and un-ticking clears the seeded text ONLY — `seededRef` records what the hook wrote, so a draft the user edited survives, which is what makes "ganti total" work. The seeded text is ordinary editable text, not a placeholder, and the box says where it came from (`previous message loaded`, hidden on the first edit) so an auto-filled draft does not read as a stale one. A repository whose HEAD is unborn answers `null` and nothing is seeded — the placeholder stays, exactly as before.
- **The stash section is pinned to the panel's FLOOR, below the change list, and its body rises.** The panel is a flex column and `GitChangesList` is the `flex-1` member, so the stash (a `flex-shrink-0` sibling, rendered last) stays on screen while the list above it scrolls — and opening it SHRINKS that list instead of pushing the section down a scroller the reader would have to chase. Measured in the browser: expanded, the list went 567px → 478px while the section's bottom stayed at the panel's own bottom edge; a section merely placed after the list in DOM order but INSIDE the scroller sat 394px above the floor. The e2e spec pins both halves (below the commit box, and within 48px of the panel's floor), because either alone is satisfied by the wrong layout.
- **The reveal is `grid-template-rows: 0fr → 1fr` (`.section-reveal`, `src/client/tailwind.css`), not `max-height`.** The wrapper is the grid, the open state is a `data-expanded` attribute, and the CHILD carries `min-height: 0` + `overflow: hidden` — without either the track cannot collapse below the content's min-content size and the section renders at full height with no animation. **The clamp child must carry no padding**: `overflow: hidden` clips the content box, never the padding box, so a `pb-2` on it left an 8px sliver of empty body under a collapsed section (measured in the browser; the padding moved one level in). The body stays MOUNTED in both states — that is what the reveal animates — so it is marked `inert` while collapsed, or the hidden message field stays tabbable and its controls are announced (verified: focus is refused on the input, the checkbox and a row's Drop button while collapsed, and the toggle itself stays focusable; all three take focus once open). `prefers-reduced-motion` turns off the transition and nothing else — the layout is identical either way (verified: 0 → 88.5px in one frame).
- **The disclosure glyph is the change list's own (`▾` open, `▸` closed, in a `w-3` track, `aria-hidden`), not a Lucide chevron — and it must carry `font-mono`.** Three sections in this panel already taught the reader that mark, and a fourth drawn as an SVG icon in a different size and colour reads as a different control. **The glyph is a TEXT character, so its face decides its size, and that was the whole bug:** the change list renders inside a `font-mono` container (12px, `ui-monospace`) while the stash header inherited the app's sans stack, so the IDENTICAL codepoint at the IDENTICAL `font-size` came out a quarter smaller — measured ink **4.65×4.65px mono against 3.49×3.56px sans** (`getComputedStyle` reports `12px` in both cases, which is why comparing font-size proves nothing). The fix is one `font-mono` on the glyph span; verified in the live panel: all three headers now measure `x=1074, box 12×16, ui-monospace, 12px, weight 600, ink 4.65`. `git-panel.e2e.ts` compares the stash glyph's computed font and ink against the **live `Changes` header's own glyph**, and that spec's fixture now leaves a real working-tree change behind — on a clean tree the `Changes` header does not render at all, so the reference silently resolved to the stash glyph itself and the assertion passed with `font-mono` removed (measured).
- **The whole row toggles, and the toggle is a full-width `<button>` — not a `<div onClick>` like the change list's headers.** It used to wrap the LABEL alone, which left a measured **189px dead strip** in the middle of a 334px row: clicking "the section row" did nothing and only the words `Stash` responded. The button now carries the row's own padding (`pl-3 pr-2`) plus `flex-1`, spanning everything up to `Save` (1062→1328px on a 334px panel; a click at five positions across that span toggles every time, and a real trusted CDP click confirms it). A `<button>` rather than a clickable div because the row needs `aria-expanded`/`aria-controls` and a Tab stop; `Save` is a SIBLING button (a button inside a button is invalid HTML and its click is swallowed), so no propagation guard is needed — verified: Save stashes without toggling the section. The e2e spec clicks the row's EMPTY MIDDLE, not the label, because a label click passes with the bug still in place; it also asserts the click point is inside the toggle's own box (1146 vs `<1015.6` with the old markup).
- The open flag persists per session (`git.stashExpanded`, beside the change list's own section flags), restored through the real session-state provider (verified: reload comes back expanded). The list is still fetched ONLY when the section is opened, so a section nobody opened costs nothing, and `Save` stays available while collapsed because it needs no list.
- **The panel's modals live in `PanelModals.tsx` and the action dispatch in `git-actions*.ts`.** The route (`routes/fs/git.ts`) was at the repo's 350-line ceiling with twenty inline branches and this feature added a dozen more; the handlers are now two domain tables (`git-actions-worktree.ts`, `git-actions-branch.ts`) merged into one `GIT_ACTIONS` dispatch. Every modal built on the shared `common/Modal.tsx` shell now carries `role="dialog"` + `aria-modal` — the hand-rolled git-panel shells already did, and a screen reader cannot announce a panel it does not know is a dialog.
- **`tests/e2e/specs/git-panel.e2e.ts` is the regression net for all of it** (10 specs, `real` mode, a real repository per test via `seedWorkingRepo`). The bugs above are invisible to a unit test — they are a real DOM, a real git state and a real click. It pins: a conflicted file listed once under Conflicts with the bar present, resolve-through-the-UI concluding a merge with a real merge commit, abort restoring the tree, a rebase concluded by `rebase --continue`, a stash pop offering no Continue, discard refused, rename in place, `-d` refused then `-D` via the checkbox, stash drop confirmed, the stash section's pinned placement, and amend rewriting rather than appending. **A fixture's git calls that FAIL by design must use `gitAllowFail`** (`execFileSync` throws on a non-zero exit, and a conflicting merge/rebase/`stash pop` exits 1 with the state left behind — the whole point).

### Search Panel (right-panel Search view)

- **The result list is VIRTUALIZED, and the reason is measurable.** A search for a common word matches tens of thousands of lines: `const` in this repo produced 19,376 hits, and mounting them all cost **385,706 DOM nodes and 34 s of blocked main thread for one five-step scroll** (headless Chromium, 4x CPU throttle, mobile viewport) — the profile put **70% of it inside Shiki's JS regex engine** (`findNextMatchSync`), because every mounted row re-tokenized its line on each re-render. Only the rows a viewport can show are mounted now: **44 rows, 1,290 nodes, 0 ms blocked for the same scroll**.
- **The layout is arithmetic in `src/shared/lib/fs/search-list.ts`, not measurement at render time.** Rows are a flat sequence (`group` headers then their hits), each row's height is the measured text box PLUS its gap, and `searchWindow` binary-searches the prefix sums for the mounted range. Gaps live in the heights rather than in `space-y-*` because a windowed list has a different set of siblings on every scroll — a CSS margin would be drawn between whichever two rows happened to be adjacent. **The wrapper carries the layout's height and the measurement targets the TEXT box inside it** (`[data-search-header] > div`, `[data-search-hit] > button`): measuring the wrapper would feed the gap back into the value that defines it, and rendering natural heights instead of the layout's would leave every row a gap short so a jump landed on the wrong hit — verified by comparing 1,779 rendered rows across 41 scroll positions against the captured SSE payload: **0 mismatches, total height exact to the pixel**.
- **`scrollTop` is measured in the spacer's coordinates**, so the container's padding is carried by the top spacer and the total is the last row's offset plus its height. `overflow-anchor: none` is set because the browser's own scroll anchoring fights a list whose rows mount and unmount underneath it.
- **A row's highlight is memoized TWICE, and both halves are needed.** `SearchRow` is `memo`'d (with a `useCallback` `onOpen` — without a stable identity the memo is useless), and `highlightSearchLine` (`src/shared/lib/code/highlight-cache.ts`) is a bounded LRU in front of `highlightCode`, because a virtualized list unmounts rows as they leave the viewport and would otherwise re-tokenize a line every time it scrolled back. **A line whose grammar is not ready is deliberately NOT cached**: `highlightCode` requests the grammar on the way through and falls back for that pass, and nothing re-renders when it lands — so a cached fallback would pin the row to plain text for the life of the cache (verified in the browser with `css`, a non-eager grammar: the rows are tokenized once the grammar arrives). The bound is 2,000 entries and the cache size is exposed (`highlightCacheSize`) because a hit and a recompute return equal strings — the map is the only observable.
- **The scroll-fade is a class on the element, not state.** `useScrollbarFadeRef` (`src/client/hooks/ui/scrollbar-fade.ts`, and the same hook in the plugin kit) returns `{ ref, onScroll }` and toggles the two overlay classes through the ref. The previous `useState` version re-rendered its owner on every scroll event, which on this list meant re-rendering every row — the trigger for the 34 s above. Every fading container in the app was migrated: the panels that own their scroller attach the ref directly, and the two lists that used to receive `isScrolling` as a prop (both session sidebars, the editor's `FileDocument`) now own it themselves.
- **One run delivers at most `MAX_SEARCH_RESULTS` (5,000) matches, and the cap is stated in one place.** The route stops at the cap and kills the `rg` child (`runRipgrep`'s `signal`) rather than draining a walk whose output is discarded, reports `truncated` on the `done` frame, and the panel prints "Showing the first 5000 matches" from the same constant. Measured: `const` went from a 3 MB payload and 19,376 rows to 848 KB and 5,000, in 51 ms. A batch that crosses the cap is trimmed rather than overshot, so the number in the notice is the number of hits the panel holds.
- **The panel is two components because the result list is expensive to re-render.** `index.tsx` owns the state and the search effect; `Body.tsx` owns the markup (fields + `SearchResults`). A keystroke in the Replace field re-renders `Body` and leaves the memoized rows alone — with the fields and the list in one component every replace keystroke rebuilt the whole list.
- **On the phone the drawer's active tab is PERSISTED** (`layout.mobileRightPanel`), and that is a performance decision as much as a convenience: `MobileRightSidebar` unmounts with the drawer, so whichever view is selected is the one that mounts and re-runs its own fetch on the next open. Coming back on Search re-ran a query that can hold thousands of hits, for a user who never asked for a search.

### Panel Plugin Kit (`@ompchamber/ui`)

- **The kit is the seam between the host and every panel — built-in or installed — so the surface a built-in view is allowed to use is the surface a plugin gets.** It is a published package (`packages/ui/`), which is why it reads the host through `configureUiKit`-injected services instead of importing `@/…`: an in-tree panel importing the kit and a plugin bundle importing it take the SAME code path, and the build shims the specifier to `globalThis.__ompchamberPluginRuntime.ui` for a bundle while it is a plain import for the app.
- **The surface is four modules, not one file** (`packages/ui/src/`): `services.ts` (the injected services and the two prop contracts), `panels.ts` (`usePanelInfo`, `useTheme`, `useSessionValue`, `useSessionState`, `useWorkspaceFile`, `useScrollbarFadeRef`), `fetch.ts` (`useChamberFetch`), `panel-host.tsx` (`PanelHostProvider` + `usePanelHost`), and `components.tsx` (the presentation kit plus `Markdown`). `index.tsx` is the package's public entry and re-exports them; the app and the shim both read the package root.
- **`usePanelHost` is a Preact CONTEXT, never a module singleton, and that is load-bearing.** The desktop stack keeps every built-in view mounted at once (hidden with CSS, so a tree's expansion and a terminal's buffer survive a switch), so "the panel currently being rendered" is not one process-wide fact — there are eleven of them live at the same time. A module-level value handed the wiki panel the terminal's `rootPath` and its `onClose`. Both layouts wrap each panel body in `PanelHostProvider` with the SAME props object they hand `panel.render(props)`, so a component nested inside a view reads exactly what its top-level one was given.
- **`useChamberFetch` is the kit's own reader, for a plugin panel that reaches the chamber's HTTP API.** The chamber's own data-backed views have moved to the realtime socket (`useRealtimeTopic`), but the kit keeps this because a plugin cannot import the host's hooks: it carries the three behaviours a hand-rolled fetcher gets wrong — a late answer for a request the user has moved past is DROPPED (a sequence guard), a new URL clears the previous payload BEFORE reading (so a stale list never renders under a new session's name), and a hidden or disabled view issues no request at all. `packages/ui/src/fetch.test.tsx` pins all three, plus the error path keeping the server's own reason.
- **`useSessionState` is `useSessionValue` for values that are not strings** — a collapsed-phase map, a picked file — through `getSessionJson`/`setSessionJson`/`subscribeSessionJson` on the injected services. JSON-encoding them into the string slot would make every reader parse it back.
- **`Markdown` renders through the chamber's pipeline by INJECTION, not by bundling it.** The marked / KaTeX / mermaid / Shiki chain plus the file-opening and clipboard hooks is a large tree, and a plugin must not carry a second copy; the host hands the kit the `MarkdownRenderer` component (`UiKitServices.markdown`). A host that injects nothing renders the source as plain text rather than failing.
- **What the kit deliberately does NOT own:** `useRepoScope`/`useRepoList` (a chamber-specific cross-panel store with its own invalidation tests), xterm, CDP screencast, the file tree and the diff parser. Those stay host hooks — a plugin that needs one depends on the library itself. Terminal, Files, Search, Git, Wiki, Context and both Browsers therefore still import `@/client/hooks/**`; the chamber's own Todo and Plan views read the realtime socket through the host's `useRealtimeTopic`, and `useChamberFetch` remains the kit's reader for plugin panels.

### Provider Credential Removal (Settings → Providers, "sign out")

- **`disable` and `disconnect` hide a provider; they do NOT remove its credential.** Both write `disabledProviders` in `config.yml`, and the OAuth token or API key stays on disk — two buttons that read as "turn this off" while leaving the secret behind is a security-relevant lie on a settings screen. omp exposes the real operation as `get_logout_accounts` + `logout`, and `POST /api/settings/providers/logout` (`src/server/routes/settings/provider-logout.ts`) drives both on the shared utility RPC child (no session involved). The credential is addressed by `(providerId, credentialId)`, which is why the accounts must be READ before one can be removed; `LogoutProviderModal` does that on open and lists them. The dialog states what survives — a `models.yml` entry and the chamber overlay row are untouched (`delete` is the control for the file entry) — so the distinction from `disable` is explicit rather than implied. A refused account read is REPORTED, never rendered as "no accounts": the two look identical on screen but only one is actionable.
- **`sign out` is offered wherever a login credential could exist, and the empty list explains itself.** omp decides which providers have removable credentials; measured on 18.8.3, a provider whose auth comes from `models.yml` or the environment answers `{accounts: []}`, and the dialog says so and points at `disable` instead.

### Provider Dialects (Settings → Providers, "Add Model Provider")

- **A provider is three `models.yml` fields, and the settings UI now offers all three.** `api` is the wire dialect (omp's own `ApiSchema`, 11 values), `auth` is `apiKey | none | oauth`, and `discovery` lets OMP list the models itself. `src/shared/lib/models/provider/dialect.ts` owns the value lists and the guards; the picker (`DialectFields.tsx`), the writer, and the validator all read from it, so a value omp rejects cannot be offered. **The lists are data, never a chain of `if`s at a call site** — a dialect is a row there, and `PROVIDER_APIS` is asserted against the shipped presets in `provider/presets.test.ts`.
- **Why this exists:** the previous dialog could only write "OpenAI-compatible + Bearer + apiKey + fetch `/models`". An Anthropic-shaped proxy was therefore unreachable (it answers `x-api-key`, and a Bearer probe 401s in a way that reads as a bad key), a keyless local server was rejected as unconfigured, and a provider omp already bundles got a duplicate model list written under it. The listing probe now follows the DIALECT — `openai-completions`/`openai-responses` send `Authorization: Bearer`, `anthropic-messages` sends `x-api-key` + `anthropic-version`, `google-generative-ai` puts the key in `?key=`, `azure-openai-responses` sends an `api-key` header with `api-version=v1` (omp's own `DEFAULT_AZURE_API_VERSION`) — and only an unclassified endpoint falls back to trying the three styles in order. Verified against a header-recording stub: each dialect produced exactly its own header.
- **Three provider shapes, and the writer treats them differently** (`upsertOmpProviderModels`, `src/server/lib/omp/config/providers.ts`; model-entry helpers split into `provider-seeds.ts`):
  - **full** — `models` non-empty; `baseUrl` plus an `apiKey` unless `auth: none`/`oauth`.
  - **discovery** — registered with `discovery: { type }` and an EMPTY model list. Writing ids as well would freeze a snapshot omp would then serve alongside its own live discovery. Verified: `omp models refresh <slug>` on such an entry returns the models from the endpoint.
  - **override** — `overrideOnly`, no model ids at all. This is the documented "override-only provider": omp keeps its own catalog models and only the endpoint changes. Verified: `anthropic: {baseUrl, apiKey, api: anthropic-messages, models: []}` still serves its 26 bundled models. **An override with no credential serves NOTHING** — omp has no key to reach the endpoint — so the empty-state message names the credential instead of only the shape.
- **A provider that does not exist yet is ALWAYS a change.** The upsert's no-op guard originally required a model addition or a filled dialect field, so a discovery/override registration — which by design adds no models — returned `written: false` and wrote nothing while the UI reported success. `providerChanged` now includes `!existing`.
- **`createdProvider` was removed** rather than left in the result: nothing consumed it, and `written` already says whether the file moved.
- **`credentialSource` is the signal for which dialog a provider needs** (`'omp-auth' | 'models.yml' | 'chamber'`, merged so `models.yml` wins). The old test — `id.startsWith('omp-auth-')` — was wrong twice over: a native models.yml entry shares that id prefix after the merge, and a keyless local server has no login flow to complete at all. A keyless provider now opens the endpoint dialog, which shows an explicit "registered with `auth: none`" note instead of an API-key field, and `handleReconnect` refuses to persist the dialog's masked placeholder as its credential.
- **Presets are grouped data, and availability is a rule not a status test.** `PRESET_NEW_PROVIDERS` carries `group`, `api`, `auth`, `discovery`, and `bundled`; `buildAvailableProviderPresets` offers a preset unless its slug is already OWNED (`providerOwnsSlug`: connected, or carrying its own `baseUrl`), and a `bundled` preset is always offered because its entry is an add-only override. **`status` alone is the wrong test** — omp reports ~60 providers it merely knows (`get_login_providers`), all `disconnected` with no endpoint, and treating those as taken hid every gateway preset, the one case where the user wants to bring their own key. The same rule feeds `existingSlugs`, which previously blocked the dialog with "already registered in models.yml" for a provider that was not in the file at all.
- **`modelSource` is persisted on the provider** so the models panel can say WHY a list is empty (`providerEmptyReason`). A discovery provider and an endpoint override have no local list BY DESIGN, and printing "no models" for either made a correct registration read as a failed one — while a hosted provider with no models keeps the unexplained message, because that one is a problem.
- **Validation was extended to the new fields** (`models-validation.ts`, unit-tested): `auth` outside the three values, an unknown `discovery.type`, `discovery` without a provider `api` (except `proxy`, which reports one per model), and `injectV1` outside `openai-models-list` are all refused. omp's failure mode is why — **one schema violation anywhere in the file makes it disable EVERY custom provider at once**.
- **`isMaskedApiKey` lives in `src/shared/lib/models/provider/dialect.ts`**, not in the writer: the client produces the `sk-••••…` placeholder and the server is the last gate before the file, so one predicate has to serve both.
- **"add model" beside "fetch models" is the path for ids no listing reports** (`AddModelModal.tsx` → `POST /api/settings/provider-model` → `manualModelSeed`). A listing endpoint is not the only way to know a model exists: an Azure deployment is a name the user chose, a gateway may serve a model its `/models` route omits, and Bedrock/Vertex expose no `/models` at all. The dialog writes the same models.yml entry the fetch would, so both paths converge on one writer. Only the model id is required — every other field is metadata omp works without (a missing context window is estimated, a missing price is simply not accounted), and requiring them would block the common case of "just add this id I know exists".
- **`manualModelSeed` drops what omp would reject rather than letting the file be validated after the fact**: a non-positive `contextWindow`/`maxTokens` and a HALF-filled price (omp's schema requires all four cost fields together) are omitted, and fractional token counts are rounded. The dialog validates the same rules inline so the user sees the problem before the request — but the seed builder is the gate, because it is also reachable from a stale client.
- **"Already registered" and "refused" are different answers, and `skippedModels` cannot tell them apart.** The writer skips a model both when the id is known and when it declines to create a provider it has no endpoint/credential for; reporting the second as the first hid the real reason ("provider not yet in models.yml and no api key available to register it"). The route reads `readNativeProviders()` BEFORE the write — after it, the model this call just added would count as pre-existing — and only a hit there is reported as a duplicate, with 200; a refusal stays 400 with omp's own reason. A duplicate is deliberately not a failure: the existing entry may be one the user hand-tuned in models.yml, and the add-only paths never touch an entry they did not write.
- **"fetch models" REPLACES the provider's list; every other writer appends.** `replaceProviderModels` (client, `shared/lib/models/provider/models.ts`) makes the endpoint's answer the model list — an id it no longer serves leaves — while carrying the user's per-model choices (visibility, sampling) onto the ids that survive. The request's `replaceModels: true` carries the same rule into `models.yml` (`prunableIds` → `removedModels`), and the panel reads its list from that file, so a client-only replace would have been undone on the next load. Measured end to end against a stub `/models` with a temp agent dir: a provider holding `[withdrawn, kept]` became `[kept, brand-new]` with `removedCount: 1`, the panel payload agreed, and a second fetch WITHOUT the flag still appended only. **The consequence is deliberate and must be named in the UI's copy:** an id registered by hand for a model the listing omits (Azure deployment, gateway-only id) is pruned by the next fetch — that is what "the listing is the list" means. `replaceModels` is sent only by the fetch path; `AddProviderModal`'s registration and the "add model" dialog leave it off, and `overrideOnly`/`discovery` can never prune (they write no ids). An entry whose id cannot be read is never pruned.
- **The endpoint and credential ride along only to CREATE a missing entry.** `baseUrl`/`apiKey`/`auth` are forwarded from the selected provider, and the writer never rewrites a provider field an existing entry already carries — so adding a model to a live provider can never change its endpoint. Verified end to end: a hand-added model on an existing provider, a fresh provider created from the dialog's endpoint+key, a keyless one with `auth: none`, and a refusal with neither — all four accepted by `omp models` with zero warnings.
- **After a hand-registered model the registry is re-READ, not re-saved** (`handleModelAdded` → `loadProvidersFromApi`). The new row exists only in omp's file, so the chamber overlay knows nothing about it; re-saving the overlay would return the overlay alone and leave the list short by one. Verified in the browser: the count went 3 → 4 and the row rendered with its context badge.

- **All four `models.yml` cost rates are entered, and the reasoning ladder is a set of checkboxes.** `PriceFields.tsx` asks for input/output/cache-read/cache-write; `EffortLadder.tsx` ticks the levels omp's `EffortSchema` accepts. Both encode a rule that is invisible in the UI otherwise:
  - **Input and output are the pair that decides whether a price exists at all** — omp requires all four `cost` fields together, so a lone cache rate with no headline price is refused inline rather than written as a partial mapping. Empty cache rates become `0`, which is the honest value for "no cached-token discount" (without them omp bills every cached turn at the full input rate). Verified against omp: `cacheRead: 0.25, cacheWrite: 3.125` round-trip through `omp models`.
  - **`off` is deliberately not an effort.** omp's schema rejects it inside `thinking.efforts` ("must be minimal, low, medium, high, xhigh or max") and turning thinking off is a per-turn choice the composer owns. An unknown level is FILTERED OUT at the route before it can reach the file — one bad level disables every custom provider — while the valid ones in the same request are still written.
  - **An empty ladder is a distinct state, not an error.** omp already assumes its own ladder for a reasoning model, so `efforts: []` would add a block that changes nothing; `toModelEntry` therefore writes no `thinking` block at all, and the hint says so ("No ladder declared — omp keeps its own default levels"). Ticking levels while Reasoning is off is refused: it would declare a capability for a model omp is not told can reason.
  - **The ladder is normalised to omp's order** regardless of the order the boxes were ticked, and `thinking.mode` is always written — omitting it is a schema failure that takes the whole file down. `thinkingErrors` in `models-validation.ts` checks mode, vocabulary and the presence of a ladder, and `sanitizeModelEntry` DROPS an unusable block rather than the model, since a model with omp's default ladder still runs.

- **"delete" exists only for a provider that HAS a `models.yml` entry, and the server says so.** `ProviderItem.inModelsYml` is set by the registry (`nativeProviderItem` is built FROM the file, so it is `true` by construction) and unioned across the merge, because the two halves see different files: a login provider's `omp-auth` half knows nothing about models.yml, while the native half does. The button appears beside enable/reconnect in `AuthSection.tsx` only when the flag is set — a provider living solely in the chamber overlay has nothing in the file to remove, and offering the button would promise an action it cannot perform. `DeleteProviderModal.tsx` names what actually goes (the file entry, its model count, the endpoint and key stored on it, which are only ever shown masked so they cannot be recovered) and what does NOT: a login provider's `omp-auth` credential is untouched, which is the difference between "I can add this back" and "I deleted my Anthropic login".
- **The DELETE handler resolves its target against the MERGED registry, not just the overlay.** It used to look the id up in the SQLite overlay alone — so a provider that exists only in `models.yml` (the common case: it was added by hand, or by an earlier version of the dialog) had no overlay row, `target` came back undefined, and the `removeOmpProvider` call below was skipped. The response still said `success: true`, the provider came straight back on the next load, and the delete looked like it had done nothing. Verified before/after against a real `models.yml`: the native-only entry is now actually removed.
- **The delete response reports `removedFromOmp` and `modelsRemoved` separately from `success`.** The overlay row is gone even when the file cleanup fails, so the two are different facts and the UI reports the failure as a warning rather than as a clean delete. `modelsRemoved` (from `removeOmpProvider`) is what lets the toast say how many models went with the provider instead of implying zero.
- **The delete fallback list is MOCK-only.** `providersStore.remove` takes `absent`/`empty` fallbacks, and passing the shipped `DEFAULT_PROVIDERS_LIST` in real mode would write demo providers into a user's overlay on the first delete — `providersStore.read` already returns `[]` there, so the fallback now matches it outside MOCK.

### Provider Usage (Settings → Usage, right-panel Usage)
- Two surfaces read one endpoint, `GET /api/settings/usage`: the Settings → Usage category (`src/client/components/settings/categories/UsageSettings.tsx`) and the right-panel `usage` view (`src/client/components/workspace/usage-panel/`). Both derive their rows from the same `buildProviders` (`usage-settings/providers.ts`), so the sidebar list and the panel dropdown cannot disagree. The provider id is the **slug**, not a closed union — a provider omp can authenticate appears without a code change.
- **The panel shows quota and balance only — never locally recorded tokens/cost.** Usage is what a provider reports; a number derived from the chamber's own transcript scan is a different quantity, and mixing the two made the card look like it had two disagreeing answers. kenari and DeepSeek are the exception only because their *own* APIs report a wallet/plan (Rupiah) and a prepaid balance — that is vendor data, not local. `aggregateUsage` therefore keeps no per-provider rollup (it still powers Token Usage telemetry, which is a separate surface).
- **A provider with no API key is omitted, never rendered as an empty row.** The credential set comes from `listCredentialedProviders` (`src/server/lib/usage/provider-key.ts`), which unions three store scans (models.yml `apiKey`, agent.db `auth_credentials`, the chamber's own provider overlay) with **omp's own view** — `get_login_providers.authenticated` plus the providers in `get_available_models`. The registry half is what makes environment variables work: `ANTHROPIC_API_KEY=… omp` authenticates and serves Anthropic models while no store on disk names it, so a store-only scan would hide a provider the user is actively running. A slug no store accounts for is reported as `environment`.
- **Two quota sources, tried in that order.** (1) `fetchOmpUsageSnapshot` (`src/server/lib/usage/omp-usage.server.ts`) runs `omp usage --json` and flattens each `UsageLimit` into `UsageLimitWindow`, resolving `usedFraction` with omp's own precedence (explicit > `used`/`limit` > percent-unit `used` > inverted `remainingFraction`). omp ships a usage adapter per vendor — 20 in 18.3.0 — but they cover **subscription plans** (rolling 5h/7d windows): anthropic, openai-codex, github-copilot, google-antigravity, google-gemini-cli, cursor, zai, kimi-code, cline-pass, minimax-code, muse-code, umans, devin, charm-hyper, xai-oauth, opencode-go, alibaba-token-plan, synthetic, ollama, ollama-cloud. (2) `fetchVendorBalance` (`vendor-balance.server.ts`) covers **pay-as-you-go credit balances** omp has no adapter for: openrouter, moonshot, siliconflow, novita, deepinfra. Both shape into the same `UsageLimitWindow[]`, so one renderer draws them and `tracked` becomes true when either yields data.
- **Anthropic and OpenAI are deliberately absent from the balance table.** Their usage/cost reports (`/v1/organizations/usage_report/messages`, `/v1/organization/usage/completions`) require an org **admin** key — a workspace key cannot substitute — so the chamber cannot read them with the credential the user actually configured. Anthropic still appears through omp's own adapter (which uses the OAuth subscription token), and its card says so when the fetch comes back empty.
- **`tracked` is a real distinction, and `accountsWithoutUsage` is the signal.** omp names a provider in `accountsWithoutUsage` **only when it has an adapter whose fetch produced nothing**; a provider it does not track never appears there at all. Verified against omp 18.3.0 with a stored credential: a failing Anthropic fetch (adapter exists) lands in the list, while a stored DeepSeek key with no adapter does not. `resolveUsageTracking` (`providers.server.ts`, unit-tested) derives `tracked` from "in `reports` or in `accountsWithoutUsage`", and the card prints a *different* explanation for each: no quota source at all versus a tracked provider whose endpoint came back empty. Collapsing the two tells the user a supported provider is unsupported. A provider that failed outright (`error` set) with no windows shows only the error — never a second "no quota source" note contradicting it.
- **kenari and DeepSeek keep their rich reports.** Both expose more than a limit list (Rupiah wallet/plan windows/coupons; prepaid balance), so `UsageProviderSummary` carries an optional `kenari`/`deepseek` field and `ProviderDetail` renders the rich card *instead of* the generic sections for those two. Every other provider gets `LimitsSection`, which is also where a USD credit balance lands.
- **A Kenari provider is identified per SLUG, so two accounts stay two providers.** `kenariProviderSlugs` decides which credentialed slugs are Kenari (spelling, or the endpoint in the chamber overlay / models.yml), `resolveKenariApiKey(slug)` reads that account's own key, and `buildKenariReport(slug)` fetches its quota/balance/usage — two accounts share the same upstream host, so the credential is the only thing telling them apart. Both halves were once pinned to the literal slug `kenari`: `providerIdentityKey` folded every entry whose name/slug/endpoint mentioned kenari onto one `kenari` key (a second models.yml account merged into the first's settings row, so its key was never read and the panel could only disconnect/delete one while omp still served the other), and the usage gate `credentials.has('kenari')` never built a report for it. Identity is now the provider's OWN slug, which still merges the two halves of one provider because omp reports a models.yml provider under its models.yml key.
- **The quota probe is cached for 60s; the Refresh button forces past it.** `omp usage` calls every provider's endpoint, so a topic republish must not run it. `?refresh=1` (sent only by a user's own Refresh) bypasses the cache — without it the button would return a minute-old snapshot and look broken. The registry probe behind `get_available_models`/`get_login_providers` has its own 60s cache and a cold spawn of ~1s, which is why provider names degrade to the slug-derived label when omp is cold rather than blocking the response. Vendor balances are fetched per request (a handful of cheap GETs) and a provider whose key lives only in the server's environment is a silent miss, not an error.
- Mock mode returns a deterministic four-provider report (kenari, DeepSeek, Anthropic with percent *and* non-percent windows, OpenRouter with a USD credit balance) so every card shape renders under `MOCK=true`.

### Provider Marks (`src/client/components/common/provider-icon/`)
- **One component draws every provider logo**, and every surface goes through it: the provider settings sidebar/header/login/reconnect modals and the "add provider" preset list, the composer's model picker (rows and section headers), and both usage surfaces. A provider therefore cannot be a whale emoji in the picker and a Lucide cloud in Settings — the previous per-surface `switch` on `providerIcon` and its `plug`/`Bot`/`Coins` placeholders are gone, and `provider-settings/Icons.tsx` was deleted with them.
- **Resolution is data, in `src/shared/lib/models/provider/glyph.ts`.** A provider reaches the component as whatever string omp reported — a login provider id (`google-vertex`), a user-typed models.yml slug, a legacy icon key (`claude`), or a display name — so lookup folds the input to lowercase alphanumerics and matches `PROVIDER_GLYPH_ALIASES`. Variants of one brand are rows in that table (`minimax-code-cn`, `xiaomi-token-plan-ams`), never branches at a call site. `resolveProviderGlyph(icon, slug, name)` tries the stored icon key FIRST so a legacy key keeps working after a slug changes; it returns `null` rather than guessing, which is what routes an unknown provider to the fallback.
- **A plugin's `providerIcon` registration beats the built-in mark, for the provider it names only** (`provider-icon/resolve.ts`, called from that one component). The provider is folded with the same rule the table uses (`foldProviderKey`), so `google-vertex`, `Google Vertex` and a legacy icon key all find a registration. A registered glyph is a complete `<svg>` source whose paint is `currentColor`; the host still owns the outer `<svg>`, so it themes and sizes like a built-in mark. Two plugins naming one provider resolve to the first merged row (`order`, then plugin id, then registration id) — deterministic, and the second registration is still accepted. A glyph with no root `<svg>`/`viewBox` falls through to the built-in mark, so the mark shown never depends on which plugin shipped a broken string.
- **A provider with no mark draws its initials, not an empty box.** `providerInitials` takes one initial per word, joined and closed with a single dot — `Tooker` → `t.`, `Toktok ID` → `ti.`, `toktok-id` → `ti.` — capped at two initials (a third overflows at icon size). **The badge is a pill, not a square**, and its font size is `1.2 × size`: a square column forced the text to 9.5px for `ti.` to fit, whose ink was 6.4px against the marks' 13.8px median, so the fallback read as an undersized icon. At 1.2× the ink lands inside the box (10–15px in a 16px band, ≥1px clearance; 1.3× clips) and matches the marks. The badge is `aria-hidden` because the provider's name is always rendered beside it.
- **The glyphs are generated data, never hand-edited** (`provider-icon/glyphs.ts`, 73 marks). Sources, in resolution order: `@lobehub/icons-static-svg` (MIT) → `simple-icons` (CC0, GitLab/Xiaomi) → `selfh.st/icons` (CC BY 4.0, LiteLLM/llama.cpp) → the vendor's own SVG with any background plate dropped (abliteration, aiand, aimlapi, yolo-auto) → a **potrace outline of the vendor's own raster logo** refitted to the shared box (coreweave, nanogpt, charm, singularity). That last tier is why five marks carry a `translate/scale` group: a brand publishing no vector mark is still drawn from its own art rather than approximated. **A traced mark is refitted so its ink fills 88% of its viewBox** — parsing `magick -trim info:` with one regex matched the *canvas* geometry rather than the ink bbox and left every traced mark ~2x small, which is the class of bug that made the initials badge look oversized by comparison; use `-format %@` (it prints the ink bbox alone) and verify the refit by measuring the rendered ink box. Each glyph keeps its own `viewBox` (mostly `0 0 24 24`; `synthetic` is 54, `litellm`/`llamacpp` 512), so a caller must pass `glyph.viewBox` rather than assuming 24. Marks whose art is naturally wide-and-short (Cloudflare, SiliconFlow, Alibaba, Abliteration) still read small by ink *height* — that is the logo's aspect, not a bake error.
- **Paint is folded to `currentColor` at bake time** — a glyph takes the surrounding ink and follows the theme (verified: a theme flip moves a mark's computed colour), which is what keeps a dense monochrome list free of the only chroma in the palette. Per-element `fill-opacity`/`fill-rule`/`stroke-width` survive because they carry the mark's own structure (Azure's overlapping panes, Cerebras' ring, Synthetic's stroked outline), not a colour. These are third-party trademarks, used to identify the provider each belongs to; they are not covered by the project licence.
- **Adding a provider** is one row in `PROVIDER_GLYPH_ALIASES` when the brand mark already exists, or one new glyph plus its row when it does not — never a new `if` in a renderer. `provider-glyph.test.ts` walks omp's whole `KnownProvider` census and fails if a provider resolves to neither a mark nor initials, so an upstream provider addition surfaces as a test failure rather than a blank badge.

### Ask Tool — Grouped Dialog (one request, every question)

- **omp offers two shapes for one `ask` call, and the chamber takes the grouped one.** By default it loops one blocking `select` per question, which the inline card reassembles with `groupAskFrames` + `useAskDrafts`; after `set_ask_dialog {enabled:true}` (sent by `configureChild`) it sends ONE `extension_ui_request` with `method:"ask"` carrying every question — with `multi` and `recommended` — answered by a single `{answers:[{id, selectedOptions, customInput}]}` reply. Verified on 18.8.3: two questions including a `multi:true` one arrived in one frame. `GroupedAsk` renders all of them with one `Submit answers`, so a multi-select question is picked in one pass instead of one round trip per toggle.
- **A grouped frame carries NO `title`, so the title walk cannot place it.** `splitAskFrames` claims it by the question IDS omp puts in both the frame and the tool call's arguments — the same key `parseAskQuestions` reads — and places the SAME frame on every question it names, because one dialog answers all of them. A grouped frame naming no open question is left as modal material, like any other unclaimed dialog. `ask-frames-grouped.test.ts` pins both directions.
- **Both halves must ship together.** Enabling `set_ask_dialog` makes omp send a frame the client cannot otherwise answer, which would block the agent with nothing on screen to answer it; the opt-in, the `questions` field on `ExtensionUiDialogRequest`, the `answers` response variant, the split's id matching and `GroupedAsk` are one change.
- **omp's `description` for a choice is VISIBLE text on its row, and both shapes draw the row through one component (`OptionRow`).** omp's own `ask` prompt puts the tradeoff there ("short labels, tradeoffs in `description`"), so it is half of what the user is deciding between. The grouped card rendered it as `title={option.description}` — a hover tooltip — while the per-question `select` loop (`FrameControl`) printed it, so the two shapes of ONE tool asked the user to pick blind vs. informed, and a phone could never hover at all. The row is now shared (`OptionRow.tsx`: mark, label, description, `suggested` badge, the multi-select "Done" emphasis), which is what makes the drift impossible rather than merely fixed; `index.test.ts` pins the description as visible text and the absence of the `title` attribute, and `ask.e2e.ts` asserts it on the real card.

### Todo Panel (right-panel Todo view)
- **The list is oh-my-pi's, and its only durable home is the session transcript.** There is no todo file and no chamber-side copy — a second copy would drift from the one the agent rehydrates, and a plan panel that disagrees with the agent is worse than no panel. `todo` calls commit a full snapshot to the entry they append (`message.details.phases` on the toolResult, or `data.phases` on a `user_todo_edit` custom entry), and every branch rehydration — resume, rewind, fork, `/btw` — reads the DEEPEST such snapshot off the ACTIVE BRANCH back out of it (omp's `getLatestTodoPhasesFromEntries` → `syncTodoPhasesFromBranch`). `src/shared/lib/chat/todo/snapshot.ts` performs that same read: branch walk by `parentId` from the last entry, newest-first, skipping `op:"view"` results (they echo the list without committing it) and errored ones.
- **Read path is `readSessionTodos` behind a realtime topic, and no omp process.** The `todos` topic resolver (`src/server/lib/realtime/topics/session-data.server.ts`) calls `readSessionTodos` (`src/server/lib/omp/session/todos.ts`) → `findSessionFileById` → full JSONL parse, cached by (size, mtime) on `globalThis`. Measured on real sessions (7.2 MB / 1905 entries): ~15 ms parse, 0.02 s cached round trip. **A full parse is deliberate** — the todos may sit megabytes from EOF (measured: 2.7 MB from the end of a live session, and `None` in another), so a bounded tail window would report "no todos" for exactly the sessions that have the most. The panel never spawns an `omp` child: that would fight the chat's own session wrapper for the same session file.
- **The read rides the session's own `todos` realtime topic, so there is no poll.** `session-data.server.ts`'s `todosDescriptor` resolves `readSessionTodos` on demand and the server republishes the topic on the `session-data-dirty` signal, which the chat emits at every turn boundary — i.e. right after each `todo` call. `TodoPanel` subscribes through `useRealtimeTopic(sessionTodosTopic(sessionId))`; the panel's own Refresh calls the topic's `refresh`. The `session-todos.ts` client hook and its `omp:session-updated` / `TODO_REFRESH_EVENT_THROTTLE_MS` hand-rolled event path are gone with it.
- **Follows a live agent from outside the chamber** (verified): with another `omp -p` process driving a session, the panel went `0/3 done · 1 in progress` → `1/3 done · 2 blocked` and rendered the blocker notes, purely off the topic republish. Within the chamber the same path makes it immediate.
- **Five statuses, not three.** omp's vocabulary is `pending | in_progress | completed | abandoned | blocked`; the chat timeline's older tool card only ever drew three, so a `blocked` task rendered as an ordinary pending one. `progress.ts` owns the status → presentation table (icon, tone, active/closed) and `todoProgress` counts **closed = completed + abandoned** — the pair omp's own HUD hides as settled, because leaving an abandoned task in the denominator makes a list read as permanently stuck. A `blocked` task's `blocker` note is rendered under its content; it is the only place omp records WHY it waits.
- **The chat's `todo` tool card is a different thing and stays separate.** `src/shared/lib/chat/todo/parser.ts` (moved from `chat/todo-parser.ts`) parses what ONE call did from its text output for the timeline card. Merging them would attribute every other call's work to whichever card was on screen; the two files are documented as the distinction.
- **Empty states are distinguished** because they mean different things: no `sessionId` ("No session selected"), a transcript with no snapshot at all (the agent never planned here), and a list whose every task is closed (renders normally, 100% bar). Collapse state per phase is persisted under `todo.collapsedPhases` (verified surviving a reload).
- **`enabled` is deliberately NOT the workspace gate the other panels take.** That flag means "the active session's cwd resolves to a registered workspace folder", which files/search/git/terminal genuinely need. A todo list lives in the session's own transcript, so a session running outside every registered workspace still has one — gating on it showed "No session selected" over a full list (measured, both desktop and mobile). The desktop view therefore takes only `active`; the phone's drawer keeps its whole-drawer gate for the workspace views but exempts the `todo` tab. `TodoPanel` itself answers "No session selected" when there is no `sessionId`.
- **Mock mode** returns a deterministic six-task list covering every status (including a `blocked` with a blocker note and an `abandoned`) so all render shapes are exercised under `MOCK=true`. The demo lives in `src/server/lib/omp/session/data-mock.ts`, called by the `todos` topic resolver — NOT in an HTTP route, because the panel reads the topic and a demo reachable only over HTTP would leave the view empty under MOCK.

### Wiki Panel (right-panel Wiki view)
- **The view sits beside Source Control in the activity bar, on both layouts**, because a wiki is read off the same remote through the same repo pick — one pair in the bar rather than one at each end. The position is not restated in the two components: they render the merged panel catalog, whose built-in half is ordered by `RIGHT_PANEL_TYPES` (the desktop bar, the desktop panel stack and the phone's tab bar all read it), so moving one row moves every surface.
- **A wiki is read over git, not over an API, and that is why one panel covers GitHub, GitLab and a self-hosted GitLab.** Both hosts publish a project's wiki as a SEPARATE repository at `<origin>.wiki.git`, so `src/server/lib/wiki/remote.ts` appends the suffix to the checkout's own remote and the fetch authenticates exactly the way the checkout does — no token scope, no API version, no per-host branch. Verified end to end on `github.com/jgraph/drawio` (19 paths, `[[Embed Diagrams]]` gollum links, images) and on `git-rbi.jatismobile.com/jns6_5/drrealhandler` (7 paths, 0.7 s cold, `_sidebar.md` and `.gitlab/redirects.yml` correctly kept out of the nav). The provider name the header shows is a LABEL: it picks the "open on the host" URL (`/wiki/Page` vs `/-/wikis/Page`) and is decided by name for `github.com`/`gitlab.com`, otherwise by probing `/api/v4/version` **only after a wiki fetch has already succeeded** (so the common failure path never pays for it).
- **The mirror is one bare, shallow clone per wiki, cached on disk under `<data>/wiki/<host>__<slug>`, TTL'd 60 s in memory** (`mirror.server.ts`). `HEAD:refs/wiki/latest` is fetched directly, so there is no working tree to keep in sync; `--depth 1` keeps a changelog wiki's history out of the cache. Two details are load-bearing: `--no-write-fetch-head` plus a refspec (rather than a named remote) keeps the credential-carrying URL out of `.git/config` and `FETCH_HEAD` — verified, neither file mentions the remote the fetch used — and the cache key is host+slug rather than the URL, so an `https` and an `ssh` spelling of one remote share a mirror. The cache itself hangs off `globalThis` (`__ompChamberWikiCache`) for the same reason the database handle does: `bun --hot` re-evaluates the module while the mirrors on disk stay.
- **Every `git` call is an argv spawn, never a shell string** (`src/server/lib/wiki/git.ts`). A wiki path is author-chosen and does hold spaces (`Setting-up-a-OneDrive-project-to-use-with-diagrams.net.md`), and a checkout path is user-chosen; there is no shell to escape them against. `GIT_TERMINAL_PROMPT=0` rides on every call, because without it a private wiki blocks on a credential prompt with no terminal to answer it and the read hangs to its timeout instead of reporting that the wiki is not readable.
- **A missing wiki is an ANSWER, not an error.** Git says "Repository not found" / "Authentication failed" / "could not read Username" for a wiki that does not exist and one the chamber cannot read, and both mean the same thing to a reader — so they map to `reason: 'no-wiki'` and the panel words it, rather than reporting a failure. The other three reasons are distinct and separately worded: `no-remote` (the checkout has no `origin`), `unsupported-remote` (a local path, a bare host — anything the suffix cannot hang off), `unreachable` (timeout, network, git missing). All four verified against the API.
- **A page is read at the ref, never off a path** — `git show <ref>:<path>` can only name a blob in the wiki's own tree, so a crafted `../../../../etc/passwd` returns "Page not found" (verified) rather than reaching the filesystem. Pages travel as markdown SOURCE (`/api/wiki/page`); the panel renders them through the app's own pipeline, which is what gives a wiki page the same sanitizing, Shiki highlighting, KaTeX and mermaid hydration the chat timeline has — verified live on a real wiki whose Home carries a ```mermaid diagram and four fenced blocks.
- **A wiki's images are in the wiki's repository, so the panel serves them itself** (`/api/wiki/asset`, bytes read with `Bun.spawn` — the text runner would turn a PNG into replacement characters). The response carries `nosniff` and a `sandbox` CSP, which is what keeps an SVG in that author-controlled tree from running script if a reader opens the asset URL directly; verified: a 455×349 PNG and its SVG twin both render inline on the page. `getImageMimeType` deliberately excludes SVG (the editor's viewers treat it as text), so the route names `image/svg+xml` itself.
- **The nav is the wiki's OWN `_Sidebar.md`, not a tree derived from the file layout** (`src/shared/lib/wiki/sidebar.ts`). Both hosts serve that file as the navigation around every page, so it carries the author's grouping, order and labels: the GitLab wikis here group `### 📚 Navigation` / `### 📋 Changelogs` / `### 📊 Info` with labels like `🏠 Home` and a `**Version**: 1.6.0` note block, all of which a folder-derived list turns into `NAVIGATION`/`CHANGE_LOGS` in a different order. The parser is deliberately tolerant — a rule instead of a heading, a nested bullet, a link with a `"title"`, and a prose block are all in real files. **A page the sidebar omits is appended under `Other pages` rather than hidden** (`withRemainingPages`): the sidebar is the author's navigation, not an index, and the panel has no address bar — measured on `jns6_5/personalschedulertrigger`, whose sidebar lists 12 of its 26 pages, the panel renders all 26. A wiki with no sidebar at all (`github.com/jgraph/drawio`) falls back to `sectionsFromEntries`, which groups by folder so the panel is never un-navigable. Verified in the browser: the sidebar's own groups and labels render, clicking `🧪 Testing Guide` opens that page in-panel with `aria-current` on the item, and no tab opens.
- **Three provider conventions are encoded in `src/shared/lib/wiki/pages.ts`, because each is invisible in the raw markdown and each was wrong in the first cut.** (1) Chrome fragments — `_Sidebar`/`_Footer`/`_Header`, any case — are not pages; listing them puts a nav fragment in the middle of the nav. `_Sidebar` is the one read back as navigation (above); `_Footer`/`_Header` are simply dropped. (2) References are case- and space-insensitive: `[[Embed Diagrams]]` targets `Embed-Diagrams.md` (gollum's space→dash rule), GitLab's `[v1.6.0](change_logs/v1.6.0)` omits the extension, and GitHub's own wiki resolves `/wiki/eMbEd-Diagrams` — so resolution tries the written path, the extension form, the dash form of both, and matches case-insensitively. (3) Assets are entries too, or a page's `![](images/schema.png)` has nothing to match.
- **A bare path is resolved from the wiki ROOT first, then from the page's own folder — and only `./`/`../` means "beside this page".** That order is not a coin flip: it is what both hosts do, and it is the difference between a working link and an inert one on a nested wiki. A real GitLab wiki writes `[TRD v1.3.3](trd/v1.3.3/home)` from `trd/v1.3.2/home.md` — rooted at the wiki, while page-relative resolution looked for `trd/v1.3.2/trd/v1.3.3/home` and found nothing. Measured on `jns6_5/personalschedulertrigger`: **25 of its 41 links failed to resolve, and every one of them then opened a browser tab** (the click handler classified them from `link.href`, which the DOM always absolutises, so a relative path read as external). After the fix the same census is **41/41**, and `jns6_5/drrealhandler` is 34/34.
- **Gollum's `[[Page]]` is expanded BEFORE the markdown parse, and its destination is percent-encoded.** `[[x]]` is invisible to a markdown parser (it renders as literal brackets), so `expandGollumLinks` rewrites it — leaving fenced blocks and inline code alone, or a page documenting the syntax gets its example rewritten. The encoding is the second half of the same bug: a bare `[Embed Diagrams](Embed Diagrams)` is **not a link at all** (a markdown destination cannot contain a space), so marked emitted the brackets as text and the whole Home page of a real wiki rendered unlinked; measured in the browser before and after (`links: [Deploying, Translations]` → `[Deploying, Translations, Embed Diagrams, Getting Support]`).
- **The panel renders the chat's `MarkdownRenderer`, in a third mode** (`wikiScope`). `document` mode was already the "the source IS the document" contract; wiki mode adds gollum expansion and resolves references against the wiki's tree — a LINK to a page becomes in-panel navigation (`data-wiki-path` → `onWikiNavigate`), an IMAGE goes to `/api/wiki/asset`, and a link to any OTHER file in the wiki keeps that asset URL with no marker (copyable, middle-clickable, inert on a plain click — the panel is a reader, not a file browser). A reference that resolves to nothing is left exactly as written.
- **The click handler classifies a wiki link from the RAW attribute, never `link.href`.** `href` is always absolutised by the DOM (`/trd/v1.3.3/home` reads as `http://127.0.0.1:7799/trd/…`), so a relative path that named no page was indistinguishable from an external URL and opened a tab. Only an `http(s):` raw href leaves the console; a bare `#anchor` is left to the browser, because the heading it names carries the id the wiki's own table of contents wrote (see below); anything else is inert.
- **Headings are given the id the page's own anchors name** (`wikiHeadingSlug`, applied by `rewriteHeadingIds`). Both hosts slug a heading by lowercasing it and dropping everything that is not a letter, digit, **combining mark**, space, hyphen or underscore, then turning spaces into hyphens — so `## 🎯 Overview` is `#overview` while `## ⚠️ Migration Queries` is `#%EF%B8%8F-migration-queries`, the symbol dropped and the U+FE0F mark after it kept. The renderer's own id keeps the emoji, so every TOC entry pointed at an element that did not exist and clicking one did nothing. Verified over all three cached wikis: **9/9 anchors resolve** (7 of them emoji-headed), and a live click scrolled the page from 858px to 0 with no new tab.
- **`wiki.selectedPage` is stored WITH its scope** (`{ scope, path }`, scope = `root repo`), the same rule `workspace.activeRepo` follows: a page path from another repository names a page this wiki does not have, so restoring it would open a 404. The stored path is used only while it still exists in the current wiki, else Home, else the first page — a wiki whose Home was renamed still opens on something readable.
- **The nav sits on the RIGHT and the page keeps the panel's leading edge** (`@[520px]:flex-row-reverse`), so the wiki reads as a menu beside the document rather than a sidebar before it. The reverse is visual only — DOM order stays list → page, so the narrow drill-down's hidden/shown pair needs no second set of rules, and the divider moves to the list's leading edge (`border-l`).
- **Layout is two columns above 520px of PANEL width and a drill-down below it** (`@container`, not `sm:` — the panel is 469px on a 1440px screen). Measured in the browser after the move: at 575px the nav is 208px at `left 1348` beside a 367px page at `left 981`; at 420px the list takes the panel and selecting a page swaps to it with a back button (the back button is `@[520px]:hidden`, so it does not appear in the two-column layout it has nothing to go back to). The page list is grouped Home → root pages → one group per folder, and filtered by a search box.
- **MOCK=true answers a deterministic demo wiki** — a page with a table, a mermaid fence, a TS fence and an internal link, plus a tree that exercises the folder grouping and the chrome/metadata filters — so every render shape works without an omp install.

### UI Authentication (the login screen)

- **The login screen is the app shell, not a page of its own.** `App` renders `<LoginScreen/>` whenever the client's auth store says `required`, at whatever URL the document was served from, and the shell is reachable without a session on purpose (it is the way in). `authGate` (`src/server/lib/auth/guard.ts`) is the one authority: a single `onBeforeHandle` that covers every Elysia route, with `isPublicPath` naming what an unauthenticated visitor may still fetch (the bundle, the fonts, `/api/auth/state`, `/login`).
- **A signed-in visitor asking for `/login` is answered `302 → /`, and that check sits BEFORE the public-path shortcut.** `/login` must stay public (it is the only way in), and that is exactly what used to let the shell render the workspace at a URL that says `/login` — a bookmark, a stale tab or the back button kept landing there. The redirect also fires when authentication is off entirely, where there is nothing to log into. Verified end to end against a real server: `GET /login` with the session cookie answers `302 location: /` on every boot, and `200 text/html` without one.
- **A session's fingerprint binds to a DETERMINISTIC key, never to the argon2 hash.** `issueSessionToken`/`verifySessionToken` take a `credentialKey`, and `credentialFingerprint` is `HMAC(sessionSecret, credentialKey)` where the key is `deriveCredentialKey(password, sessionSecret)` — scrypt, salted with the persisted secret. The argon2 hash cannot serve: its salt is random per boot, so a restart minted a new hash, changed the fingerprint, and **silently killed every session on every restart and every `bun --hot` save** — measured: a token valid before a second `initAuth` call was rejected after it, with the secret correctly read back from disk. That defeated the documented reason the secret is persisted at all ("a restart keeps its sessions"), and it is what a user reported as being bounced back to the login screen. argon2's own `salt` option is not an alternative (verified on Bun 1.4.2: two hashes with the same salt still differ). The revocation properties are unchanged and pinned by tests: a different password derives a different key, and `revokeAllSessions` rotates the secret — both kill every existing token, while a restart with the same password does not. `auth.json` still holds only the secret: nothing on disk can enable authentication or reveal the password. Verified end to end: log in, `SIGKILL` the server, boot it again with the same `OMPCHAMBER_DATA_DIR` and password, and the same cookie still reports `authenticated: true`.
- **The client store flips on a 401 only OUTSIDE `/api/auth/`** (`AUTH_PREFIX`, `src/client/hooks/ui/auth.ts`). The bridge wraps `window.fetch` once so 128 call sites need no auth awareness, but the auth endpoints answer 401 about the credential the caller just supplied — `POST /api/auth/password` does for a mistyped CURRENT password — and treating that as a lost session threw a signed-in user's whole workspace behind the login screen over an ordinary typo. A gate rejection of the same path is indistinguishable and costs nothing: any other gated request flips the store on its own. Pinned by `src/client/hooks/ui/auth.test.ts` (happy-dom).
- **The login screen re-checks the session instead of trusting what put it there**, on mount and whenever the tab becomes visible: a sign-in in another tab, or a document restored from the back/forward cache, would otherwise leave a form asking for a password the browser already has. `probeSession()` is deliberately read-only — using the store-aware `checkAuthState()` would mount the workspace with the settings an unauthenticated shell never injected (the same reason `login()` reloads instead of flipping a flag) — and it answers `null` rather than `false` when the server cannot be asked, so a dropped request neither signs a user out nor sends them somewhere unverified.
- `/api/auth/password` and `/api/auth/revoke` are implemented server-side but have no UI caller yet; the sign-out surface is likewise not wired.

### Build & Dev Loop
- **The server is the only entry point, and it is the bundler's entry too.** `src/server/index.ts` imports `index.html`; Bun bundles that page's script, styles and assets and serves them from its own routing table (`/_bun/asset/*` and `/_bun/client/*` in dev, `/chunk-*` in production). `bun run dev` is therefore ONE process — there is no client watcher, no `dist/client` to have been built first, and no second port.
- **HMR is real and Bun owns it.** `Bun.serve({ development: true })` injects its own client and pushes updates over `import.meta.hot`; saving a client file is applied in the browser, saving a server file restarts the process (`bun run --hot`). The `dev-assets.ts` proxy that forwarded rsbuild's hot-update chunks is gone with rsbuild.
- **Dev assets are proxied through the server, because Bun's own dev asset routes cannot be cached and that is what made every page load re-download the bundle.** In `development: true` Bun answers `/_bun/client/*` and `/_bun/asset/*` from its routing table with an `ETag` it then ignores (`If-None-Match` → always `200` + full body), no `Cache-Control`, and no compression — measured on 1.4.2: a 19.7 MB unminified dev bundle was re-sent in full on every load, against 9.5 MB *once* in production. `lib/assets/dev-assets.server.ts` closes it: `ssr.ts` rewrites the shell's `/_bun/client|asset/` urls to `/_dev-assets/*` (Bun's table wins for the paths it declares, so a route on `/_bun/*` is never reached — verified), and that module fetches the bytes back from the listener to add `Cache-Control`, a content `ETag` and the `304`, plus the compression `plugins/compress.ts` already provides (19.7 MB → 3.3 MB zstd). `/_bun/hmr` (the WebSocket) and `/_bun/unref` (the beacon) deliberately stay on Bun. The rewrite runs BEFORE the bootstrap payload is injected, so a `/_bun/` string inside a user's settings is untouched. **`no-cache`, never `immutable`**: the bundle's name is a build-generation hash that changes per rebuild, but the CSS asset names are NOT content-addressed — appending a rule to `tailwind.css` changed the bytes at the same `/_bun/asset/<hash>.css` URL — so `immutable` there would pin stale styles for a year.
- **The dev bundle is held by the service worker, not the HTTP cache, because the HTTP cache physically cannot hold it.** Chrome declines to store a response whose decoded body reaches ~5 MB — measured with `Cache-Control: no-cache` and a working `ETag`: 1 MB and 4 MB answered `304` on the next load, while 5/6/7/8/16/20 MB were re-fetched in full and never sent `If-None-Match`. So the proxy alone still left the 19.7 MB bundle re-downloading every load. `public/sw.js` therefore caches `/_dev-assets/client/*` in Cache Storage (no per-entry limit; verified: the second load reports `transfer: 0` and the cache holds one entry). It keeps ONE generation — storing a new bundle deletes the others, so a rebuild cannot accumulate bundles — and it deliberately does NOT cache `/_dev-assets/asset/*`, whose names survive a content change; those go to the network and revalidate through the proxy's `ETag`.
- **`development` is derived, not configured**: Elysia's Bun adapter passes `development: !isProduction` to `Bun.serve` from `NODE_ENV`, so `bun run dev` and `bun run start` differ by that one variable and nothing else. The proxy and the shell rewrite are gated on the same variable (`DEV_ASSETS_ENABLED`), so production is untouched: its assets are content-hashed and already answered with a working `304` and `immutable` by Bun's table (runtime) or `plugins/static.ts` (AOT).
- **A dev server walks toward the descriptor cliff, and the surface now says so before the breakage.** `development: true` keeps the whole client module graph open for HMR — measured **3,545** descriptors after a single page load for this app, against **17** with `development: false` — and a macOS reload never closes the previous generation's (`bun#40706`; the pre-exec sweep exists only on Linux), so the count climbs with every rebuild (measured +2…+9 per edit, ~17/min on this repo while agents edit it). At Darwin's `OPEN_MAX` (10,240) `posix_spawn` starts answering `EBADF: bad file descriptor, posix_spawn '/bin/sh'` — verified A/B: 10,230 descriptors spawn fine, 10,240 fails — and from then on **every** spawn in the process fails at once: the PTY shell, the omp child, `git`, `rg`, until the instance is restarted. `lib/lifecycle/fd-pressure.ts` keeps the count visible: `GET /api/health` carries `fds: { open, highest, limit, nearCliff }` (a `fcntl(F_GETFD)` sweep capped at the cliff, ~1 ms, null where the host cannot answer) and `ompchamber status` prints it with a restart hint. A long-lived session belongs on a production server: 17 descriptors, not 3.5k.
- **Process-wide state that owns a descriptor belongs on `globalThis`, not in a module binding.** `bun --hot` re-evaluates a changed module in place, so a module-level cache is reset while its handle lives on and the old one is never closed. `db.server.ts` leaked a `bun:sqlite` handle per reload of that file — measured `db.sqlite` and `db.sqlite-wal` at 19 descriptors, +2 per edit, each one 2 descriptors closer to the cliff above. The slot is `globalThis.__ompChamberDb`, for the same reason the terminal store, the flock host and the provider cache are anchored there.
- **`lib/assets/conditional.server.ts` owns the one "is the client's copy still good?" decision**, because two routes hand out bytes and they must agree: `plugins/static.ts` (a file on disk) and `lib/assets/dev-assets.server.ts` (bytes fetched back through Bun's dev asset routes). A rule applied to one and not the other would make one asset kind revalidate differently from another for no reason a caller could see. The load-bearing part is precedence — RFC 9110 §13.1.3: a recipient MUST ignore `If-Modified-Since` when the request carries `If-None-Match`, so the presence of `If-None-Match` settles the response on its own and a non-match means "stale" (200), never a reason to consult the date. Every branch errs toward "not modified = false": a false costs one full response, a wrong true hands the client a stale asset with no way to notice. The file route mints a WEAK validator from size+mtime (`W/"<size>-<mtimeSec>"`) — a content hash would mean reading every asset on every request, the opposite of the point, and a wrong 304 from size+mtime needs both a same-size edit and a preserved mtime, which no build or editor does. **The mtime is floored to whole seconds before comparing**: HTTP dates carry one-second resolution, so a file whose mtime has a fractional part would otherwise be permanently "newer" than the `Last-Modified` this server just sent for it and could never revalidate (measured: `IMS` on an unfloored mtime answered `200` every time). Verified end to end in both prod modes — `/sw.js` (the only `max-age=3600` asset, so the only one that ever revalidates) now answers `304` to `If-None-Match` and to a fresh `If-Modified-Since`, and `200` + the new bytes once the file actually changes. The AOT bundle had no validator at all before this, so every hour each client re-downloaded it in full; runtime mode already had one from Bun.
- **`bun run build`** (`scripts/build-client.ts`) bundles the SERVER plus the page's assets into `dist/client`, and that bundle is what `ompchamber serve` executes (from `dist/client` as its cwd). It exists for the published tarball and for CI, and the CLI runs it on demand when the bundle is missing (see `buildProductionBundle` in `src/cli/lib/runtime.js`); `--dev` skips it entirely, and production does not need it — `development: false` makes the server bundle its HTML route on the fly and cache it in memory. **`Bun.build` via the JS API, never `bun build`**: the CLI does not read `bunfig.toml`'s `[serve.static]` plugins (verified: `bun build --target=bun --production` emitted Tailwind's `@theme` verbatim, zero utility classes).
- **`bunfig.toml`'s `[serve.static].plugins` is the dev and prod plugin list.** One entry, `src/server/lib/bundler/css.ts`, which expands Tailwind v4 (`@theme`/`@import "tailwindcss"` are PostCSS syntax Bun's CSS parser rejects), flattens nested at-rules (`nested-at-rules.ts`, registered after Tailwind), and lifts `@font-face` blocks out of the bundle. `scripts/build-client.ts` passes that same module to `Bun.build` explicitly.
- **That plugin makes the Tailwind toolchain a RUNTIME dependency, not build tooling.** `Bun.serve` loads it whenever an HTML route is bundled — every `ompchamber serve --dev` and every `bun run start` — so `@tailwindcss/postcss`, `postcss` and `tailwindcss` are all declared in `dependencies`. They were not: `@tailwindcss/postcss` was a devDependency and `postcss` was declared nowhere, which no local run could reveal (a checkout has the whole tree) but a published install cannot load. Measured on a production-only install of the published tarball: the server came up and answered `503` on every page, logging `error: Failed to load plugins for Bun.serve: Cannot find package 'postcss'`; `bun add -g` failed one dependency later on `@tailwindcss/postcss`. `tailwindcss` itself is direct rather than transitive because `@import "tailwindcss"` in `src/client/tailwind.css` is resolved by Tailwind's own resolver from the project root — verified by forcing the package out of the root (nested under `@tailwindcss/node` only): the bundle then fails with an `enhanced-resolve` error. `src/server/lib/bundler/dependencies.test.ts` walks every bare import in `src/` and fails if one is missing from `dependencies` (a `devDependency` counts as missing), which is what keeps a build-shaped module from drifting back into the build-only list.
- **Nested at-rules must be flattened before Bun sees them, because Bun's minifier re-nests them into a form Chrome drops.** For `target: 'bun'` (which this build needs — its entrypoint is the server) Bun emits a rule's nested at-rule as `@supports (…) { & { … } }`, and a nested rule whose parent selector names a pseudo-element is inert in Chrome: `&` under `::placeholder` or `::-webkit-scrollbar-thumb` never applies, so the rule's earlier fallback declaration wins. Tailwind emits its colour fallbacks in exactly that shape (`color: var(--x); @supports (color: color-mix(…)) { color: color-mix(…) }`), so the whole app's placeholder and scrollbar colours collapsed to full ink — and the same shape also cost `--ink-secondary`/`--ink-muted`/`--ink-hairline`, `--theme-info-hover`/`--theme-warning-hover`, and the `.prose-content`/`.shiki .find-match` refinements. `flattenNestedAtRules` (`nested-at-rules.ts`) hoists each nested at-rule out of its rule with the parent selector resolved, preserving declaration order and the containing `@layer`, so the emitted CSS is `@supports (…) { .sel::placeholder { … } }` at the top level and no minifier has anything left to re-nest. The rsbuild pipeline this replaced compiled for browsers and flattened the nesting itself, which is why the migration surfaced it. `css.test.ts` builds a fixture through the real plugin with the production options and fails if `&` survives — asserting on the flattener's own output would not catch it.
- **Font faces cannot be bundled.** Bun's CSS loader resolves EVERY local `url()`: with `file` it inlines the font as base64 (592 kB stylesheet, ~377 kB gzipped, every face downloaded whether or not a formula renders) and with `dataurl` it writes the ABSOLUTE FILESYSTEM PATH into the CSS. A same-origin path is not an escape hatch — `url("/fonts/x.woff2")` fails the build with "Could not resolve"; measured against Bun 1.4.2, only `data:`, `http(s):` and protocol-relative urls are left alone. So the faces leave the bundle: the plugin rewrites them to `/fonts/<basename>` and strips them from the module, and the server re-declares them on `/fonts.css` by reading the same source stylesheets under `src/` on every request (`lib/assets/font-faces.ts` holds the extraction, shared by both ends) while `lib/assets/fonts.server.ts` resolves each basename back to the installed package. The server derives the sheet from source rather than from a directory the bundler wrote, because that artifact is produced once per process and can never be repaired — an `rm -rf` while the server runs, or a fresh clone that never built, left `/fonts.css` empty for the rest of the process and the terminal's Nerd symbols face silently vanished (tofu boxes, no error). The shell links it through `app-head` — a `<link href="/fonts.css">` in `index.html` would be resolved by the HTML loader and fail the same way.
- **`index.html`'s own asset references are relative** (`./public/icon.svg`), because the HTML loader resolves them and emits hashed copies; an absolute `/icon.svg` fails the whole build. The manifest's OWN icon entries stay absolute (`/icon.svg`): Bun does not rewrite inside a copied JSON file, and `public/` is served directly.
- **`public/sw.js` is served by a route, not by the bundler** — it is referenced only from an inline `<script>`, which the HTML loader does not scan, so it is never copied. `tryServeStatic` answers it from `public/`.
- **Asset roots are resolved from the package**, not the cwd (`lib/assets/fonts.server.ts` walks up from `import.meta.dir`). An installed package runs the AOT bundle with `dist/client` as its cwd, where a cwd-relative `public/` or `node_modules/` does not exist. Two questions, two resolvers, and they are NOT the same directory in every install shape: `packageRoot()` is the first root holding `node_modules` (where the DEPENDENCIES are — fonts are served from there), while `packageDir()` is the first root holding `src/` (where the PACKAGE is — the source stylesheets `/fonts.css` is assembled from live there). A **hoisted** install puts the package under `node_modules/ompchamber/` and its dependencies in the parent `node_modules/`, so `packageRoot()` is the PARENT — resolving `src/` through it found nothing, served an empty `/fonts.css`, and silently dropped every `@font-face` (the Nerd symbols face among them). Verified against a simulated hoisted published install: empty sheet through `packageRoot()`, full 4064-byte sheet through `packageDir()`.
- **The shell is rendered by fetching the server's own `/_shell` route.** Bun renders an HTML route only while serving, and there is no in-process API for an `HTMLBundle` — `new Response(bundle)` yields the string "[object HTMLBundle]" and `app.handle('/_shell')` answers 404, because the route lives in `Bun.serve`'s routing table rather than Elysia's. `index.ts` hands its listener to `plugins/shell.server.ts` for exactly this.
- **A shell that would not render reports the EDIT that broke it, and a `200` is not proof it rendered.** `renderShell` used to check only `!response.ok`, so a failed client bundle surfaced as "Shell route answered 500." — while the file, line and message sat inside Bun's own "Build Failed" page as a binary payload (`Uint8Array.from(atob(…))`) with no server-side reader. `lib/bundler/build-errors.server.ts` obtains them the supported way instead: after a failure, it rebuilds the same entrypoint with `Bun.build({ target: 'browser', throw: false })` and the plugins `bunfig.toml` names, and formats each `log.position` as `file:line:column  message` plus the offending source line. The probe is not a subset of the route's failures, deliberately: a **missing named export** is answered `200` by the route while Bun swaps the bundle for a 104-byte stub that only calls `location.reload()`, so the page cannot run and is reported as the real failure it is; an unresolved import that tree-shaking drops fails nothing and stays silent (verified against the route on Bun 1.4.2 — both `500` shapes reported, both `200` shapes handled as above). The check is on the MARKUP, not the status: with `development: false` Bun caches the HTML route's output, and a build that failed on the FIRST request leaves it caching an **empty body answered `200`** for every later request — measured `req1 500 len=0`, `req2..n 200 len=0`, still empty after the source was fixed, because production never rebuilds that cached output. `SHELL_MARKER` (`<!--app-bootstrap-->`, shared with the SSR route's substitution) is what distinguishes real markup from a cached failure; when the bundle builds cleanly but the markup is not the shell, the page says the fix is a RESTART, because that is the only thing that rebuilds it. Both the reason and the marker travel through the same 503 page, HTML-escaped — the reason carries arbitrary source lines, and a `<` in one would truncate the page at the first tag.
- **`serve.routes` and Elysia's routes coexist**: `new Elysia({ serve: { routes: { '/_shell': shell } } })` — Bun's table wins for the paths it declares, everything else reaches `app.fetch`, and Elysia's `websocket` handler is composed alongside.

### Browser E2E Layer (`tests/e2e/`)

- **The layer above `bun test`, and the only one that sees the assembled product.** Unit and component tests mount a tree in happy-dom; route suites call handlers in-process. Neither sees the SSR shell, the client bundle through Bun's asset routes, the realtime socket, a spawned `omp` child, or a real panel width. Every bug that reached a user this cycle lived there — a stream indicator that died 450 ms in, a toolbar clipped at 296px, a wiki link that opened a tab. The specs are the regression net for that class.
- **The MOCK update popup opens over the app on every boot, and a spec must dismiss it — with a locator HANDLER, not a click.** `MOCK=true` answers "an update is available" (`MOCK_CURRENT_VERSION`/`MOCK_LATEST_VERSION` in `lib/updates/check.ts`), so the Update dialog's `fixed inset-0` backdrop swallows every click. The check is ASYNCHRONOUS, so a click issued at `domcontentloaded` lands before the dialog exists and the later popup then blocks the next action — the flake this pins. `fixtures/app.ts`'s `openApp`/`installOverlayHandler` register a `page.addLocatorHandler` on the popup's "Later" button, which fires whenever it appears (and again on a reload). Do not "fix" this by disabling the popup or by sleeping.
- **A spec waits on a CONDITION, never a duration, and the condition must be the one the action needs.** Three real flakes were found and pinned this way: a send issued before the sidebar's folder list loaded had no `cwd`, fell to the mock path, and rendered nothing (the folder's name on screen is the gate); a reload issued before the 600 ms `session-state` debounce landed read the previous layout back (`page.waitForResponse` on the `POST` is the gate); and keystrokes typed as soon as `.xterm` was visible were written to a socket with no shell behind them and lost (the prompt's own bytes on the terminal socket are the gate). A `waitForTimeout` would have been too short on a loaded runner and wasted time on an idle one, in all three cases.
- **Assert the observable that actually changes, not the control you clicked.** The editor's saved state is an icon swap and its `aria-label` does not move, so the spec asserts the FILE ON DISK; xterm paints to a WebGL canvas with no text nodes, so the terminal spec asserts the terminal socket's frames. An assertion on the button, or on `.xterm-rows`, would have been vacuous.
- **A dialog's state is initialized by MOUNTING it fresh, never by a reset effect — and this spec is what found that.** `NewWorkspaceModal` kept one mounted form and cleared its fields in a `useEffect` keyed on `isOpen`; Preact runs effects AFTER paint, so the dialog was on screen and its fields focusable before the reset landed, and anything written in that window was discarded. Measured through this layer: a path typed into the field was wiped and the listing stayed on the home directory; the same bug in `DirectoryList`'s new-folder field left it empty with the submit button disabled. The fix is structural — `if (!isOpen) return null` and mount the form — so there is no ordering question to get wrong. The related lesson is that `fill()` is a legitimate way to find this: it writes synchronously after the element exists, which is exactly the window an effect-based reset loses.
- **`getByRole(name:)` matches a SUBSTRING, so a fixture's locator handler can click the wrong thing.** `installOverlayHandler` addresses the update popup's "Later" button; a spec that put a row named `appeared-later` on screen had that row matched and CLICKED by the handler, which navigated the dialog into the folder and made the row vanish — a failure that looked like a broken refresh. The handler's locator carries `exact: true`. Check every locator used in `addLocatorHandler` (and any handler that fires on a page-wide match) for this: the popup's own control is exactly "Later".
- **Two runners, disjoint globs, on purpose.** `bun test` owns `*.spec.ts`; Playwright owns `*.e2e.ts` (`testMatch` in `tests/e2e/playwright.config.ts`). The first version of this layer used `.spec.ts` and `bun test` imported the Playwright file into its own process, where `test.describe` throws "Playwright Test did not expect test.describe() to be called here". Never let the globs overlap — neither runner can be told to ignore a file the other owns without also hiding a real suite.
- **The runner is Playwright's own, in `tests/e2e/`, never `bun test`.** A browser spec needs a per-file context, a per-file server and a trace artifact — a lifecycle Bun's runner does not own, and one that fights its single-process, shared-`globalThis` model (the reason `test-support/isolated-db.ts` exists).
- **`fixtures/server.ts` boots a REAL server subprocess**, not an in-process Elysia app, because the thing under test is the assembled product. It is runtime-agnostic (`node:child_process`, `node:net`, `globalThis.fetch`) — it runs in a Playwright WORKER, which is Node, so a `Bun.spawn` there is a ReferenceError.
- **Isolation is the contract, and it is why `getDatabasePath` was fixed.** Every path the server writes is redirected under one temp root removed at teardown: `OMPCHAMBER_DATA_DIR`, `OMPCHAMBER_DB_PATH`, `PI_CODING_AGENT_DIR`, plus `SYNC_WORKSPACE=false`. `getDatabasePath` put the MOCK branch BEFORE the `OMPCHAMBER_DB_PATH` check, so a `MOCK=true` server started from a checkout wrote the repository's own `workspace.db` no matter what the caller set — verified, and pinned by `src/server/db.server.test.ts`. An explicit override now wins over BOTH defaults. Do not reorder those branches; a test that leaks into `~/.ompchamber` or the checkout's `workspace.db` corrupts the developer's machine.
- **Readiness is polled on `GET /api/health`, and the PORT is compared**, never parsed from the boot log. The route is a stable shape (`ok`, `mock`, `port`); a log line is prose a future edit may reword. Comparing the port is what stops a stale instance or a lost port race from being adopted silently.
- **`fixtures/fake-omp.ts` is the keystone, and it is a real protocol CLIENT, not a mock.** It speaks omp's NDJSON wire (`ready`, `{type:'response'}` with `command`/`success`/`data`, and the session event frames), so the code under test is the real spawn path, frame reader, frame fold, realtime topic and renderer. A double that stubbed any of those would test the double — the same argument `test-support/realtime-server.ts` makes. It honors the argv the chamber actually builds (`--mode rpc-ui --cwd … --resume … --approval-mode …`) and prompts select behaviour: `delay:<ms>`, `tool:<name>`, `ask:<text>`, `error:<text>`, `retry:<n>`, `slow`, default `Response to: <prompt>`.
- **The fake must emit the FULL accumulated `message_update` frames the chamber requests.** `configureChild` sends `set_event_filter {messageUpdates:"full"}`, so every `message_update` carries the whole message again — that is what the client folds. The fake re-sends the accumulated content on each delta (and the tool-call fixture re-sends its block with the name/id), so a spec observes the same shapes a real child sends.
- **`FAKE_OMP_RECORD_PATH` appends every RECEIVED frame as JSONL**, so a spec can assert what the chamber sent (that the event filter was requested, that a reload reached a live child) rather than inferring it.
- **Two modes, chosen per spec.** `mock` uses the seeded demo presets and needs no `omp` install (fast, no fake). `real` runs `MOCK=false` with `OMPCHAMBER_OMP_BIN` pointed at a shim that execs `fake-omp.ts` under Bun — the shim exists because the server spawns the path directly, so it must be executable. There is no model and no network in either mode.
- **Fixture data is created through the REAL API** (`fixtures/seed.ts` → `POST /api/folders`), never by writing the database. A hand-written row skips the route that resolves `project_path` and the scan the sidebar reads, so it tests a state the app cannot produce.
- **`data-testid` only where no stable accessible name exists.** The preference is `getByRole` + accessible name (the toolbars already carry `title`/`aria-label` on every icon-only button), then visible text, then a testid for a container to scope a query, a virtualized row, or a canvas. Measured: `src/` had ZERO testids before this layer; the set added is `app-root` (both layouts) and `composer-input`. Message rows already carry `id={msg.id}`, so a spec addresses a row by its id rather than by a new attribute. Add a testid as part of the spec that needs it, with a stable domain name — never speculatively, never layout detail.
- **The E2E project is typechecked separately** (`bun run typecheck:e2e` → `tsc -p tests/e2e`) because it runs under Node, not Bun, and the root tsconfig covers only `src/` and `packages/`. `ci.yml` runs this gate so a broken spec fails the cheap job, not only the browser one.
- **CI runs it on every push to `main`** (`.github/workflows/e2e.yml`), on a pull request only when the `e2e` label is applied, plus nightly and manual dispatch. A browser job is minutes, not seconds, so the label is the cheap-PR escape hatch — but a push to `main` is a merge, and it is verified there like the other gates. The release job's own `[skip ci]` commits do not re-trigger it (verified). Chromium is required; firefox/webkit are opt-in projects not yet run in CI. Failure artifacts (trace, screenshot, HTML report) are uploaded only on failure.

### Route Method Contract
- Route modules keep the ported Remix shape: an exported `loader` (GET) and/or `action` (mutating verbs). **`action` owns method dispatch** — it branches on `request.method` and returns its own `405 { error: 'Method not allowed' }`.
- Because of that, `bindingsFor`/`actionBindings` mount `action` on **all four** mutating verbs, and add a 405 GET fallback when the path has no `loader`. Registering only the "supported" verb would turn a wrong-verb call into a 404 and hide the real problem.
- **One parameter name per path position.** Elysia's router rejects `/api/files/:sessionId` and `/api/files/:fileId/toggle` in the same tree. When two routes share a segment position, unify the name (the handlers map it to their own local variable). Current shared names: `sessions/:sessionId` (also carries a folder id for `GET /api/sessions/:sessionId`), `files/:fileId`.

## Agent Operational Workflows

### Diagnostic Protocol on Build Failures
1. **Log Scrape**: Scrape build output from bun runner (matching `exit 1` conditions).
2. **Error Isolation**: Target the root failure point (e.g., missing package imports, type mismatch, or invalid asset clipping).
3. **Patch Generation**: Formulate a runnable bun terminal command (e.g., `bun add @superdesign/svg-geometry@latest && bun run build`).
4. **Execution in Chamber**: The user or agent triggers execution directly in the right sidebar chamber panel.

### Code Style & Persistence Guidelines
- Use the CSS variable system defined in `src/client/tailwind.css` (`var(--theme-ink)`, `var(--theme-paper)`, etc.) and standard Tailwind classes mapped to them (`bg-paper`, `text-ink`, `border-ink/20`).
- The application supports multiple themes (e.g., E-Ink Paper Monochrome, One Dark Pro Soft). **DO NOT** hardcode raw hex colors like `#141310` or `#faf8f3` in component files.
- Semantic states are expressed purely through these theme variables.
- Every theme write goes through `applyDocumentTheme` (`src/client/hooks/ui/theme.ts`): it sets `<html data-theme>` and dispatches `omp:theme-changed`. Writing `document.documentElement.dataset.theme` directly leaves runtime consumers that cannot see CSS (the mermaid hydrator repaints diagrams per theme) on the previous palette.
- The only allowable chroma (outside of dark theme) is the signal red variable `var(--theme-error)` (`text-error`, `bg-error`) reserved for failures and error messages. Syntax highlighting is an explicit, user-approved exception: it is provided by Shiki with the dual-theme pair `one-light` (light themes) + `one-dark-pro` (dark themes). Token colors arrive as `--shiki-light` / `--shiki-dark` CSS variables on `.shiki` spans — consume them in `src/client/tailwind.css` under `[data-theme]`, never hardcode token hex, and never reintroduce `--syntax-*` variables or `.token.*` classes.

### Changelog Policy (Release-Only)
- **NEVER edit `CHANGELOG.md` during normal work** — not for a feature, a fix, a refactor, a typo, or a version-less "unreleased" note. A task ends at code plus the gates in rule 8; the changelog is not part of it.
- `CHANGELOG.md` is written **only when cutting a release**, and releases are cut by `.github/workflows/release.yml` on every push to `main` — so since `0.6.0` the file is written **by the pipeline, never by hand**: `release.config.mjs` derives each `## [x.y.z] — YYYY-MM-DD` section from the Conventional Commits since the last tag, above the previous release (newest first), carrying the `[Keep a Changelog](https://keepachangelog.com/en/1.1.0/)` categories that apply (`### Added`, `### Changed`, `### Fixed`, `### Removed`). The section order, the header and the leading `### BREAKING CHANGES` group are that config's `commitTypes` and `writerOpts`; a new category means editing both.
- New sections link their compare range **inline** (`## [0.6.0](…/compare/v0.5.0...v0.6.0) — …`) and their bullets are commit subjects, not the hand-written prose the sections before `0.6.0` use, so the `[x.y.z]:` reference block at the file's tail stops at the last hand-written release. Never add to, reword or reformat a section that already shipped — it describes what shipped, not what a later change adjusted.
- Write entries as released behavior: a bullet **is** the commit subject, so the subject carries the changelog — name the behavior that changed, never a restatement of the diff. A type marked `hidden` in `release.config.mjs` (`chore`, `style`, `test`, `build`, `ci`) appears nowhere, and a type carrying `release: false` in `release/release-rules.js` cannot cut a version on its own — not even with a `!` on it, because the rules there shadow the analyzer's own `{ breaking: true }` fallback for every type this repository uses.
- A bullet credits its author — `… ([c148bc5](…)) (thanks [@octocat](https://github.com/octocat))` — unless that author is the repository owner, whose own commits carry the bulk of every release. `release/contributors.js` resolves the handle offline from GitHub privacy addresses (`NNN+login@users.noreply.github.com`) and asks the API about every other author, which is why the release job's `GITHUB_TOKEN` is what credits a contributor who commits with a real mailbox; bots (`[bot]` logins, `type: 'Bot'`) and unverified addresses get nothing, and a failed lookup never fails the release.

### Conventional Commit Type Selection
Every commit uses Conventional Commits — pick the type from what the diff actually does to observable behavior, not from how big it is:
- **`feat`** — new user-visible behavior: a feature, endpoint, setting option, or capability that did not exist before. A change that only reorganizes internals while the UI/API output stays identical is NOT a feat.
- **`fix`** — corrects existing behavior that was wrong: a bug, regression, wrong result, crash, or broken edge case. There must be a demonstrable "before was wrong" state; a behavior change that is merely a decision is not a fix.
- **`refactor`** — restructures code with zero external behavior change: renames, file moves/extractions, deduplication, type tightening, performance work with no visible effect.
- **`perf`** — the primary intent is a measurable performance improvement, with behavior unchanged.
- **`style`** — formatting/whitespace/import order only; no logic change. (`hidden` in `release.config.mjs`.)
- **`test`** — adds or repairs tests only; no production code change. (`hidden`.)
- **`build`** — toolchain, dependencies, build scripts (`package.json`, `bunfig.toml`, `scripts/build-client.ts`, `bun.lock`). (`hidden`.)
- **`ci`** — pipeline config only (`.github/workflows/`, `release.config.mjs`). (`hidden`.)
- **`chore`** — maintenance that fits none of the above (ignore files, secondary scripts). (`hidden`.)
- **`docs`** — documentation only (README, AGENTS.md, comments).
- **`BREAKING CHANGE`** — append `!` and a footer when a change requires callers/users to act: removed/renamed API, route, setting, or a changed contract. The changelog's `### BREAKING CHANGES` group comes from this footer. Two limits are enforced by `release/release-rules.js`, not by convention: **`!` releases a major version only on `feat`, `feature`, `fix`, `perf` and `refactor`** — on `chore`, `docs`, `ci` and the rest it releases nothing at all, so a breaking change to the build or the pipeline belongs in the type that carries it — and **the footer is read case-sensitively**, so it is written `BREAKING CHANGE: …` (or `BREAKING-CHANGE:`) at the start of a line. A lowercase `breaking-change` mention in prose is not a footer; before the pattern was pinned, one such line in a `docs` body cut a major release by itself.
| Mixed change in one commit: split into separate commits when the files are separable; if not, use the dominant type and note the rest in the body. The subject names the behavior that changed (it becomes a changelog bullet verbatim), the body explains the why/how — never restate the diff. `release/bump.test.js` asserts the whole table, and `.github/workflows/ci.yml` runs it (with the other three gates) on every pull request and on `main`.

### Package Releases (plugin-sdk / ui)

- **The published packages are versioned from commits too — never bump them by hand.** They are released by the SAME workflow as the app, `.github/workflows/release.yml`, whose `packages` job runs `node release/release-packages.mjs` and cuts a release per package through semantic-release. The version rules, the changelog shape and the contributor credit are the app's, reused rather than restated: `release/packages.mjs` reads `commitTypes`, `parserOpts` and `releaseRules` out of `release.config.mjs`.
- **The app releases AFTER the packages, in one chained run, and the order is load-bearing.** The app does not ship `packages/` (see its `files` list) — at runtime it resolves `@ompchamber/*` from its own `node_modules`, which is the version `bun.lock` records for those workspace packages, and a `workspace:` spec is substituted from the LOCK rather than the manifest. Releasing the app first therefore publishes stale pins: measured, `ompchamber@4.1.1` on npm declares both packages at `1.0.0` while they are at `2.0.0` (and `@ompchamber/ui@2.0.0` declared the SDK at `1.0.0` while the SDK was `2.0.0`). The `packages` job commits the refreshed `bun.lock`, and the `app` job `needs: packages` and fast-forwards to that commit before it installs and releases. The workflow is four jobs: `packages` → `packages-publish`, and `packages` → `app` → `app-publish`; a failed package release stops the app's, because the pin state would be unknown.
- **One workflow means one concurrency group, and that is the point.** A concurrency group is not a lock: it is a queue that DROPS pending members as it grows. An earlier revision split the releases across two workflows and shared one group between them so they could not race on their release commits; measured, two pushes in quick succession put four runs in the one group and GitHub cancelled the app's runs to keep the queue bounded, so the app stopped releasing entirely. With both releases in one workflow there is no second group to collide with, and each job's `git fetch origin main && git merge --ff-only FETCH_HEAD` covers the intra-run ordering.
- **Both release jobs fast-forward their checkout before installing, and that is not optional.** semantic-release refuses to release when the local branch is behind the remote — "The local branch main is behind the remote one, therefore a new version won't be published." — and it exits 0, so the run reports success while releasing nothing. Measured on this pipeline's first real run: the app's release had landed first and the packages run silently cut no release.
- **A release cuts the tag and the GitHub Release; the publish is dispatched.** The release commits are pushed with `GITHUB_TOKEN`, which raises no workflow run (only `workflow_dispatch`/`repository_dispatch` are exempt), so the `packages-publish` job calls `gh workflow run publish-plugins.yml -f packages=…` for exactly the packages that released, and `app-publish` calls `gh workflow run publish.yml -f tag=…`. Both publish workflows stay separate and keep the `npm` environment's approval gate, the gates and the tarball check.
- **The two release jobs repeat their setup steps rather than sharing them through YAML anchors.** GitHub does support anchors, but an alias carrying an entire step into a DIFFERENT job is not a shape the documented examples cover, and a parser that rejects it means no release at all, silently, on the push that needed one. Six short steps duplicated is the cheaper failure mode.
- **A rehearsal in a scratch clone still pushes to PRODUCTION.** `@semantic-release/git` pushes to `repositoryUrl`, which semantic-release reads from `package.json`'s `repository` field — **not** from the clone's `origin`. Measured: a "scratch" run with a local bare origin pushed two release commits and two tags to `github.com/rajebdev/ompchamber`, and the branch had to be reverted by hand (nothing was published — the tag push raises no workflow run, and this pipeline never publishes). `assertReleaseEnvironment` in `release/packages.js` now refuses to run outside CI unless `OMPCHAMBER_RELEASE_ALLOW_NON_CI=1`; **rehearse with `--dry-run`**, which skips every `prepare` step and pushes nothing.
- **`@semantic-release/npm` cannot write the version here, and that was found by rehearsing.** It shells out to `npm version`, and npm does not support the `workspace:` protocol this workspace declares its SDK dependency with: the run dies with `EUNSUPPORTEDPROTOCOL Unsupported URL Type "workspace:"` on a *sibling* package's manifest, after npm reifies the tree (it removed `node_modules` outright in the first attempt). `release/version-package.mjs` is a local plugin that writes the one field instead, with no package manager in the loop — which is safe precisely because this pipeline does not publish. `bun publish` in `publish-plugins.yml` is what packs the protocol correctly (verified: the published 1.0.0 tarball carries the exact SDK version).
- **Three mechanisms narrow one repository's history to one package, and all three are needed.** (1) A per-package `tagFormat` (`plugin-sdk/v${version}`) makes the range start at that package's own last tag. (2) A **path filter** in front of the analyzer and the notes generator keeps only commits that touched the package directory — a tag range still contains every app commit made in between, and a `feat(panels)` there would bump the package's minor version while its own code did not change (measured on this repo: 12 commits in `plugin-sdk/v1.0.0..HEAD`, 2 of them touching the SDK). (3) The local version plugin writes the new version into the package's own `package.json`, and its `verifyConditions` refuses a `private` package rather than cutting a release with nothing to publish.
- **The filter is applied by WRAPPING the two plugins, not by a shareable config.** `context.commits` is what both read and semantic-release hands the same context to every plugin in a step, so the only place a subset can be introduced is inside the plugin call. The wrappers are **step keys** (`analyzeCommits`/`generateNotes`), never entries in `plugins`: `validatePlugin` requires a `plugins` array's first element to be a string or plain object, while `validateStep` accepts a function — a function in `plugins` fails with `EPLUGINSCONF`, and the step keys are also the only place a function can carry options.
- **`release/commits.js` is the path lookup, because nothing upstream has it.** semantic-release's own collector (`git-log-parser`) reads a fixed field set — hash, author, committer, subject, body — and **no paths**. Two whole-range calls: `git log` once for messages and identities, and `git diff-tree --stdin --name-only -r --root` once for every hash (one process, and measured identical paths to `git log --name-only`). `--root` is what makes the repository's first commit list its paths at all. The scratch-repo test in `release/packages.test.js` is what pins it.
- **`scopeCommits` takes the repository as an argument** (`context.cwd`), not a path derived from the module. They are the same in the pipeline, but a caller whose commits came from elsewhere would otherwise have its hashes looked up in the wrong tree, where every commit reads as path-less — and a path-less commit is deliberately **kept** (a merge or an empty commit carries no change of its own, and dropping it would drop a `revert` git recorded that way). That "keep everything" failure is silent; the test caught it.
- **Catalog order is load-bearing and a failure STOPS the run.** `@ompchamber/ui` declares `"@ompchamber/plugin-sdk": "workspace:*"`, and `release/packages.js` is the one place a package's directory, tag prefix and manifest name are stated (`release/packages.test.js` asserts them against the tree). `.github/scripts/publish-plugin-packages.sh` exits on the first failure rather than publishing a `ui` after a failed SDK release.
- **A `workspace:` spec is substituted from `bun.lock`, NOT from the manifest — so bumping a version without refreshing the lock publishes a stale dependency.** `bun.lock` records a version for every workspace package, and `bun publish` reads that record. Measured in production: the version plugin bumped `packages/plugin-sdk` to 2.0.0 and committed it, but the lock still said 1.0.0, so the next release published `@ompchamber/ui@2.0.0` declaring `"@ompchamber/plugin-sdk": "1.0.0"` while the SDK was 2.0.0 on the registry — an install resolving the old SDK, which is exactly the incompatibility the 2.0.0 release existed to announce. Reproduced in isolation: bump `packages/a/package.json` without `bun install` and `bun pm pack` in a dependent `packages/b` still writes the old version. `release/version-package.mjs` therefore runs `bun install --lockfile-only` after each version write (`--lockfile-only` because the job has already installed and only the lock's record needs to change), and `@semantic-release/git` commits `bun.lock` beside the manifest — without the commit the refresh would be discarded and the next release would re-publish the stale pin. `release/packages.test.js` builds a two-package fixture and asserts the dependent package packs the NEW version.
- **A manual release still works and is still the escape hatch**: bump the version in the package's `package.json`, push `plugin-sdk/vX.Y.Z` (or `ui/vX.Y.Z`), and `publish-plugins.yml` publishes it. That workflow also takes `packages` (what the release workflow dispatches), `tag` (re-run one release whose publish failed, without re-creating it) and `package` (a hand-run fallback) — resolved in that order, and the tag/version match is checked for the `tag` input as well as for a tag push.

### GitHub Bot & Review Automation

`@ompchamber-bot` is a GitHub App plus the workflows in `.github/workflows/`; it triages every new issue and reviews every pull request. `CONTRIBUTING.md` is the contributor-facing half of this contract — read it before changing any of these files, because the two must tell the same story.

- **Writes go through the App, never `GITHUB_TOKEN`.** Every bot job mints an installation token from `BOT_APP_ID` + `BOT_APP_PRIVATE_KEY` (`actions/create-github-app-token`), so comments and labels come from `@ompchamber-bot` and cannot re-trigger a workflow that matches bot comments. Jobs are skipped outside `rajebdev/ompchamber`: a fork run has no App secret.
- **Command surface**, first line of a comment, exact match: `@<BOT_MENTION> help|review|summarize|triage|reproduce [focus]` (plus the `/oc-review` alias). `help` is answered without a model — it is a fixed string. The mention comes from the repository variable `BOT_MENTION` (default `ompchamber-bot`) rather than a literal, so an App whose slug differs still triggers: `bot-config-check.yml` is the one place that reads the App's real slug from its own installation token and reports the value to set.
- **The agent is the pinned `omp` CLI, run headless.** `.github/scripts/install-omp.sh` owns the version pin (`OMP_VERSION`); `.github/scripts/run-omp-bot.sh` runs `omp -p` with a persona file, a policy overlay, and the prompt on stdin. The runner needs `oven-sh/setup-bun`; `omp` is a Bun program.
- **Two provider modes, picked by whether `BOT_API_BASEURL` is set.** Unset: `BOT_MODEL` is a provider omp already knows and `BOT_API_KEY` is exported as the env var that provider reads (`BOT_API_KEY_ENV`, e.g. `DEEPSEEK_API_KEY`). Set: the model lives behind an OpenAI-compatible gateway, so the script declares a provider for the run from `.github/bot/provider-models.yml` and passes the key with `--api-key`. The second mode exists because omp ships no provider for an arbitrary base URL, and because **`--api-key` overrides the file's value while a `models.yml` `apiKey` cannot reference an environment variable** (`$VAR` and `${VAR}` are both literally true strings — verified against a local OpenAI-compatible stub) — so the template carries a placeholder and the real secret never touches the runner's disk. A thinking level (`BOT_THINKING`) only reaches the provider when the model entry declares `reasoning: true` — verified against the stub: without that line `--thinking` is accepted and silently dropped, with it a `--thinking high` run arrives as `reasoning_effort: "high"`. The template carries the line; a model's declared `efforts` may never include `off` (the schema rejects it, and omp clamps `off` up to the lowest listed effort). Repository settings: secret `BOT_API_KEY`; variables `BOT_MODEL`, `BOT_API_BASEURL` (optional), `BOT_API_KEY_ENV` (required only when `BOT_API_BASEURL` is unset), `BOT_THINKING` (optional, default `high`), `BOT_MENTION` (optional, default `ompchamber-bot`). The three provider settings are read from either store (`vars.X || secrets.X`), so a value placed in Secrets still works. **`BOT_MENTION` must be a variable**: every command trigger is a job condition, and a job condition may read `github`, `needs`, `vars` and `inputs` — never `secrets` — so a secret of that name is silently ignored and the default is used instead (`bot-config-check.yml` reports exactly that).
- **Policy is data, in the `.github/bot/*.yml` policy overlays.** `tools.approval.<tool>: deny` plus a `bash.patterns` allowlist ending in `- match: "*"` / `deny` gives a deny-by-default session; the reviewer cannot edit a file or run anything but `gh`, `git`, `rg`, `ls`, `cat`. **Never write `approval: prompt`**: there is no UI on a runner, so a prompt is a rejected call that reads to the model as a broken tool.
- **Procedure is versioned with the repository**, in `.omp/skills/{pr-review,issue-intake}/SKILL.md`, read by the agent through `skill://`. The persona files (`.github/bot/*.persona.md`) hold identity, guardrails and the exact output contract; the skills hold the steps. A 25 KB prompt never lives in a workflow.
- **Nothing downstream trusts the model.** `verify-review-verdict.sh` re-reads the posted comment from the API, requires the final line to be the marker `<!-- omc-review-meta {"head":"…","verdict":"…"} -->`, checks that the marker's HEAD equals the requested HEAD and is still the current one, that the human-readable verdict and reviewed-HEAD lines agree, and only then writes one `review:*` label. A mismatch fails the job and marks `review:automation-failed`; the verdict itself never fails a check. The human-readable checks read **values, not decoration** (backticks, bold, whitespace): a live run posted a correct review with every backtick stripped on the way to the API, and a gate stricter than the generator turns a finished review into a wasted run — the HEAD must still be named as a complete token, so tolerance applies to formatting and never to content.
- **Readiness is a label, not a comment**: `review:pending|ready|needs-evidence|blocked|human-required|automation-failed`. Exactly one at a time — `set-review-status.sh` is the only writer. Drafts carry none.
- **Trust boundary**: `pull_request_target` runs with secrets, so the base is what is checked out and the head is fetched as passive git data — never installed, built, or executed. A diff touching `AGENTS.md`, `CONTRIBUTING.md`, `.github/{workflows,scripts,bot,ISSUE_TEMPLATE}/**`, `.github/PULL_REQUEST_TEMPLATE.md` or `.omp/skills/**` is refused (`review:human-required`): automation must not clear a change to its own policy.
- **Logic lives in `.github/scripts/*.sh`, not in YAML.** Each script takes arguments and reads its state through `gh`, so it can be exercised locally against a stubbed `gh`; the workflow steps stay thin glue. When adding a gate, add it as a script.
- **Never put user content into a `run:` block through `${{ }}`** — title, body, comment text and focus go through `env:` and are read as shell variables. `run-omp-bot.sh` pipes the assembled prompt to `omp` on stdin for the same reason: no interpolation into shell text, no argument-quoting hazard.
- Editing any of these files is a `ci`-type change; the review-policy paths above mean the pull request that changes them will be marked `review:human-required` and must be read by a human.

## Codebase Architecture & File Organization Rules

### 1. File Size Ceiling (Hard Limit: 350 Lines)

- **Maximum 350 Lines Per File**: Every TypeScript and TSX file must strictly stay under 350 lines of code (`wc -l` result `< 350`).
- **Decompose before you hit the limit**: When a file approaches the ceiling, split it immediately — never let it cross 350 and never "temporarily" exceed it.
- **Extraction patterns** (pick the one that matches the code):
  - Large render blocks ➔ sub-components in the parent's kebab-case folder (`git-panel/TreeView.tsx`).
  - Stateful logic clusters ➔ custom hooks under `src/client/hooks/<domain>/`.
  - Pure functions / constants / validators ➔ `src/shared/lib/<domain>/` modules.
  - Large callback objects / factories ➔ factory functions taking a single `deps` record (preserves closure semantics exactly).
  - Shared low-level utilities ➔ a sibling `shared/` or `utils.ts` inside the feature folder.
- **Verify**: `find src -name "*.ts" -o -name "*.tsx" | xargs wc -l | grep -v total | awk '$1>350'` must print nothing.

### 2. Folder & Filename Conventions (Clean Names)
- **Symmetrical folders**: A component's folder mirrors its name in **kebab-case**, and the folder's main entry is `index.tsx`:
  - `ChatTimeline` ➔ `src/client/components/workspace/chat-timeline/index.tsx`
  - `GitPanel` ➔ `src/client/components/workspace/git-panel/index.tsx`
  - `SessionSidebar` ➔ `src/client/components/layout/session-sidebar/index.tsx`
  - `ModelDropdown` ➔ `src/client/components/workspace/model-dropdown/index.tsx`
- **Suffix-only filenames**: When the folder already supplies the context, child files DROP the redundant prefix and keep only the suffix:
  - `src/client/components/workspace/model-dropdown/Header.tsx` — not `ModelDropdownHeader.tsx`
  - `src/client/components/workspace/git-panel/TreeView.tsx` — not `GitTreeView.tsx`
  - `src/client/components/workspace/chat-timeline/tool-renderers/panels/Bash.tsx` — not `BashPanel.tsx`
  - `src/client/hooks/chat/timeline/actions.ts` — not `useChatTimelineActions.ts`
  - `src/shared/lib/omp/rpc/manager.ts` — not `rpc-manager.ts`
- **No duplicate basenames in the same folder**: if two files would collide, move one to its correct domain folder or give it a distinguishing suffix (e.g. `panels/SearchTool.tsx` vs `panels/SearchFs.tsx`).
- **`index` is reserved for the folder's real entry point** (the main component/hook implementation) — never a re-export barrel (see rule 3).
- **Naming case**: kebab-case for folders and multi-word non-component files (`active-project.ts`, `notification-sound.ts`); PascalCase for Preact component files; `useXxx` prefix only when the file is a standalone reusable hook at a domain root.
- Reusable or cross-cutting components belong in `src/client/components/common/`.
- No empty, abandoned, or ghost folders (`src/applet/`, duplicate domain folders, etc.).

### 3. Direct, Explicit Imports (No Barrel Clutter)
- Do NOT create re-export-only `index.ts` barrels inside `src/client/components/`, `src/client/hooks/`, or `src/shared/lib/` — they pollute editor fuzzy-search and hide file origins.
- `index.tsx`/`index.ts` is allowed ONLY when it contains the folder's actual implementation (the main component/hook), not a list of `export ... from` statements.
- Import the concrete module explicitly via the `@/` alias:
  - `import { ChatTimeline } from '@/client/components/workspace/chat-timeline';` (folder entry)
  - `import { Header } from '@/client/components/workspace/model-dropdown/Header';`
  - `import { useChatTimeline } from '@/client/hooks/chat/timeline';`
  - `import { toTitleCase } from '@/shared/lib/chat/title-case';`
- The only intentional barrel is `src/shared/types/index.ts` (the central type barrel).

### 4. Absolute Imports via `@/` Alias (No Relative Imports)
- **All** internal imports MUST use the `@/` path alias (mapped to `./src/*` in `tsconfig.json`, which Bun's bundler reads directly). Relative imports (`./`, `../`) are **forbidden** in application code.
- This applies to every import form: `import`, `import type`, `export ... from`, and side-effect imports.
- Examples:
  - `import { ChatTimeline } from '@/client/components/workspace/chat-timeline';`
  - `import type { OmpSession } from '@/shared/types/omp/session';`
  - `import { getDb } from '@/server/db.server';`
  - `import '@/client/tailwind.css';`
- Exceptions (keep relative):
  - Third-party packages and node built-ins (never prefixed with `@/`).
  - Assets outside `src/` (e.g., `package.json` at the project root) — use a relative path.
- The `~` alias is deprecated; use `@/` exclusively.
- **Verify**: `grep -rnE "from '\.\.?/" src --include='*.ts' --include='*.tsx' --include='*.js' | grep -v node_modules` must print nothing. `src/cli/**` is covered by this gate too — it is Bun-run plain ESM, so `@/cli/...` resolves there like everywhere else.

### 4b. Import Preact Directly (zero React packages)
- **Never write `from 'react'` or `from 'react-dom'` in `src/`.** Import the runtime directly:
  - Hooks → `import { useState, useEffect, useRef } from 'preact/hooks';`
  - Components, context, portals, and React-shaped types → `import { memo, Suspense, lazy, createContext, createPortal } from 'preact/compat';`
  - Generic element/event types → `import type { TargetedMouseEvent, TargetedKeyboardEvent } from 'preact';`
- **Zero-react state:** package.json contains no React packages and `tsconfig.json` carries no `react*` alias. The three former shim consumers were replaced: `react-icons` → `lucide-preact` + static brand SVGs (`src/client/components/common/file-icon/`), `react-simple-code-editor` → the hand-rolled editor in `src/client/components/common/code-editor/`, `react-resizable-panels` → the hand-rolled group/panel/separator trio in `src/client/components/layout/desktop-layout/resizer/`.
- **Adding dependencies:** if a package imports `'react'` in its published code, either pick a Preact-native alternative or hand-port the small surface you need — never re-introduce a react→preact alias to accommodate it.
- **Event types:** Preact's `MouseEvent`/`KeyboardEvent` from `preact/compat` are generics requiring one type argument. Use `TargetedMouseEvent<HTMLElement>` for JSX handlers, and the DOM's own `globalThis.MouseEvent`/`globalThis.KeyboardEvent` for native `addEventListener` callbacks and xterm handlers.

### 5. Server vs Shared vs Client Modules
- **Three-way split.** `src/server/**` is Bun-only (see the Runtime section at the top), `src/client/**` is browser-only, and `src/shared/**` is imported by both. Never import a `node:` builtin or `bun:sqlite` from `src/client/**` or `src/shared/lib/**`; if a shared module needs one, it belongs in `src/server/lib/**` instead.
- Non-UI modules MUST be grouped into domain subfolders — never dumped flat in the root of `src/client/hooks/`, `src/client/data/`, `src/server/lib/`, `src/shared/lib/`, or `src/shared/types/`.
- **`src/client/hooks/<domain>/`**: `chat/`, `ui/`, `workspace/`, `browser/`, `models/`, `settings/`. Split further when a family grows: `chat/timeline/` (timeline state + actions), `chat/omp/` (live agent bridge), `settings/providers/` (provider settings state, API calls, actions, messages).
- **`src/shared/lib/<domain>/`**: `chat/`, `code/`, `fs/`, `markdown/`, `models/`, `omp/`, `workspace/`. `omp/` splits into `core/`, `rpc/`, `session/`, `config/`; `models/` splits into `provider/` for the provider family (dialect, presets, models, connection, cleanup, label, glyph).
- **`src/server/lib/<domain>/`**: the same domain tree, holding only the modules that touch Node/Bun builtins or the database. A server family splits the same way (`omp/session/usage/` holds the aggregator and its presentation shaping).
- **`src/client/data/<domain>/`**: `settings/`, `samples/`, `mock/`, `models/`, `theme/`, `agent-data/`, `context-data/`.
- **`src/shared/types/<domain>/`**: group related interfaces (`settings/`, `omp/`); truly cross-cutting types stay at the root.
- Grouping changes are atomic: move the files AND update every importer in the same change.

### 6. Pure UI Components & Semantic Separation
- **`src/client/components/` is for Preact UI (`.tsx`)**. Co-located pure helpers are allowed when scoped to that feature, but must be `.ts` and live under the feature folder or its `shared/` (e.g. `tool-renderers/shared/detect-format.ts`, `editor/utils.ts`).
- Anything reusable beyond a single feature belongs in `src/shared/lib/`, never in a component folder.
- **Dedicated non-UI directories**:
  - **Hooks (`src/client/hooks/<domain>/`)**: Custom Preact hooks.
  - **Data (`src/client/data/<domain>/`)**: Mock or static datasets.
  - **Types (`src/shared/types/<domain>/`)**: Domain interfaces and types.
  - **CLI (`src/cli/`)**: The `ompchamber` command-line entry (`ompchamber.js`) and its `lib/` (arg parsing, process lifecycle, registry, serve/update/stop/restart/status/logs). These stay `.js` (plain ESM, no build step) and run under Bun via the `#!/usr/bin/env bun` shebang. `pkgRoot` is resolved two levels up from `src/cli/ompchamber.js`; keep that depth if the file ever moves.

### 7. Domain Types Architecture
- Domain data models and shared TypeScript interfaces must be organized cleanly under `src/shared/types/`:
  - `workspace.ts` — folders, session entities, and sorting types
  - `fs.ts` — file explorer node trees, opened files, and search result items
  - `git.ts` — git changes, branch lists, and view mode states
  - `chat.ts` — messages, agent actions, monologue, and attachments
  - `settings/` — settings state and per-category settings shapes (`agent.ts`, `command.ts`, `mcp.ts`, `project.ts`, `provider.ts`, `skill.ts`, `state.ts`)
  - `omp/` — oh-my-pi bridge types (`session.ts`, `agent.ts`)
  - `index.ts` — central export barrel for all types (`import type { ... } from '@/types'`)

### 8. Verification Requirements
- Every change must pass:
  1. `bun run lint` (`tsc --noEmit`) without errors.
  2. `bunx tsc --noEmit --noUnusedLocals --noUnusedParameters` without errors.
  3. `find src -name "*.ts" -o -name "*.tsx" | xargs wc -l | grep -v total | awk '$1>350'` no file over 350 line codes
  4. Production build verification (`bun run build`).
- **Unused Code Check (MANDATORY before task completion)**: Before declaring any task done, verify no unused imports, locals, or dead props were introduced or left behind:
  - Fix every `TS6133` (declared but never read), `TS6192` (all imports unused), `TS6196` (declared but never used), and `TS6198` (all destructured elements unused) error.
  - Remove unused imports (icons, types, components) and unused destructured props/state — do not leave dead code behind.
  - If a component's props/state become unused because a feature was stubbed or removed, strip them from the interface, the destructure, and every call-site in the same change.
  - Do NOT ship `import React from 'react'` in `.tsx` files — the Preact JSX transform makes it unnecessary (keep named imports like `useState`).
- **Structural Checks (MANDATORY for refactors that move/rename files)**:
  - No file exceeds 350 lines (rule 1 command).
  - No relative imports remain (rule 4 command).
  - No duplicate basenames inside the same folder.
  - Every moved/renamed file's importers are updated in the same change; grep for the old path returns nothing.

### 9. Layout & Panel Resizing
- **Two width units, deliberately.** The **sidebar** is stored in **pixels** — it holds a session list, which does not get more useful on a wider monitor. The **editor and the right panel** are stored as a **share of the group's available area** (a fraction), because a pixel width is only right on the display it was dragged on. A slot may carry both; the fraction wins when the area is known, and the px value is what it renders at before then.
- **Sizes are px at the resizer boundary.** The hand-rolled resizer (`src/client/components/layout/desktop-layout/resizer/`) is px-only end to end: fixed panels get a px flex-basis and one filler panel absorbs the remainder. A fraction is resolved to px *before* it reaches a `Panel` — never pass a percentage string into `defaultSize`/`minSize`, because `toPx` parses it with `parseFloat` and `"45%"` would silently become 45px.
- **The panel ceiling is dynamic, not a constant, and the editor + right panel are a COUPLED PAIR.** `resolvePanelWidth` (`src/shared/lib/workspace/panel-widths.ts`) caps a panel by the smaller of three things: its own max (`PAIR_MAX_FRACTION` = 0.6), the pair total minus what the sibling reserves (`PAIR_MAX_TOTAL_FRACTION` = 0.7), and the group budget (`available − chat floor − the sibling's reserved width − handles`). The defaults are editor 0.4 + right 0.3 = 0.7, so growing one forces the other down and neither can reach 0.6 while the other is open. The right panel has ONE default fraction for every view (`DEFAULT_RIGHT_PANEL_FRACTION`) — a per-view table cannot coexist with the pair, because the two defaults must sum to the total (a 0.6 terminal beside a 0.4 editor is 1.0); views differ only by their floor and their remembered width. `WorkspacePanels` resolves the RIGHT panel first (reserving the editor's WANTED share), then the editor (reserving the right panel's ACTUAL width) — that asymmetry is what makes an editor asking past its default push the right panel down first, with the pair still summing to 0.7. Reserving only a sibling's FLOOR is the shape that broke: the two declared widths summed past the group, flexbox shrank BOTH, and the right panel rendered 15px under its share (measured at 1440 with both open: editor asked 507 / rendered 477, right asked 245 / rendered 230). Verified in the browser at 2K: defaults render editor 40% / right 30%; an editor wanting 0.5 renders 50% / right 20%; an editor wanting 0.9 caps at 60%. The pair cap is computed in PIXELS and ROUNDED (`0.7 × 4000` is `2799.9999…` in binary floating point).
- **One remembered width PER PANEL, never per group**: the sidebar, the editor panel (a separate width for source tabs and for diff tabs), and each of the eleven right-panel views (`context`, `files`, `search`, `git`, `wiki`, `terminal`, `user-browser`, `browser`, `usage`, `todo`, `plan`) each own their width — the sidebar's lives in its own module (see the GLOBAL rule below), the rest in `src/shared/lib/workspace/panel-widths.ts` (data) and `src/client/hooks/workspace/panel-widths.ts` (state); the single default fraction, px defaults, per-view minimums, and the view list live in `src/shared/lib/workspace/right-panels.ts`. Sharing one number between panels — or resetting a panel to a hard-coded width when it is toggled or switched — is exactly the bug this shape exists to prevent.
- **The sidebar's width is GLOBAL, and that is the one exception to "per session".** It lives in `app_settings.omp_sidebar_width` (`src/shared/lib/workspace/sidebar-width.ts` + `src/client/hooks/workspace/sidebar-width.ts`), beside the sidebar's other cross-session state (`omp_sidebar_expanded_sessions`, `omp_sidebar_sort`) — never in `layout.panelWidths`. The sidebar lists the same sessions in every chat and only the highlight moves, so a width that changed when the user picked a different session read as the layout jumping on its own. It was not always global: `0004c95` (2026-09-23) swept the sidebar into the per-session map along with the editor and the right panel, which had a real reason to be there, and `9d361a9` (2026-10-08) then dropped the `desktopLayoutSizes` seed that had been keeping a dragged width global — so a `left` slot existed in `layout.panelWidths` for two weeks and 120 sessions on the author's install carry the same seeded 351 while a handful carry a local drag. `resolveSidebarWidth` therefore migrates by PRECEDENCE — stored setting, else the retired GLOBAL `desktopLayoutSizes.left`, else the open session's slot — because adopting a session slot first would move the sidebar 351 → 500 on the first switch. A `left` slot is deleted from a session blob on the first open after the upgrade and dropped by `mergePanelWidths`, so no stored state keeps a second answer.
- **Widths are per session for the editor and the right panel, and a new session starts EMPTY.** They live in `session_ui_state` under `layout.panelWidths`, beside the rest of a session's layout state (`layout.activeRightPanel`, `layout.showRightPanel`, `layout.showLeftPanel`, `layout.userToggledEditor`, `layout.openedFiles`), so switching sessions restores the layout that session was left in. A session that has never been resized has no `panelWidths` at all, so every panel resolves from its own default fraction (`DEFAULT_EDITOR_FRACTIONS`, `DEFAULT_RIGHT_PANEL_FRACTION`) or px fallback. **There is deliberately no global seed for these** — a former `app_settings.desktopLayoutSizes` carried the last global drag into every new session, and since the per-session migration nothing wrote it, it froze at a stale value and pinned a new session's editor to its 320px floor (measured) while the diff tab opened normally. Writing to it could not repair it either: the write would have to run before the session's own blob loads and would clobber it with the global value. The SIDEBAR is the exception and is global — see the rule above.
- **A pending `new-…` session's UI state is loaded like any other session's, because it is persisted like any other.** The id is what the URL carries (`?sessionId=new-…`), so a reload of a pending chat — a dev-HMR reload, or a second tab — re-enters that slot with a row already on the server. `SessionStateProvider` used to short-circuit it as "fresh, nothing stored yet" and mark it ready without a fetch; every consumer then showed its fallback (the repo picker reset to the workspace root, the right panel jumped back to `files`) **and the next write destroyed the stored blob**, because `persistSession` posts the WHOLE in-memory map — a state that was never loaded persisted as one key. `markSessionReady` existed only for that short-circuit and is gone; the only special case left is spawn adoption (`migrateSessionState`), which reads the transient slot's now-hydrated cache.
- **A resize drag is deferred.** The separator moves a ghost guide line and re-applies the real width at most every `RESIZE_FOLLOW_INTERVAL_MS`; the panel's own 200ms width transition smooths the steps. Applying the width on every `pointermove` reflows an xterm buffer, a CodeMirror document and a browser iframe per frame, for a width the user is still choosing.
- **A collapsed panel stays mounted.** `Panel`'s `collapsed` prop renders it at zero width and marks it `data-panel-collapsed`, so its state (tree expansion, terminal buffer) survives and the width transition has something to animate. The separator walks past collapsed panels when it resolves its neighbours — pairing a drag against a zero-width panel whose registry floor still reads 320 clamps every delta to zero and kills the handle.
- **Restore through props, not imperative rebuilds**: every panel's `defaultSize` is derived from the remembered width for its current slot, and `Panel` adopts a changed `defaultSize` itself — that covers a right-panel view switch and an editor source↔diff switch, both of which keep the panel mounted while only its width slot changes. No layout cache exists to go stale. Append an entry here if a new resizable group is introduced.

### 10. Route Organization & Domain Grouping
- **Domain-Based Subdirectories**: Routes under `src/server/routes/` MUST be organized and grouped into subdirectories matching their functional domain (e.g., `src/server/routes/settings/`, `src/server/routes/chat/`, `src/server/routes/fs/`, `src/server/routes/terminal/`, `src/server/routes/telemetry/`, `src/server/routes/sessions/`, `src/server/routes/files/`, `src/server/routes/folders/`).
- **No Monolithic Flat Folder Clutter**: Do NOT dump API endpoints loosely in the root of `src/server/routes/` as flat files. `src/server/routes/index.ts` is the only file that enumerates domains; every domain folder owns its own modules and never imports a sibling domain.
- **One Elysia plugin per domain**: Each domain folder exports `HandlerBinding[]` built from its route modules (see `src/server/lib/route-adapter.ts`). Route modules keep the ported Remix shape — an exported `loader` (GET) and/or `action` (mutating verbs) — so status codes and payloads stay identical to the pre-migration API. Prefixes are declared once, in `routes/index.ts`.

### 11. Environment Data Modes (`MOCK=true` vs `MOCK=false`)
- **`MOCK=true` (Simulation & Demo Mode)**:
  - All features and loaders utilize rich predefined datasets and presets from `src/client/data/` (simulated demo chats, token telemetry ranges, agent/project presets).
  - Database seeding automatically injects sample workspace folders, demo commit sessions, and file structures.
- **`MOCK=false` (Real Data Mode)**:
  - The application operates strictly against real backend resources and real SQLite database persistence.
  - No synthetic sample sessions, fake dialogues, or hardcoded mock files are auto-injected.
  - Managed globally through `Bun.env.MOCK` and verified via `@/server/mock.server`.
